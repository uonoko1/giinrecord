# スクラムのエージェント定義

`docs/WORKING_AGREEMENT.md` の役割（PO / 開発者 / レビュアー）を、サブエージェントの定義として置いたもの。

| ファイル | 役割 | 使い方 |
|---|---|---|
| `developer.md` | 開発者。Ready の PBI を1つ担当。専用 worktree で TDD → 変異テスト → PR | Ready の件数ぶん（最大5）を**同時に**立ち上げる |
| `reviewer.md` | 敵対的レビュアー。実装者とは別人。別 worktree で変異を入れて壊しにいく | PR ごとに1人。データの経路・セキュリティに触る PR は必ず |

## PO（メインセッション）がやること

**PO は実装しない。** 2026-09-04 に PO が5件を直列で自分で実装し、ユーザーに
「作業はスクラムでやってね。Ready のタスクは5つくらいサブエージェントを立てて並列で」と指摘された。

1. **スプリントプランニング**: 計測に基づいて PBI を切り、`ready` ラベルを付ける。
   受け入れ条件は「内容を削って条件を満たす」誤った直し方が通らない形に書く
2. **開発者を Ready の件数ぶん同時に立ち上げる**（`Agent` ツール。定義は `developer.md` を読ませる）。
   worktree は `<scratchpad>/wt/<issue#>`。
   - **同じファイルを触る PBI 同士は、触る場所を分ける指示を書く。**
     「末尾に足す」だけでは足りない——**全員が末尾に足すと、そこで衝突する**（2026-09-04、
     #423 / #424 / #425 が `target-size.test.ts` の末尾に `describe` を足して 3-way で衝突した）。
   - **足す場所を PBI ごとに指定する**（「#423 は `.links` の describe の直後」「#424 はその次」）か、
     **ファイルを分ける**（`target-size-links.test.ts` のように）。後者のほうが確実
   - 先にマージされた PR に合わせて、残りは rebase する。**中身を変えずに解消させる**
3. 開発者から PR が来たら**レビュアーを立てる**（`reviewer.md`）。
   **その報告を PR のコメントに貼る**（`gh pr comment <pr> --body-file <報告>`）——
   **`merge-when-green.sh` はそのコメントが無ければマージしない**（#1006）
   - **例外なし。** 2026-09-23〜24 に PO が **2 日で 33 本を 1 件もレビューさせずにマージ**した
     （09-23 に 21 本、09-24 に 12 本。ユーザーの指摘で発覚）。
     **PO はこの数を 2 度間違えた**——最初「1 日で 31 本」、直して「2 日で 32 本」。
     **2 度目も誤りで、PR #1000 自身が母数から漏れていた**（レビュアーが 2 度とも数え直した）。
     **「数を確かめずに書く」ことを戒める文書が、その数を 2 度外している。**
     **自分で検算したから十分だ、と判断したのが誤り**である——
     **PO の検算は「PR の主張が正しいか」しか見ておらず、「PR が試していない壊し方」を見ていない。**
     それが `reviewer.md` の 4 番（**PR が試していない変異を入れる**）であり、**PO には代われない。**
   - **「docs だけ」「測定だけ」もレビューさせる。** 測定の PBI は
     **数字が間違っていても緑になる**——実例: `docs/DATA_CONTRACT.md:237` の
     「いちばん小さい境は青森 11」が誤りのまま残り、**#1007 が数え直したら
     ずれていたのは 1 か所ではなく 8 か所**だった。
     しかも `assert.equal(11 - SEATS_CHANGED_FLAG, 1)` という**定数どうしの恒真式**があり、
     **実測が何であっても永久に緑**だった。
   - **自動マージ（`gh pr merge --auto`）を armed にするのはレビューの後。**
     先に armed にすると、緑になった瞬間に GitHub が畳んでレビューの機会が消える。
   - **レビュアーが間違っていることもある。ただし、今のところ実測ではほとんど間違っていない。**
     - **実測**: PR #1000 のレビュー 7 件は、**担当者自身が「7 件とも正しく、7 件とも自分で再現した」**と
       書いている（PR #1000 本文）。**的中率 7/7。**
     - **PO はここを「およそ半分」と書いて、レビューの重みを割り引く規則を作りかけた。**
       **「担当者が自分の誤りを 3 件認めた」のを「レビュアーが 3 件外した」と取り違えていた**
       （レビュアーが一次資料で指摘）。**根拠の無い数字で規則を緩めようとした。**
     - **だから立証責任は差し戻される側に置く**: **担当者は、指摘を再現できなかったことを
       コマンドと出力で示す。示せなければ差し戻しは有効。**
       **「再現できません」の一言で差し戻しを消さない。**
     - **PO とレビュアーが対立したら、PO が実物で確かめて裁定し、撤回した理由を残す。**
       （**前例として `docs/WORKING_AGREEMENT.md` の「レビュアーが関数単体を見て差し戻し、
       PO が呼び出し側を確認して撤回した」を引きたくなるが、あの節の教訓は
       「実物で確かめろ」であって「レビュアーは外すから割り引け」ではない**——
       PO が自分に有利な向きに読み替えかけたのをレビュアーが正した。）
     - **「再レビュー」を無限に繰り返さない。** 止める人が要る。それは PO である。
4. レビューが通ったら `scripts/po/merge-when-green.sh <pr>` でマージ（手で `gh pr merge` しない）
   - **差し戻したら、直った版を必ず再レビューさせる**（別のレビュアーでよい）。
     **設計が変わっているので、1 度目のレビューは効かない。**
     **「2 度目だから通す」ではなく「2 度目だからこそ念入りに」。**
   - **詰まったらモブに切り替える**（ユーザーの提案、2026-09-24）。
     - **機械で測れる条件は 2 つだけ**（それ以外は判断だと正直に書く）:
       **(a) 同じ指摘で 2 回以上差し戻している**（PR のレビューコメントで数えられる）、
       **(b) 担当者が「分からない」と申告した**（報告に書いてある）。
     - **(c) 「1 人では射程が足りない」（共有層・複数県・本番の経路にまたがる）は判断である。**
       **測定ではない。** しかも**ほとんどの ETL の PBI が当てはまる**ので、
       **これを「条件」と呼ぶと、好きなときにモブにできる抜け道になる**（レビュアーの指摘）。
       **使うなら、判断した理由を PR か Issue に 1 行残すこと。**
     - **起動するのは PO。** (a)(b) を満たしたら、**PO が `Agent` で 3 人立てる。**
       条件だけ書いて動詞が無いと発火しない。
     - **モブのやり方**: 同じ PBI に**役割を変えた 3 人**——**実装 1 / 敵対的レビュー 1 / 別解を探す 1**。
       **同じ worktree を共有しない**（**1 つの worktree は 1 つのブランチしか持てない**ので、
       3 人が同じディレクトリで作業すると互いのブランチを切り替えてしまう。
       **これは git の原理上の制約で、この事故の記録は `docs/sprints/` に見つからなかった**——
       **PO が「Sprint 14 の事故」と書いたが出典が無く、代わりに挙げた 16/17/25 も
       worktree の有用性と掃除の話だった**（レビュアーが 2 度とも指摘））。
       **3 人の結論を PO が突き合わせ、食い違いを潰してから 1 本の PR にする。**
     - **モブにしないほうがよい場合**: **担当者が自力で直せているとき。**
       実例: **PR #1000** の担当者は敵対的レビューの 7 件を**7 件とも自分で再現し、
       うち 3 件は自分の誤りと認めて直した**（テストは `pdf-row-order.test.ts` が **8 → 19 件**、
       変更した 2 ファイルの合計で **32 件**。**PO は中間コミットの 17 件を最終値として書いていた**）。
       **ここにモブを入れると遅くなるだけである。**
5. **リリースして本番で確認**（「リリースされて初めて成果物」）。リリース前の状態を記録してから出す
6. **レトロ**: `docs/sprints/` に書く。作業合意に足すものがあれば PR にする

## PO がやってはいけないこと

- Ready の PBI を自分で実装する（開発者の仕事）
- 開発者の worktree に入る・触る
- レビュー無しでマージする（データの経路・セキュリティ・マージ道具に触る PR は特に）
  **2026-09-23〜24 に、この行が在るのに 33 本がレビュー無しでマージされた**
  （実測: **PO 31 本 / bot 2 本**）**。**
  **手順に書くだけでは止まらなかったので、`scripts/po/merge-when-green.sh` に検査を入れた**（#1006）:
  **PR のコメントに「レビュー」の語と結論の語**（`マージしてよい` / `直してから` / `反対`）
  **が同じ 1 件の中に無ければマージしない。**
  **`reviewed` ラベルのような自己申告にしていない**のは、33 本のときの PO が
  「自分で検算したから十分だ」と判断していたからである——**同じ判断でラベルは付けられる。**
  **PO 自身の検算はレビューではない。**
  飛ばすには `--no-review <理由>` が要り、**理由は省略できず**（空白を除いて 7 文字以上）**、ログに残る。**
  **この検査には既知の穴がある**（実測。詳細と直す方向は `docs/ops/board.md`）:
  **担当者が「レビューありがとうございます、直しました」と返答し、その中で採決データの
  「賛成／反対」に触れると、レビュアーが走っていなくても通る**
  （全履歴で通る 9 件のうち **3 件が誤検出**: #224 / #457 / #566）。
  **つまりこの検査は「レビューを必ず走らせる」ことを保証しない。**
- 「テストが緑」を根拠にする
