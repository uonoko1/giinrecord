# 初回訪問のフォント転送量（自サイト配信の unicode-range スライス）

Issue #449 の調査の記録。**この issue では直していない。**
**次に測る人が同じ測り方の間違いを繰り返さないために残している。**

結論を先に書く:

- **減らせる余地はある。しかも #449 が見積もったより大きい。**
  ただし **「スライスが細かすぎる」からではない。** 原因は
  **同じ文字を「家族 × ウェイト」の数だけ重複して読んでいる**こと。
- **`/members` の実測は 1,950 KB。** #449 が書いた 512 KB は**低すぎる**（後述の測り方の落とし穴）。
  **`/rollcalls` の 1,190 KB / 82件 は正しい**（3回とも同じ値）。
- **`font-display: swap` は効いている。** 614 face すべてに `swap` があり、
  **描画を止めている woff2 は 0 件**。FCP はどのページでも最初のフォント到着**より前**に出ている。
- **`/members` の「さらに表示」を1回押すと +1,067 KB**（21件）。**押した瞬間に転送量が 1.5 倍になる。**
- **直すなら「ウェイトを減らす」が一番効く。** スライスの粒度は触らなくてよい。
  提案は **#449 では実施せず、別 issue に切り出す**（末尾に案）。

## 1. 測り方

本番（`https://gikailog.jp`、`https://giinrecord.jp` に 301）を Playwright の Chromium で、
**390px 幅**・**ページごとに新しいコンテキスト**（＝キャッシュ無し＝初回訪問）で開き、
`document.fonts.ready` のあと **2.0〜2.5 秒**待ってから `response` イベントを集計した。
サイズは **`response.body().length`**（本文の実バイト数）。

計測日: 2026-09-04。使ったスクリプトは一時ファイルで、この PR には入れていない。
下の 4 つの値さえ取れば同じ判断ができる。

1. `.woff2` のレスポンス件数と本文バイト数（家族・ウェイト別）
2. `public/fonts/fonts.css` の `unicode-range` と、ページ上で
   **その (family, weight) が実際に描いている文字**の突き合わせ
3. `PerformanceResourceTiming.renderBlockingStatus` と `first-contentful-paint`
4. `CSSFontFaceRule.style.font-display`（CSSOM から。CSS の文字列ではなく**効いている値**）

### 測り方の落とし穴（実際に踏んだ）

- **`response.allHeaders()["content-length"]` を当てにしない。**
  最初のスクリプトはこれを優先して読み、取れなければ body に落とす、という順にしていた。
  この順だと `/members` が **41〜67件 / 512〜1,028 KB** と、**回ごとに違う低い値**になる。
  **`body().length` だけを見ると 3 回とも 118件 / 1,950 KB で一致する。**
  **#449 の 512 KB / 35件 と 118件 は、同じページの同じ状態を測った 2 つの数字である。**
  片方（512 KB）が低すぎるだけで、**118件のほうが正しい。**
- **`document.fonts.ready` + 2秒でも足りないことがある。**
  3回測って 1回だけ `/members` が 92件 1,355 KB になった（Shippori Mincho 700 が 62→36件）。
  **`networkidle` まで待ったうえでの 2秒**でこれなので、**1回の計測を根拠にしない。**
  この文書の数字は**すべて 3回で一致した値**か、一致しなかった場合はそう書いている。
- `vite preview` は使えない（`docs/research/target-size-inline.md` と同じ理由）。
  この調査は**本番を直接測った**ので、その問題は踏んでいない。
- `CSS.getPlatformFontsForNode`（CDP）で**実際に描画に使われた face** を確認した。
  全ページで `isCustomFont: true` の `Shippori Mincho` / `BIZ UDPGothic` が返る。
  **フォールバックで描かれていた、ということはない**（これを確認しないと数字が本番の値にならない。
  `target-size-inline.md` の「27px」がその失敗例）。

## 3. `font-display: swap` は効いている（描画は止まっていない）

| ページ | FCP | 最初の woff2 到着 | 最後の woff2 | `blocking` な woff2 | FCP 前に届いた woff2 |
|---|---:|---:|---:|---:|---:|
| `/` | 352 ms | 349 ms | 566 ms | **0 件** | 4 / 65 |
| `/rollcalls` | 420 ms | 421 ms | 805 ms | **0 件** | **0 / 82** |
| `/members` | 476 ms | 495 ms | 935 ms | **0 件** | **0 / 118** |

- CSSOM から読んだ `font-display` の値は**614 face すべて `swap` の 1 種類だけ**。
- `renderBlockingStatus` が `blocking` の woff2 は **どのページでも 0 件**。
- `/rollcalls` と `/members` は **FCP の時点でフォントが 1 つも届いていない**。
  つまり**最初の描画は全部フォールバック**で出ており、フォントは後から差し替わっている。
  **これは `swap` の設計どおり**で、転送量は体感の初回描画を遅らせていない。

**ただし `fonts.css` 自体は `renderBlockingStatus: "blocking"` である。**
サイズは **520,684 B → gzip 43,843 B**、応答は 50〜56 ms で終わっている。
（**この 614 face / 43,843 B は #452 より前の値。** 500 を外した後は
**492 face / 416,567 B → gzip 42,068 B**。§5-5 を見ること。）
**614 face の CSS は gzip で 43 KB なので、ここは問題ではない**
（`renderFontsCss` が同じ `unicode-range` を持つ 5 face を隣に並べているのが効いている）。

**結論: 受け入れ条件の「`font-display: swap` が効いているか」は「効いている」。ここは直す必要が無い。**

## 4. なぜ重いのか（本当の原因）

### 4-1. 読んだスライスは、ほとんど「数文字のため」に読まれている

読まれた各スライスについて「そのスライスの `unicode-range` に入る文字を、
そのページで実際に何字描いたか」を数えた。

| ページ | 1字だけ | 2〜5字 | 6〜20字 | 21字以上 |
|---|---:|---:|---:|---:|
| `/rollcalls` | 23件 363 KB (31%) | 20件 265 KB (22%) | 23件 323 KB (27%) | 16件 238 KB (20%) |
| `/members` | **33件 772 KB (40%)** | 38件 542 KB (28%) | 42件 526 KB (27%) | 5件 110 KB (6%) |
| `/` | 25件 327 KB (35%) | 24件 306 KB (33%) | 14件 248 KB (27%) | 2件 50 KB (5%) |

**1文字を描くためだけに読まれているスライスが、`/members` では 772 KB（全体の 40%）ある。**
極端な例（すべて実測）:

```
/members  shippori-mincho-700.23.woff2   66 KB  使用 1 字 / 収録 223 字
/members  shippori-mincho-700.41.woff2   57 KB  使用 1 字 / 収録 223 字
/rollcalls biz-udpgothic-700.22.woff2    36 KB  使用 1 字 / 収録 223 字
```

**1文字も描いていないスライスは、どのページでも 0 件だった。**
つまり**「要らないものを読んでいる」のではなく、「1字のために 66 KB 読まされる」**のが実態である。
これは **unicode-range スライスという方式そのものの性質**で、
**スライスを細かくしても粗くしても、この構造は変わらない**（§5-1）。

### 4-2. 同じ文字を、家族 × ウェイトの数だけ重複して読んでいる

**これが本当の原因である。**

同じ slice index（＝同じ `unicode-range`）を、**2つ以上の face が別々に**読んでいる:

| ページ | 重複している index | その重複ぶん（各 index で一番大きい 1 つだけ残した場合との差） |
|---|---:|---:|
| `/members` | **44 index** | **715 KB** |
| `/` | 22 index | 526 KB |
| `/rollcalls` | 23 index | 366 KB |

例（`/members`）: slice `20` `63` `74` `75` `76` `78` … を
**`BIZ UDPGothic 400` と `Shippori Mincho 700` の両方が読んでいる。**
`/` では slice `102` を **3 つの face**（BIZ400・Shippori700・BIZ700）が読んでいる。

**ページに出る文字の集合は 1 つ**なのに、
**その文字が本文（ゴシック）にも見出し（明朝）にも出るので、両方のスライスを読む**。

同じ全文字を **1 家族 1 ウェイトだけ**で賄うとしたら（実在のスライスの大きさから計算）:

| ページ | 現状 | BIZ UDPGothic 400 だけ | Shippori Mincho 700 だけ |
|---|---:|---:|---:|
| `/members` | 1,950 KB / 118件 | **1,122 KB / 66件** | 1,266 KB / 66件 |
| `/rollcalls` | 1,190 KB / 82件 | **814 KB / 55件** | 837 KB / 55件 |
| `/` | 969 KB / 67件 | **429 KB / 31件** | 426 KB / 31件 |

（`/` の現状 969 KB は「fonts.css から計算した値」で、実測 931 KB とは 38 KB ずれる。
ページ内に出る文字から逆算しているので、`::before` などの疑似要素の文字を拾えていないぶん
実測より多くなる。**傾向を見るための数字で、実測の置き換えではない。**）

### 4-3. どの CSS がそれを起こしているか

```
apps/web/app/routes/rollcall.css:33
  .rollcalls-item a { … font-weight: 700; }        ← 議案名 722 字を BIZ UDPGothic 700 で描く

apps/web/app/routes/members.css:29
  .members-item__name { font-family: var(--font-head); font-weight: 700; }
                                                    ← 議員名 339 字を Shippori Mincho 700 で描く
```

- `/rollcalls` の **822 KB（69%）は `.rollcalls-item a` の太字**である。
  一覧の議案名は**このページで一番字種が多く（722 字）、かつ太字**なので、
  **本文用の 400 とはまったく別に 55 スライス読む。**
- `/members` の **1,090 KB（56%）は `.members-item__name` の明朝太字**である。
  議員名は**漢字の字種がもっとも多い**（人名漢字は使用頻度が低く、
  Google のスライスは頻度順なので**後ろの重いスライスに散る**）。

## 5. 減らせる余地があるか（受け入れ条件の判断）

### **ある。ただし「スライスの粒度」ではない。**

### 5-1. スライスの粒度を変えても減らない（**やらないこと**）

#449 の候補「614 スライスは細かすぎるかもしれない」は**この方向では効かない**。
`shippori-mincho-500` の実測（全 122 スライス、3.58 MB）:

| slice index | 件数 | 合計 | 平均/スライス | 1字あたり |
|---|---:|---:|---:|---:|
| 0–9 | 10件 | 531 KB | 53.1 KB | 244 B |
| 10–49 | 40件 | 2,212 KB | 55.3 KB | 254 B |
| 50–89 | 40件 | 502 KB | 12.6 KB | 138 B |
| 90–121 | 30件 | 391 KB | 13.0 KB | 234 B |

**1字あたりのバイト数は 138〜254 B でほぼ一定である。**
つまり Google のスライスは**すでに詰まっている**。

- **粗くする**（1スライスの収録字数を増やす）と、
  1字のために読むバイト数が**増える**。§4-1 が悪化する。
- **細かくする**と、`/members` の 118 リクエストが**さらに増える**。

**どちらに動かしても総量は減らない。粒度は触らない。**

### 5-2. 効くのは「ウェイトを減らす」（実在のスライスから計算した上限）

デザインを変えないと実行できないので**この issue では実施しない**が、
**どれだけ効くかは測れる**ので数字だけ出しておく。

| 試算 | `/rollcalls` | `/members` | `/` |
|---|---:|---:|---:|
| 現状 | 1,190 KB | 1,950 KB | 969 KB |
| **A: BIZ UDPGothic 700 を 400 に統合** | 861 KB（**−330**） | 1,950 KB（±0） | 655 KB（**−313**） |
| **B: Shippori Mincho を 1 ウェイトに統合** | 1,190 KB（±0） | 1,839 KB（−111） | 915 KB（−54） |
| C: 両方 | 861 KB（−330） | 1,839 KB（−111） | 601 KB（−367） |

**A が `/rollcalls` と `/` に効き、`/members` にはまったく効かない。**
`/members` の 1,090 KB は `Shippori Mincho 700`（見出し家族）で、
そこを削るには **B ではなく「議員名を見出し家族で描くのをやめる」しかない**
（`.members-item__name` の `font-family: var(--font-head)` を外すと 1,090 KB のうち
BIZ UDPGothic 400 と重複する 715 KB ぶんが消える）。**これはデザインの変更である。**

### 5-3. 転送量を減らさずに効く手（デザインを変えない）

- **`Shippori Mincho 500` は 3 ページのどこにも出てこなかった。**
  読まれた face は 500 / 700 / 800 のうち **700 と 800 だけ**。
  `FONT_FAMILIES` は 500 を宣言している（`apps/web/app/lib/self-hosted-fonts.ts:18`）が、
  `apps/web/app/styles/` に `font-weight: 500` の指定は 1 件も無い（grep で確認）。
  ※ **調査の範囲外なので確認しきれていない**: `font-weight: 500` を CSS で指定していなくても、
  ブラウザが 400 の要求に対して 500 を選ぶことはある。今回 3 ページで読まれなかったのは
  事実だが、**全ページを測ってはいない。**
  → **この但し書きは当たった。** #452 の1回目は `/members/{id}`（国会議員）で
  **500 が 2件 38 KB 読まれている**のを実測して中止になった。原因は
  `.member-session-count` が `--font-head` を継承したまま `font-weight: 400` を書いていたこと。
  **#454 でそれを直したうえで #452 として 500 を外した**（§5-5）。
  なお **「転送量は 1 バイトも減らない」と書いていたのは誤り。** woff2 は変わらないが、
  **`fonts.css` 自体が小さくなる**（§5-5 に実測値）。
- **`Cache-Control` を伸ばす。** 現状 `public, max-age=604800`（7日、`immutable` 無し。
  `deploy/nginx/site.conf:81-82`）。**ファイル名にハッシュが無いのが理由**とコメントにある。
  ただし**スライスの中身は Google のフォントの版が変わらない限り変わらない**ので、
  ファイル名にハッシュを付ければ `immutable` + 1年にできる。**初回訪問には効かない。**
- **`preload`。** #449 の候補どおり総量は減らない。
  §3 のとおり **`swap` で描画は止まっていない**ので、**効果は「差し替えが早くなる」だけ**。
  `/members` は 118 件のうち何を preload するかを決められない（どの字が出るかはデータ次第）。
  **`/members` には使えない。**

### 5-5. `Shippori Mincho 500` を外した結果（#452 の実測）

**やった。** `FONT_FAMILIES` から 500 を外し、**614 face → 492 face**（`.woff2` は 122 ファイル削除）。

測り方は §1 と同じだが、**本番ではなくローカルの `build/client` を配信して測った**
（#454 の修正が本番に出る前だったため）。配信は `deploy/nginx/site.conf` と同じ
`gzip on` / 既定の `gzip_comp_level 1` を再現している。
**現状の `fonts.css` が本番実測と同じ 43,843 B になったので、再現できていると判断した。**

**転送量（`PerformanceResourceTiming` の値。`body().length` ではない）**

| `fonts.css` | 前 | 後 | 差 |
|---|---:|---:|---:|
| `decodedBodySize`（raw） | 520,684 B | 416,567 B | **−104,117 B（−20.0%）** |
| **`encodedBodySize`（gzip lv1 = 本番と同じ）** | **43,843 B** | **42,068 B** | **−1,775 B（−4.0%）** |
| `transferSize` | 44,143 B | 42,368 B | −1,775 B |

参考（本番は lv1 なので下は使われない）: lv6 で −1,321 B、lv9 で −1,296 B。

**「gzip で 8 KB 減る」という見積もりは誤りだった。実際は 1.8 KB。**
理由は予想どおりで、**削った 122 face は隣の face と `unicode-range` が完全に同じ**＝
gzip が最も効いていた部分だから。**raw が 20% 減っても gzip 後は 4% しか減らない。**
`renderFontsCss` が同じ slice を隣接させている設計の裏返しである。

**woff2 の転送量は全ページで 1 バイトも変わらない**（15 ページすべてで件数・バイト数が完全一致）。
`unicode-range` に当たらない face は元から読まれていないので、これは想定どおり。

**リポジトリからは 3.58 MB 減る**（19 MB → 15 MB）。

#### 外す前に確認したこと（次に同じことをする人へ）

**「CSS に書いていない」は根拠にならない。** #452 の1回目がそれで中止になった。
**必ずブラウザで測る**こと。今回やったのは:

1. **全 15 ページ**（`/` `/members` `/rollcalls` `/coverage` `/assemblies` `/assemblies/{id}`×2
   `/about` `/compare` `/terms` `/privacy` **国会議員 3 人**・**地方議員 1 人**）を
   **3回ずつ**測って `shippori-mincho-500` が **0 件**（3回とも一致）
2. **`CSS.getPlatformFontsForNode` に `Shippori Mincho Medium` が出ない**こと
   （**ダウンロードの有無だけでは足りない**。#452 の1回目はここで「実際に描いている」ことまで確認した）
3. **タブ切替・`<details>` 展開・「さらに表示」を押した後**でも 0 件
   （初期描画に出ない DOM を拾うため。`/members` は展開すると 118 → 139 件になる）

外した後も同じ 15 ページを 3 回測り、**woff2 の件数・バイト数が前と完全一致**、
**スクリーンショット 10 枚が前後でバイト単位まで同一**であることを確認している。

### 5-4. 「何もしない」は成り立つか

**成り立たない、と判断する。**

`fonts.css` の `Cache-Control` は 7 日なので**2回目以降は効く**が、
**初回で 1〜2 MB**は、`/members` の「さらに表示」を押すと **3,017 KB** になる（§6）。
JS を 70 KB 削った #411 に対して**桁が 2 つ違う**。
一方で **§5-2 の A は `/rollcalls` を 28% 減らせる**ことが実在のスライスから計算できている。
**「余地が無い」とは書けない。**

| `/members` | 「さらに表示（残り768名）」 | 1,950 KB / 118件 | **3,017 KB / 139件** | **+1,067 KB / +21件** |

追加で読まれた face:

- `/rollcalls`: **11件中 10件が `biz-udpgothic-700`**（議案名の太字。§4-3 のとおり）。
  残り 1 件が `biz-udpgothic-400`。
- `/members`: **21件すべてが `shippori-mincho-700`**（議員名。`.44` `.40` `.39` `.19` `.48` …）。
  **1件も 400 が増えていない** = 追加の 768 名の名前に出る漢字は
  **本文用フォントではすでに読み終えていて、見出し用フォントだけが足りない**。
  §4-2 の重複が、押した瞬間にもう一度起きている。

**#449 の「押すと追加のスライスが読まれるはず」は当たっている。**
`/members` は **1 回押すだけで 1 MB 増える**ので、**折りたたみは効いている**
（200件で切らなければ初回から 3 MB 読む）。**折りたたみ自体は残すべき。**

## 7. やらないと決めたこと

- **フォントを変える／減らす** — デザインが変わる。`docs/` の設計方針の範囲。
  §5-2 は**数字を出しただけで、実施していない。**
- **外部 CDN に戻す** — #168 でプライバシー方針として自サイト配信にしたもの。**選択肢に入れない。**
- **スライスの粒度を変える** — §5-1 のとおり**どちらに動かしても減らない。**
- **この issue で直すこと** — #449 は調査。提案は §8。

## 8. 別 issue に切り出す候補（この issue では作らない）

## 9. この判断が変わる条件

- **`FONT_FAMILIES` のウェイトを増やした**とき。§4-2 の重複が face の数だけ増える。
- **`FONT_FAMILIES` のウェイトを減らした**とき。**要求されたウェイトが無いと、ブラウザは
  一番近い別のウェイトで描く**（CSS Fonts 4 §5.2）。#452 で 500 を外したので、
  `--font-head` に 400 を書いたときの落ち先は **500 ではなく 700**（＝字が太くなる）になった。
  `apps/web/app/styles/font-weight-match.test.ts` がこれを止めている。
- **見出し家族（Shippori Mincho）を本文の長い一覧に使い始めた**とき。
  `/members` がまさにそれで、**1 ページで一番重い原因**になっている。
- **折りたたみの件数（200）を増やした**とき。§6 のとおり `/members` は
  **1 回の展開で +1,067 KB** なので、初回に描く件数がそのまま転送量になる。
- **Google がスライスの切り方を変えた**とき。§5-1 の「1字あたり 138〜254 B」を測り直すこと。
