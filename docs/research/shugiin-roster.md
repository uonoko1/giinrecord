# 回次ごとの衆院議員名簿の一次資料の調査（Issue #245）

調査日: 2026-08-24。取得は `curl -A "gikailog-etl/0.1 (+https://github.com/uonoko1/gikailog)"`（`packages/etl/src/fetch.ts` の UA）、間隔 ≥ 1.3 秒、計 21 リクエスト。

robots.txt の確認結果（**この調査の結論を左右したので先に書く**）:

| ホスト | robots.txt | 内容 |
|---|---|---|
| `www.shugiin.go.jp` | **404**（159 bytes） | 制限の記述自体が無い |
| `www.sangiin.go.jp` | 404（#237・#217 で確認済み） | 同上 |
| `kokkai.ndl.go.jp` | 302（実体なし） | API は公開仕様どおり利用 |
| **`warp.ndl.go.jp`** | **200**（159 bytes、`Last-Modified: Thu, 23 Jul 2026`） | **`Disallow: /web/`, `Disallow: /20`, `Disallow: /search`, `Disallow: /collections/`** |

## 結論（先に）

**回次ごとの衆院議員名簿は、機械的に取得してよい一次資料としては存在しない。**

内訳は 3 つに分かれ、**「無い」と「有るが取ってはいけない」が混在している**のがこの調査の要点:

1. **衆議院サイトには過去名簿が無い**（`1giin.htm` の「現在」1 枚だけ。会派別・委員名簿も同じ「現在」1 枚）。これは #237 の追認。
2. **WARP には 2014〜2026 年の月次スナップショットが 148 点ある**。カバー範囲は申し分ない。**しかし WARP の robots.txt が、アーカイブ本文の置き場である `/web/` と `/20…` を `User-agent: *` に対して明示的に Disallow している。** つまり**資料は在るが、ETL が自動で取ることは許されていない**。
3. **会議録 API・議案ページから在籍者名簿を再構成することはできない**（発言者・提出者は在籍者の一部でしかない）。実測で裏づけた（下記 4 節）。

補強する実測値をひとつ。**第217回の議案に載る提出者・賛成者の氏名 334 人のうち、現在の名簿に居るのは 165 人（49%）しかない。** 残り 169 人は 2024 年総選挙で入れ替わった当時の議員で、現在の名簿には存在しない。**「氏名が一致しないだけ」ではなく「本当に半分は別人の集合」**であり、現行実装が氏名一致による推定を拒んでいるのは正しい。名簿を用意せずに紐づけを増やす道は無い。

**したがって #245 は「一次資料が見つかった／見つからない」の二択では答えられない。答えは「WARP に在るが、robots.txt により自動取得は不可。使うなら NDL への利用連絡という人間の手続きが要る」。** 実装 PBI を今すぐ起こせる状態ではない（提案は 7 節）。

## 2. WARP（国立国会図書館 インターネット資料収集保存事業）

**カバー範囲の点では、これが唯一の当たり**。そして**取得の可否で落ちる**。

### 2-1. 保存されているか → されている（148 スナップショット）

WARP は RFC 7089（Memento）の TimeMap を公開している（`https://warp.ndl.go.jp/info/help` の 7 節）。エントリポイント:

```
TimeMap  https://warp.ndl.go.jp/collections/timemap/{元URL}
TimeGate https://warp.ndl.go.jp/collections/{元URL}
```

`1giin.htm` の TimeMap を実際に引いた（200 / 27,153 bytes / `application/link-format`）:

```
https://warp.ndl.go.jp/collections/timemap/https://www.shugiin.go.jp/internet/itdb_annai.nsf/html/statics/syu/1giin.htm
```

結果:

| 項目 | 値 |
|---|---|
| memento 数 | **148** |
| 最古 | **2014-04-25**（`20140425002716`） |
| 最新 | 2026-07-01（`20260701001247`） |
| 頻度 | **ほぼ毎月 1 回**（2015〜2025 年は各年 12 点、2014 年 9 点、2026 年 7 点） |

**2014 年 4 月以降、月次で切れ目なく在る。** 第186回国会（2014 年）以降の任意の時点の衆院名簿が、原理的には復元できる。`data/bills/` の `submitterNames` が分布する第195〜221回（2017 年〜）は**完全にこの範囲に収まる**。

### 2-2. 取得してよいか → **robots.txt が明確に禁じている**

`https://warp.ndl.go.jp/robots.txt`（200、`Last-Modified: 2026-07-23`。**先月更新されており、現行かつ意図的**）:

```
User-agent: JAEA-FNAA
Disallow:

User-agent: *
Disallow: /search
Disallow: /en/search
Disallow: /web/
Disallow: /en/web/
Disallow: /20
Disallow: /collections/
```

TimeMap が返す memento の URL は**すべて `/web/` 配下**:

```
https://warp.ndl.go.jp/web/20211201001007/https://www.shugiin.go.jp/…/1giin.htm
```

さらに `/web/…` を引くと（200 / 36,356 bytes）中身は**アーカイブ本文ではなく JS の外枠**で、実体は別パスに埋まっている:

```html
src="/20211205/20211201001007/https://www.shugiin.go.jp/…/1giin.htm"
```

この実体パス `/20211205/…` も **`Disallow: /20` に一致する**。実際、外枠だけを見ても名簿は取れない（`令和…現在` の一致 0 件、プロフィールリンク 0 件、`profile/` の氏名 0 件）ことを実測で確認した。

**つまり本文に到達する経路（`/web/` と `/20…`）が両方とも Disallow。TimeMap 自体の `/collections/` も Disallow。** 例外的に許可されているのは `JAEA-FNAA` という特定のクローラ 1 つだけで、汎用の UA には開かれていない。

**この調査ではこれ以上 WARP の本文を取得しなかった**（外枠 2 点で構造を確認した時点で、robots に反する取得だと判明したため。#245 の「WARP は保存サイトなので取得の礼儀に特に注意」に従った）。

### 2-3. 評価

| 観点 | 評価 |
|---|---|
| 一次資料の所在 | `https://warp.ndl.go.jp/collections/timemap/https://www.shugiin.go.jp/internet/itdb_annai.nsf/html/statics/syu/{1..10}giin.htm` |
| **カバー範囲** | **2014-04 〜 2026-07、月次 148 点。第186回以降の全期間を覆う（`submitterNames` のある第195〜221回を完全に含む）** |
| 形式 | 元ページそのまま（Shift_JIS の HTML）。**`parseShugiinMemberList` がそのまま使える**はず（ページ上部の `令和N年M月D日現在` も含めて元のまま保存されている想定。ただし**本文を取得していないので未検証**） |
| 取得可否 | **不可（robots.txt により禁止）** |
| 実装難度 | 技術的には**低い**（TimeMap を引く → 各 memento を `decodeRosterPage` → 既存パーサ）。**障害は技術ではなく許諾** |
| リスク | **robots 違反。加えて WARP のヘルプ 7-3(2) は「特定 IP からの大量リクエストはアクセス遮断しうる」と明記。10 ページ × 148 点 = 1,480 リクエストは「大量」に当たる可能性が高い** |

**取れるものが在るのに取らない、という判断をここで明示しておく。** リポジトリの原則（推定で紐づけない）とは別種の、**相手サイトの意思表示を尊重するという原則**の話。

### 2-4. ただし道が閉じたわけではない

WARP のヘルプ 7-2 / 7-3 は API について次のように書いている:

> 利用に必要な手続きはありません。
> 継続的に API を利用する場合は、利用状況と連絡先を「お問い合わせ」からお知らせください。

**robots.txt は自動クローラ向けの一般的な意思表示で、API には「継続利用なら連絡してほしい」という別の窓口が用意されている。** この 2 つは矛盾しているように見えるが、実務的には「無断の全面クロールは断る／用途を伝えれば相談に応じる」と読むのが自然。

**したがって次の一手は実装ではなく問い合わせ**（7 節）。これは ETL が自動で決められることではないので、**リポジトリの運用者（人間）が判断すべき事項**としてこの文書に残す。

## 3. 議案の提出者・賛成者ページから在籍を再構成できるか

**できない。原理的に。**

議案の経過ページに載るのは**その議案の提出者と賛成者だけ**で、在籍者の集合ではない。実測（`data/bills/217/`）:

| 項目 | 値 |
|---|---|
| 第217回の議案に現れる提出者・賛成者の**異なり氏名** | **334** |
| 当時の衆院議員の定数 | 465 |
| 捕捉率 | **72%**（残り 131 人は、その回次に 1 件も議員立法に関与していない） |

しかも**この 334 は「名簿」ではない**:

- 会派が書かれていない（`match-shugiin-bills.ts` が `resolveMember(index, nameText, undefined)` と会派なしで呼んでいるとおり）。**同姓同名を絞る手段が無い**
- ふりがなが無い。`memberIdFromName(name, kana)` の kana を作れないので、**そもそも既存の ID 体系に載らない**
- 「賛成者として名前が載った」ことは在籍の証拠になるが、**載らなかった人が非在籍とは言えない**ので、集合として閉じない

**自己言及になっている点が決定的**: 紐づけたいデータ（議案の氏名）から名簿を作って、その名簿で同じデータを紐づけても、**新しい事実は 1 件も増えない**（334 人が 334 人の氏名に当たるだけ）。質問主意書・発言の紐づけには一部効くが、その 3 者の氏名の和集合を「在籍者名簿」と呼ぶのは**定義のすり替え**であって一次資料ではない。

**結論: 名簿の代わりにはならない。**

## 4. 会議録 API の発言者情報から在籍を再構成できるか

**できない。推定にならない範囲では、名簿として使える集合にならない。**

### 取れる情報（実測）

`https://kokkai.ndl.go.jp/api/speech?nameOfHouse=衆議院&sessionFrom=217&sessionTo=217&…` は 200 で返り、**過去回次でも問題なく引ける**（第217回の衆院レコード数 **55,126**）。1 レコードの発言者情報:

```
speaker: 堀内詔子   speakerYomi: ほりうちのりこ   speakerGroup: 自由民主党・無所属の会
```

**氏名・ふりがな・会派が揃う**（`memberIdFromName` に必要な 2 つと、同姓同名を絞る会派）。この点だけ見れば議案ページ（3 節）より質が高い。

### なぜ名簿にならないか（実測）

300 レコード（第217回、`startRecord` 1・5,000・20,000 の 3 か所）を取って数えた:

| 項目 | 値 |
|---|---|
| サンプルした発言レコード | 300 |
| `speakerGroup` あり（＝議員） | 217（72%） |
| **異なり発言者** | **33 人** |
| うち第217回の議案氏名 334 人を覆う数 | **24 人（7%）** |

**300 レコード引いて 33 人。** 発言は少数の議員に極端に集中する（委員長・大臣・質疑者が繰り返し登場する）ので、**レコード数を増やしても異なり人数は急速に頭打ちになる**。55,126 レコード全部を引いても 465 人に届く保証はどこにもなく、**届いたかどうかを確かめる術も無い**（正解の名簿が無いから確かめられない、というのがそもそもの問題）。

### 「発言した＝在籍」は事実だが、名簿ではない

#245 が注意しているとおり、**「発言した」は在籍の十分条件**であって必要条件ではない。この非対称性が効く:

- **在籍者を漏れなく列挙できない**（発言しない議員が捕捉されない）。名簿は「その回次に誰が居たか」の**閉じた集合**である必要があり、開いた集合では `rosterCoveredSessions()` の意味が変わってしまう
- 仮に発言者だけで `Member` を作ると、**「発言しなかった議員は存在しないことになる」**。賛同法案 420 件のうち、発言していない議員の分は**依然として紐づかないまま**、しかも「名簿はあるのに紐づかない」という**より紛らわしい状態**になる

`docs/research/backfill-142-199.md` が参院で同じ結論を出している（「その日に発言した人の情報で、在籍者名簿ではない。採決に参加した 215 人のうち発言するのは数人」）。**衆院でも同じ。**

### 「こういう条件なら事実として扱える」論点（#245 が許した範囲）

推定を避けたまま使える形が 1 つだけある。**名簿としてではなく、突合の補助として使う**:

> 発言レコードの `speaker` + `speakerYomi` + `speakerGroup` は、**その回次のその日にその会派の議員としてその氏名が記録された**という事実。
> **同姓同名の曖昧性を解消する材料**としてなら、推定を増やさずに使える。

ただし現状これは**効かない**。同姓同名で困っているのではなく、**候補が 0 人**（名簿そのものが無い）だから紐づかない。**曖昧性解消の道具は、候補集合が在って初めて意味を持つ。** よって**この経路は今回の制約を解かない**。名簿が手に入った後に、同姓同名が実際に問題になったら再検討する材料として書き留めるにとどめる。

## 5. 選挙結果（総務省）から当選者名簿を作れるか

**この調査では確認できていない（未取得）。** リクエスト予算を WARP と会議録の実測に充てたため。以下は**見た範囲での評価**であり、実物に当たっていないことを明記する。

衆議院サイト側の `衆議院議員総選挙一覧`（`…/shiryo/senkyolist.htm`、200 / 14,882 bytes）は実際に取ったが、**掲載されているのは各総選挙の期日と回次だけで、当選者の氏名は 1 件も無い**（`任期満了の場合` / `解散の場合` のアンカーがあるだけ）。**衆議院サイト経由で選挙結果から名簿を作る道は無い。**

総務省側（未取得）について、原理的な問題を 2 つ挙げておく。**仮に取れても、そのままでは名簿にならない**:

1. **ふりがなの有無**。`memberIdFromName(name, kana)` は氏名とふりがなのハッシュ。選挙結果に kana が無ければ**既存の ID 体系に載らない**（別の ID 空間を作ることになり、名簿と選挙結果で同一人物が別 ID になる）
2. **総選挙の時点と回次のズレ**。選挙結果は「当選した 465 人」であって「第N回国会の在籍者」ではない。**任期中の辞職・死亡・繰上補充・補欠選挙・会派移動が反映されない**。会派は名簿の重要な列（`MemberTerm.group`）で、選挙時の所属政党とは別物（`自由民主党・無所属の会` のような会派名は選挙結果には出ない）

つまり選挙結果は「総選挙の当選者」という別の事実であって、**回次ごとの在籍者名簿の代用にするには補正が要り、その補正が推定になる**。3 節・4 節と同じ構造の問題。

**未確認事項として 8 節に残す。** 潰すなら総務省の実物（`https://www.soumu.go.jp/senkyo/senkyo_s/data/` 配下）に当たる小さな spike を別途立てるのが筋。

## 6. 参院に回次別名簿があって衆院に無い理由

**公式の説明は見つけていない**（両院ともその旨を書いたページは無い）。以下は**実物の構造から読み取れること**であり、推測を含む部分はそう書く。

### 実物の対照

参院の回次別名簿（実測 200 / 67,520 bytes）:

```
https://www.sangiin.go.jp/japanese/joho1/kousei/giin/217/giin.htm
             ↑ 回次が URL のパスに入っている
```

ページ内の記述:

```
第217回国会（常会）（令和7年1月24日～令和7年6月2…）
令和7年7月31日現在
```

**「第217回国会」という会期と、その時点の日付の両方が書かれている。** URL の `217` が示すとおり、**回次ごとに 1 枚作って残す設計**になっている。

衆院（実測 200 / 52,186 bytes）:

```
https://www.shugiin.go.jp/internet/itdb_annai.nsf/html/statics/syu/1giin.htm
             ↑ 回次がどこにも無い。固定の1枚を上書きしている
```

ページ内は `令和8年2月18日現在` のみで、**回次への言及が無い**。

### 制度的な背景（構造から言えること）

両院の任期の性質の違いが、この設計の差と整合する:

- **参院は 3 年ごとの半数改選で、任期 6 年の議員が常に居る。** 議員の入れ替わりが**会期の区切りと対応づけやすく**、「第N回国会の議員は誰か」が名簿として意味を持つ
- **衆院は解散があり、任期が不定。** 総選挙で 465 人全員が入れ替わる（=`profile/NNN.html` の連番が総選挙ごとに振り直されるのは `shugiin-members.ts` のコメントが記録しているとおり）。会期ではなく**「総選挙から次の総選挙まで」が議員集合の単位**になり、回次で切る動機が弱い

**ここまでは構造の観察。以下は推測**: 衆院は Lotus Domino（`itdb_annai.nsf`）で「現在の議員」を DB から動的に出力する作りに見え（`.nsf` のパス、`profile/NNN.html` の連番が振り直される挙動）、**過去の状態を別 URL で残すのは設計に入っていない**のだろう。参院は回次ごとに静的ページを作る運用。**どちらが正しいという話ではなく、実装方針の差**。

**この差は当分埋まらないと見るべき**で、衆院側が過去名簿を出し始めるのを待つ計画は立てられない。だから 2-4 の WARP への問い合わせが現実的な唯一の道になる。

## 9. 次の一手（提案。実装 PBI ではない）

**この調査の結論は「技術的な障害ではなく許諾の問題」なので、次は実装ではない。**

1. **WARP（NDL）に利用可否を問い合わせる**（人間の作業）。ヘルプ 7-2 が「継続利用は連絡を」と案内している窓口に、次を伝えて可否を尋ねる:
   - 用途（衆院議員の在籍名簿の復元。非営利・公開リポジトリ）
   - 対象 URL（`syu/{1..10}giin.htm` の 10 本）とスナップショット数（各 148 点程度＝**計 1,480 リクエスト、1 回限りのバックフィル**。日次で繰り返すものではない）
   - 間隔（≥ 1 秒）と UA（`gikailog-etl/0.1`）
   - **robots.txt が `/web/` を Disallow していることを承知した上で尋ねている**旨

   **この回答が来るまで WARP からの取得は行わない。**
2. **並行して総務省の選挙結果を 1 spike で潰す**（5 節）。WARP が断られた場合の代替になりうるか、ふりがなの有無だけでも確認する価値がある。**ただし 5 節に書いたとおり、そのままでは名簿にならない**見込み
3. **どちらも駄目なら、この制約は「解けない」として受け入れる**。その場合:
   - `submitterNames` / `supporterNames` は**氏名の事実として残り続ける**（現行どおり。表示側で「氏名は分かっているが議員ページには紐づかない」ことを示す余地はある）
   - **氏名一致による推定には踏み込まない**（`match-shugiin-bills.ts` の現行方針を変えない）
   - 第222回以降は**回次が進むごとに 1 回次ぶんずつ積み上がる**（日次 ETL が現在の名簿を取り続けるので、時間が解決する部分がある）。**過去は埋まらないが、未来は埋まる**

**やらないこと**: 現在の名簿への氏名一致で過去回次を紐づけること。**第217回の 334 人のうち 169 人（51%）は現在の名簿に居ない**（冒頭の実測）ので、氏名一致は「当たらない」だけでなく**同姓同名の別人を 1 人にする危険が現実にある**。`docs/DATA_CONTRACT.md` と #217 の方針どおり、やらない。
