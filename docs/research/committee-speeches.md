# 委員会発言の全量取得によるサイズと形の実測（Issue #263）

調査日: 2026-08-25。第221回国会（特別会）の**衆参両院・全会議**の発言を、国会会議録検索システム 検索用API
`https://kokkai.ndl.go.jp/api/speech` から**実際に全量取得した**（`nameOfMeeting=本会議` を外す）。
取得は UA `gikailog-etl/0.1 (+https://github.com/uonoko1/gikailog)`（`packages/etl/src/fetch.ts` の UA）、
**間隔 1.2 秒・逐次（並列なし）**、計 706 ページ（衆院 334・参院 372）＝約 14 分。
取得結果はスクラッチ領域に置き、`data/` には**一切コミットしていない**。

この調査の目的は #242（委員会の発言を収録）の前提となる数字を、推定から実測に置き換えることである。
`docs/research/individual-records.md` の「見ていないこと」が記録していた 3 つの未測定項目
（全量取得・`speakerGroup` の割合・正規化後の実バイト数）に、この調査で答えを出した。

## 結論（先に3行）

1. **サイズは推定より大きい**。発言1件の正規化後は**実測 768.5 バイト**で、PO の回帰推定 534 バイトの **1.44 倍**。
   22回次に外挿すると議員に紐づく分だけで **約 455 MB**（`data/members/` は現在 90 MB なので**約 6.1 倍**）。
   ただし**衆院側を 22 回次に広げるには #71（回次ごとの衆院名簿）が前提**（DATA_CONTRACT の制限。§5 の注意 2）。
2. **議員に紐づく割合は 84% ではなく 77.87%**（実測 69,872 件中 54,407 件）。研究の 84% は 298 件サンプルの値だった。
3. **形の違うレコードは無い**。分科会・連合審査会・公聴会・審査会・調査会を含め、
   API が返すキー構成は **1 種類だけ**（21 キー固定、欠損は `null` で表現）。
   **パース側**（`parseSpeechPage` / `toSpeech` / `toExcerpt`）は改造なしで通るが、
   **URL 組み立て `speechPageUrl` は `nameOfMeeting=本会議` をハードコードしており、ここは変更が要る**。

## 2. 議員に紐づく割合（実測）

`speakerGroup`（会派）を持つ＝議員である、の代理指標で数えた。

| 院 | 発言 | `speakerGroup` あり | 割合 |
|---|---|---|---|
| 衆議院 | 33,032 | 25,948 | **78.55%** |
| 参議院 | 36,840 | 28,459 | **77.25%** |
| 計 | 69,872 | 54,407 | **77.87%** |

**研究が記録していた 84%（298 件サンプル）は、全量では 77.87% だった**（-6.1 ポイント）。
サンプルは予算委員会（総理入り＝議員の質疑が多い）に寄っていたため高く出ていた。

`speakerPosition`（役職）を持つのは衆院 13,565（41.07%）・参院 15,539（42.18%）。

### レコードの構造的な不変条件（実測）

69,872 件すべてを調べて、次の 2 つが成り立つことを確認した:

- **`speakerGroup` と `speakerPosition` の両方が空のレコードは 0 件**。全員がどちらかを必ず持つ。
- **`speech` 本文は全件が `○` で始まり**、既存の `toExcerpt` の正規表現
  `/^○[^\s　]+[\s　]+/` が**全件で話者表示を除去できた**（除去に失敗した件数 0）。

この 2 つは #242 の実装にとって重要で、**既存の `parseSpeechPage` / `toSpeech` / `toExcerpt` は
1 行も変えずに委員会発言を処理できる**ことを意味する。
ただし**取得 URL を組み立てる `speechPageUrl` は `nameOfMeeting` に `"本会議"` をハードコードしている**ので、
そこは #242 で変更が必要（パースは無改造、取得は要変更）。
（必須項目 `speechID` / `session` / `speaker` /
`nameOfMeeting` / `date` / `speech` / `speechURL` の欠損も 0 件、`session` は全件 int）。

下表は**本番と同じ渡し方**（`cli.ts` L213 / L225 のとおり院ごとの名簿を `matchSpeeches` に渡す）で、
本番の `matchSpeeches` / `resolveMember` を実際に import して数えた値である。

| 院 | 会派つき発言者（実人数） | 名簿に突合できた人数 | **`unmatched.json` に載る発言** |
|---|---|---|---|
| 衆議院 | 414 | 395 | **0 件** |
| 参議院 | 322 | 236 | **246 件** |

（両院を1つのプールにして渡すと **衆院 31 件 / 参院 0 件**と逆転する。同姓同名 7 組の扱いが変わるため。

### `speakerRole` は null だけではなかった

`individual-records.md` は「見た 300 件では全て `null`」と記録していたが、**全量では値が入る**:

| `speakerRole` | 衆議院 | 参議院 |
|---|---|---|
| `null` | 32,034 | 35,041 |
| `参考人` | 918 | 1,679 |
| `公述人` | 80 | 120 |

`参考人` / `公述人` は**全件が `speakerGroup` を持たず、`speakerPosition` に肩書きが入る**。実例（公聴会）:

```
122105262X00120260310_002  予算委員会公聴会
speaker: 堀真奈美  speakerGroup: null
speakerPosition: 東海大学健康学部健康マネジメント学科教授  speakerRole: 公述人
```

`speakerRole` は「議員でない発言者」の明示的な標識として使える（が、政府参考人＝局長・審議官には
付かないので、`speakerGroup` の有無を置き換えるものではない）。

## 3. 正規化後の実バイト数（実測）

`data/` は `stableJson`（`JSON.stringify(value, sortKeys, 1)`＝**キーソート・インデント1**）で書く。
現行の `SpeechEntry`（`kind` / `session` / `date` / `speechId` / `meeting` / `excerpt` / `chars` /
`position?` / `sourceUrl`）に正規化して、この書式でバイト数を数えた。

| 対象 | 件数 | 実バイト数 | **1件あたり** |
|---|---|---|---|
| 第221回 全発言 | 69,872 | 53,696,737 B（53.70 MB） | **768.5 B** |
| うち会派つき（＝`data/` に入る分） | 54,407 | 40,262,807 B（40.26 MB） | **740.0 B** |
| 参考: 現行 `data/` の `speech` 行（本会議のみ） | 7,519 | 4,293,398 B | **571.0 B** |

**PO の回帰推定「発言1件 ≒ 534 B」は、委員会発言では成り立たない**。実測は 768.5 B で **1.44 倍**。
会派つきに絞っても 740.0 B（1.39 倍）。現行の本会議の行（571.0 B）と比べても 1.35 倍大きい。

差が出る理由は 3 つあり、いずれも実測した:

1. **会議名が長い**。`meeting` は平均 30.4 B（本会議は「本会議 第N号」で約 20 B）。
   最長は `地域活性化・こども政策・デジタル社会形成に関する特別委員会 第15号` の **96 B**。
2. **`position` が付く割合が高い**。委員会は 41.07%（衆院）に `speakerPosition` があり、
   付くときの平均は 38.8 B（全体に均すと +15.9 B/件）。
3. **本文が長く、抜粋 200 字が埋まりやすい**。正規化後の本文は平均 441.5 字（衆院）・400.8 字（参院）で、
   **200 字の上限で切られるのは衆院 70.2%・参院 67.4%**。つまり大半の行が `excerpt` を満杯まで使う。

なお **`EXCERPT_CHARS = 200` の上限は既に効いている**: 本文全文なら 43.5 MB のところ、
抜粋は 16.3 MB（**37.4%**）に収まっている（衆院 33,032 件で計測）。

## 4. 形の違うレコードの有無（実測）

**無かった。** 70,544 件すべての JSON キー構成を集計したところ、**キーセットは両院とも 1 種類だけ**である。

```
closing, date, imageKind, issue, issueID, meetingURL, nameOfHouse, nameOfMeeting,
pdfURL, searchObject, session, speaker, speakerGroup, speakerPosition, speakerRole,
speakerYomi, speech, speechID, speechOrder, speechURL, startPage
```

**API はキーを落とさない。値が無いときは `null` を入れる**。したがって「フィールド構成が違う」形の差は生じず、
差は「どのキーが `null` か」だけに現れる。`null`（または空文字）の割合:

| キー | 衆議院 | 参議院 |
|---|---|---|
| `closing` | 33,380（100%） | 37,164（100%） |
| `speakerRole` | 32,382（97.0%） | 35,365（95.2%） |
| `speakerPosition` | 19,815（59.4%） | 21,625（58.2%） |
| `pdfURL` | 11,863（35.5%） | 15,824（42.6%） |
| `speakerGroup` / `speakerYomi` | 7,432（22.3%） | 8,705（23.4%） |

`speakerGroup` と `speakerYomi` が `null` になる件数は**両院とも完全に一致**する（会派を持たない発言者には
読みも付かない）。`closing` は全件 `null` で、この API では使われていない。

特殊な会議体も同じ構造である。実例:

```
連合審査会  122104911X00120260514_001
  nameOfMeeting: 内閣委員会経済産業委員会連合審査会  issue: 第1号
  speaker: 山下貴司  speakerGroup: 自由民主党・無所属の会  speakerPosition: null  speakerRole: null

審査会      122104183X01420260724_001
  nameOfMeeting: 憲法審査会  issue: 第14号
  speaker: 古屋圭司  speakerGroup: 自由民主党・無所属の会  speakerPosition: null  speakerRole: null
```

違いは `nameOfMeeting` の**文字列が長い**ことだけで、フィールドの有無は本会議と変わらない。
`issue` は全件（69,872 件）で空でなく、値は「第N号」の 39 種類。
`speechURL` は全件が `https://kokkai.ndl.go.jp/txt/{issueID}/{speechOrder}` の 1 形式（平均 53.3 B）。

**Sprint 12 の島根（別構造の PDF で落ちた）と同じ失敗は、この API では起きにくい**。
根拠は「1 会期を全量見てキーセットが 1 種類だった」ことであり、**他の回次で同じとは限らない**（下記「見ていないこと」）。

## 5. 22回次（第200〜221回）に外挿したサイズ

発言は既に第200〜221回の**22回次ぶん** `data/` に入っている（`data/members/` の `speech` 行を数えると
第200回 253 件 〜 第221回 1,298 件、計 7,519 件）。委員会発言を入れると同じ範囲に揃うことになる。

**22回次ぶんを ×22 で外挿するのは誤り**なので、**22回次すべての `numberOfRecords` を API から実測した**
（44 リクエスト、間隔 1.3 秒）。回次ごとの開会日数が違うため、量は 2 桁ぶれる:

| 回次 | 衆議院 | 参議院 | 回次 | 衆議院 | 参議院 |
|---|---|---|---|---|---|
| 200 | 16,151 | 13,136 | 211 | 50,176 | 44,642 |
| 201 | 45,135 | 37,742 | 212 | 12,315 | 13,247 |
| 202 | 538 | 488 | 213 | 54,748 | 49,242 |
| 203 | 11,364 | 10,820 | 214 | 317 | 354 |
| 204 | 55,323 | 48,000 | 215 | 427 | 350 |
| 205 | 251 | 329 | 216 | 8,129 | 6,758 |
| 206 | 442 | 329 | 217 | 55,126 | 41,580 |
| 207 | 1,937 | 2,438 | 218 | 586 | 660 |
| 208 | 47,357 | 40,865 | 219 | 11,308 | 9,137 |
| 209 | 739 | 549 | 220 | 16 | 214 |
| 210 | 17,850 | 15,992 | **221** | **33,380** | **37,164** |

**合計 797,651 件**（第221回の 70,544 件はその 8.8%）。通常国会（201・204・208・211・213・217）が
5 万件級、臨時会・特別会は数百〜数万件と幅が大きい。**第221回を 22 倍した 1,551,968 件は実測の約 1.95 倍で、過大**である。

この実測件数に、第221回で測った比率（`speechOrder` 0 が 0.95%、会派つきが 77.87%、
1件あたり 740.0 B）を掛けると:

| 指標 | 実測ベースの値 |
|---|---|
| 22回次の総レコード | **797,651 件**（実測） |
| うち発言（`speechOrder` 0 を除く） | 約 790,053 件 |
| うち会派つき（`data/` に入る分） | **約 615,188 件** |
| **`data/members/` への追加分** | **約 455 MB** |
| 全発言を入れた場合 | 約 607 MB |
| gzip 後（実測比 0.2149） | 約 98 MB |

現在の `data/members/` は **90 MB**（1,057 ファイル）なので、**約 545 MB＝現在の約 6.1 倍**になる。

**注意 1（外挿の仮定）**: これは「第221回で測った 1 件あたりのバイト数と会派つき比率が、他の 21 回次でも同じ」
という仮定を置いた外挿であり、**他の回次では測っていない**（下記「見ていないこと」）。件数だけは全回次で実測した。

**注意 2（衆院側は現状の契約では 22 回次に広げられない）**: 上の 455 MB は**算術としての外挿**であって、
**いまの実装でそのまま取得できるという意味ではない**。`docs/DATA_CONTRACT.md`（`TimelineEntry(speech)` の項）は
衆院の発言を「**名簿が覆う回次（`meta.sessions` の最大）だけ取得・突合し、過去回次の衆院本会議は取得しない**」と
**意図的に制限**している。理由は「名簿に無い旧議員を同名の現職に紐づけない」ため（#71 で回次ごとの名簿が入れば広がる）。
`cli.ts` L205-208 のコメントも同じ制限を明示している。

したがって:

- **参院側**は回次ごとの名簿があるので 22 回次に広げられる。
- **衆院側を 22 回次に広げるには #71（回次ごとの衆院名簿）が前提**になる。#71 が無いまま過去回次を取ると、
  契約が禁じている「旧議員を同名の現職に紐づける」誤りが入る。
- つまり **455 MB は「#71 が入った後の上限」**であり、#71 が無い現状で #242 を入れた場合の増分は
  これより小さい（衆院は 1 回次ぶんだけ）。**その条件での内訳は計算していない**（下記「見ていないこと」）。

### 取得時間（実測ベース）

1 ページ 100 件・間隔 1 秒として:

| | ページ数 | 所要 |
|---|---|---|
| 1 回次（第221回）＝日次 ETL の増分 | 706 | **約 11.8 分** |
| 22 回次＝初回バックフィル | 8,000 | **約 2.2 時間** |
| 参考: 現行（本会議のみ・第221回） | 16 | 約 16 秒 |

日次 ETL は `targets`（既定は直近 5 回次）だけ取得するので、**日次の増分は「現行回次ぶん」**である。
ただし既定 `DEFAULT_SESSIONS` が直近 5 回次であることを踏まえると、
開会中の通常国会が対象に入る日は 5 回次ぶん（最大で 1 時間規模）を取り直すことになる。

## 6. ビルド成果物への波及（実測）

`data/` の増加は `data/` だけでは終わらない。web は `ssr: false` の**静的プリレンダー**で、
`members/index.json` の全議員ぶん HTML を書き出す（`apps/web/react-router.config.ts`）。
現在いちばん重い議員ファイルで実測すると:

| | 実バイト | 元 JSON 比 |
|---|---|---|
| `data/members/m_974040.json`（発言 2,082 行） | 1,137,741 B | 1.00 |
| → `build/client/members/m_974040/index.html` | 2,440,536 B | **2.15** |
| → `build/client/members/m_974040.data` | 858,871 B | 0.75 |
| 合計（配信される成果物） | 3,299,407 B | **2.90** |

**議員 JSON 1 バイトにつき、ビルド成果物は約 2.90 バイト**になる。
`data/members/` が 545 MB になると、ビルド成果物は現在の 487 MB から **約 1.58 GB** に膨らむ計算になる
（`build/client` 全体の実測は現在 487 MB、うち `members/` 279 MB・`data/` 113 MB）。
デプロイは `rsync -az --delete` で共用 VPS に送る（`.github/workflows/deploy-site.yml`）ので、
**VPS のディスクと転送時間に直接効く**。

議員ページは回次ごとに `<details>` で畳むが（#103）、**畳んでいるだけで HTML には全件書き出される**
（`apps/web/app/routes/member.tsx`）。したがって**折りたたみはモバイルの転送量を減らさない**。

nginx は `application/json` に gzip を掛ける（`deploy/nginx/site.conf`）ので、
**実際に回線を流れるのは gzip 後**である。実測した最重量ページ:

| | 実バイト | gzip 後 |
|---|---|---|
| `members/m_974040/index.html` | 2,440,536 B | **227,865 B** |
| `members/m_974040.data` | 858,871 B | **116,948 B** |

**発言 2,082 件で既に約 345 KB（gzip 後）が 1 ページで転送される**。

### 1 議員あたりの偏り（実測）

第221回の会派つき発言を発言者ごとに数えると、**分布は極端に偏る**:

| 院 | 実人数 | 最多 | 中央値 |
|---|---|---|---|
| 衆議院 | 414 | **602 件** | 19 件 |
| 参議院 | 322 | **861 件** | 59 件（`statistics.median` では 59.5） |

（中央値は件数降順に並べた `v[n//2]`。参院は n=322 の偶数なので、
2 値の平均を取る定義では 59.5 になる。定義の差であって値の食い違いではない。）

1 回次で最多 602〜861 件なので、**22 回次では最重量の議員が数千件規模**になる。
現行の最重量ファイル（発言 2,082 件で 1.14 MB・ページ 2.44 MB）から見て、
**この層のページは 1 ページで数 MB〜十数 MB に達する**。平均ではなく、この裾が問題になる。

## 7. 持ち方の推奨

3 案を「検索性」「モバイルでの重さ」「git の肥大」で比較する。数字は上記の実測に基づく。

### git の肥大について（共通の前提・実測）

`writeDataset` は `members/` を**毎回全消しして書き直す**。直近の data 更新コミットを
**`data/members/` に限定して**測ると次の規模になる（コマンド: `git show --stat --format="" {sha} -- data/members`）:

| コミット | `-- data/members` 限定 | コミット全体（`git show --shortstat`） |
|---|---|---|
| `86eb8da` data: refresh 2026-08-24T14:37Z | 303 files, +36,147 / -2,115 | 334 files, +71,723 / -40,248 |
| `d7b4fc2` data: local assemblies 2026-08-24T12:14Z | 112 files, +181,655 / -47 | 474 files, +319,803 / -115 |
| `3689be6` data: refresh 2026-08-24T04:57Z | 771 files, +392,459 / -32,084 | 2,378 files, +711,829 / -32,729 |

**この 2 列は別のものを測っている**（左はパス限定、右はコミット全体）。パス限定の値は
`git log --all --shortstat | grep "303 files changed"` のような**コミット全体の集計では出てこない**ので、
引用するときは必ず「`-- data/members` 限定」と併記すること。

data コミットの回数は数え方で変わる: **現ブランチで `data/` を touch したコミットは 3 か月で 25 回**
（`git log --oneline --since="3 months ago" -- data | wc -l`）、
**全ブランチでメッセージが `data:` で始まるものは 24 回**
（`git log --since="3 months ago" --oneline --all | grep -ciE "^[0-9a-f]+ data:"`）。
`stableJson` はインデント 1 なので、**`SpeechEntry` 1 件が 11 行**を占める。
22 回次の会派つき 615,188 件＝**約 677 万行**が `members/` に載り、
**更新のたびに差分が出うる**（`.git` は現在 77 MB）。

| 案 | 検索性 | モバイルでの重さ | git の肥大 |
|---|---|---|---|
| **(a) 1議員1ファイルのまま** | ○ 変更なし。議員ページは 1 ファイル読むだけで完結し、`/compare` の実行時 fetch も現状のまま | ✗ **最悪**。最重量の議員で 1 ページ数 MB〜。プリレンダー HTML に全件出るので折りたたみでは減らない。ビルド成果物 約 1.58 GB | ✗ 約 677 万行が `members/` に集中。全消し→書き直しなので毎回の diff が巨大 |
| **(b) 発言だけ別ファイル `members/{id}/speeches.json`** | △ 議員ページが 2 ファイル必要になる。プリレンダーはビルド時に両方読めるので**表示上は等価**、ただし `/compare` など実行時 fetch する画面は取得を 1 回増やす必要がある | △ **HTML には結局全件書き出されるので、プリレンダーのままなら軽くならない**。軽くするには「発言タブを実行時 fetch にする」など**描画側の変更とセット**にする必要がある | ○ 発言の行が別ファイルに分離し、発言以外（採決・議案・態度）の diff が発言の巨大な diff に埋もれなくなる。総行数は変わらない |
| **(c) 本文を持たず `speechURL` のみ** | ✗ **抜粋が消えるので、ページ上で「何を言ったか」が読めなくなる**。全文検索の材料も無くなる | ◎ **いちばん効く**。実測で 25.75 MB → 8.92 MB（raw、衆院221 の全発言）、gzip 後は **5.41 MB → 0.42 MB＝約 1/12.7** | ◎ 1 件あたりの行数・バイト数が大きく減る |

**推奨: (b) を骨組みにして、(c) は採らない。ただし (b) 単独では軽くならないので、次の 2 つを #242 の中で決める。**

理由:

- **(c) を採ると「事実を見せる」という目的を損なう**。`excerpt` は要約ではなく原文の冒頭 200 字で、
  議員ページで実際に読ませている唯一の発言内容である（`member.tsx` が `entry.excerpt` をそのまま描画）。
  これを消すと行が「発言した」という事実だけになり、リンク先を開かないと何も分からない。
  中立性の観点でも、**原文の冒頭を出すのは要約より安全**である。
- **(a) のままだと最重量ページが数 MB になる**。これは実測した偏り（1回次で最多 861 件）から避けられない。
- **(b) はファイルを分けるだけでは転送量を減らさない**。プリレンダーが HTML に全件を焼き込むためで、
  これは実測（HTML は元 JSON の 2.15 倍）で確かめた。

したがって #242 で**併せて決めるべきこと**:

1. **収録範囲を 22 回次に広げるか、直近数回次に絞るか**。
   22 回次＝455 MB / 8,000 ページ / 2.2 時間に対し、**第221回だけなら 40 MB / 706 ページ / 12 分**。
   実測した回次別件数（表 5）を見ると、通常国会 6 回次（201・204・208・211・213・217）だけで
   569,936 件＝**全体の 71.5%** を占めるので、**「どこまで遡るか」がサイズを決める最大の変数**である。
2. **議員ページで発言を全件プリレンダーするのをやめるか**。
   やめない限り (a)(b) いずれでもモバイルの転送量は同じである。
   案としては「発言タブだけ実行時 fetch（`members/{id}/speeches.json` を取りに行く）」で、
   これは (b) のファイル分割が前提になる。

**この推奨は運用コストとサイズの比較であって、#242 をやるべきか否かの判断ではない。**
効果の側は実測で大きい。**本番の名寄せコード（`matchSpeeches` → `resolveMember` / `indexByName`）を
実際に import して**第221回の発言を通し、`memberId` が付いた実人数を数えた（自作の簡易突合ではない）。

| 母数（現在の `data/members/index.json` で実測） | 人数 | うち第221回の委員会で発言 |
|---|---|---|
| **個人の記録ゼロ**（`bills` + `questions` + `speeches` が 0）の衆院議員 | 159 | **116 人** |
| **`speeches` が 0** の衆院議員 | 356 | **286 人** |

**この値は「名簿をどう渡すか」で変わる**。本番の `cli.ts` は `matchSpeeches` に**院ごとの名簿**を渡す
（参院発言には参院名簿 `members`、衆院発言には衆院名簿 `shugiin.members`。`cli.ts` L213 / L225）。
DATA_CONTRACT も「発言の院と紐づけ先議員の院は一致する（ETL が不一致を拒否する。#107）」と定めている。

- **院ごとの名簿を渡す（＝本番と同じ）**: **116 / 286**、衆院の `unmatched` は **0 件**
- 参考: 両院を1つのプールにして渡すと **113 / 282**、衆院の `unmatched` は **31 件**

差は、両院プールでは**同姓同名が 7 組**現れ、`resolveMember` が会派でも絞れず `undefined` を返すため
（青山繁晴・中田宏・田中昌史・白坂亜紀の 4 組は会派も同一）。**7 組はすべて「衆院議員と参院議員」の組**で、
本番のように院ごとに渡せば同一プールに入らないので衝突しない。
上表は**本番と同じ渡し方**の値を採った。

なお `159 = 116 + 43` は引き算で出した恒等式なので検算にならない。**独立に数えると**、
個人の記録ゼロ 159 人のうち第221回の委員会で発言した人が 116 人、発言しなかった人が 43 人で、
この 2 つを別々に数えた結果が 159 に一致する。

> **脚注（数字が動いた経緯）**: `individual-records.md`（#237）は「個人の記録ゼロ」を **195 人**と記録しているが、
> これは #237 の spike 時点の値である。その後 同じ Sprint 13 の **#235（質問主意書）・#236（衆院の本会議発言）**
> が入ったため、現在の母数は **159 人**（#244 のタイトル・本文も同じ理由で訂正済み）。
> 上表は 2026-08-25 時点の `data/members/index.json` で数え直したもの。

## 見ていないこと

- **第221回以外の回次で、1件あたりのバイト数・会派つき比率・レコードの形を測っていない**。
  22回次のサイズ外挿（455 MB）は、**第221回で測った比率を全回次に当てはめたもの**である。
  件数 797,651 だけは全回次で実測した。
- **分科会と両院協議会のレコードを 1 件も見ていない**。第221回（特別会）には存在しなかった。
  予算の分科会が立つ通常国会（例: 第217回）で形が同じかは未確認。
  `individual-records.md` が挙げていた「分科会で形が違うか」という問いは、**この調査では答えが出ていない**。
- **116 / 286 は「本番と同じ院ごとの名簿の渡し方」での値**。両院を1つのプールにすると 113 / 282 になる
  （§7 に併記）。どちらを設計の前提にするかは #242 で決める必要がある。
- **参院の `unmatched` 246 件について、なぜ `position` が付かないのか**は確かめていない
  （246 件が「衆院名簿に同名がいる衆院議員の発言」であることは実測したが、
  同じ立場の発言が衆院側では全件 `position` を持つ理由は特定していない）。
- **#71 が無い現状（衆院は 1 回次のみ）で #242 を入れた場合の増分**を計算していない。455 MB は
  「#71 が入って衆院も 22 回次に広がった後」の値である。
- **名寄せ後に実際に `data/` を書いて測っていない**。455 MB は正規化した `SpeechEntry` のバイト数の合計で、
  `members/{id}.json` に配ったときのファイル数・1ファイルの実サイズ・`index.json` の増分は測っていない。
  ETL を通して実際に書き出せば、JSON の入れ子ぶんだけ増える。
- **ビルドを実際に通していない**。1.58 GB は「現在の最重量ファイルで測った 2.90 倍」を全体に掛けたもので、
  発言が増えたときにこの倍率が保たれるかは確かめていない（HTML の定型部分は件数に比例しないので、
  実際の倍率はこれより小さくなる可能性がある）。
- **git の実際の増分を測っていない**。677 万行という行数は計算値で、
  `.git` が何 MB 増えるかは commit して確かめていない（zlib 圧縮と delta 圧縮が効くので行数には比例しない）。
- **`/compare` など発言以外の画面への影響**。(b) を採った場合に実行時 fetch がどう変わるかは設計していない。
- **`speechId` から回次を復元できない問題との関係**。`docs/DATA_CONTRACT.md` の carried の規約では
  `speechId` は NDL の会議録 id で回次を含まないため引き継ぎで回次を復元できず、
  #256 の `lostSessionEntries`（回次粒度の消失検出）は行の `session` に依存する。
  発言を別ファイルに移した場合にこの検算が同じように効くかは検討していない。
- **API のレート制限の実際の上限**。1.2 秒間隔で 706 ページを通したが、
  短縮してよいか（#231 で見直し中）はこの調査では判断していない。
