## 2. コードポイント走査（受け入れ条件 1）

### 2.1 数え方

正規表現の文字クラスは**すべて `\uXXXX` エスケープで書いた**。
理由は、**最初リテラルで `[豈-﫿]` と書いたところ、打った「豈」が U+8C48（CJK 統合漢字）だったため
範囲が U+8C48–U+FAFF になり、「野」「高」「関」など普通の漢字を大量に拾っていた**からである。
そのときは「互換漢字入り 13,905 票」という**偽の数字**が出た。

**式が正しいことを、正負の対照で先に示してから数えた:**

```

対照 '岡﨑'(U+FA11)         期待=True 実際=True
対照 '野'                   期待=False 実際=False
対照 '高'                   期待=False 実際=False
対照 '髙'(U+9AD9)           期待=False 実際=False   ← 異体字だが互換漢字ではない
対照 '𠮷'(U+20BB7)          期待=True 実際=True
```

## 3. Unicode 正規化では解けないことの確認

#529 が青森で観測した「どの正規化でも一致しない」は、既存 7 県のデータでもそのまま成り立つ。

```
'辻󠄀内 裕也' vs '辻内 裕也'
  NFC:  False   NFKC: False   NFD:  False   NFKD: False
```

**U+FA11 は Unicode のどの正規化形でも変化しない**（実測。JIS 互換のため正規化から除外された
「例外的な互換漢字」に当たる）:

```
U+FA11 の NFC / NFKC / NFD / NFKD → すべて U+FA11
```

つまり **`normalize()` を何段重ねても罠 2 は解けない**。解いているのは各実装が持つ**明示的な変換表だけ**である。

## 5. 「別人の記録が出る」向きの検査（受け入れ条件 1・2）

これが Issue の主眼なので、**衝突が生まれる向き**を独立に数えた。

### 5.1 字体を畳むと同名衝突が生まれるか

名簿 1,057 名を、(a) 空白除去のみ (b) 国会の `normalizeName` (c) 地方の `nameKey` の
3 通りでキー化し、**同じキーに 2 人以上入る組**を数えた。

```
空白除去のみ:              7 組が衝突 / 1,050 キー / 1,057 名
match-votes.normalizeName: 7 組が衝突 / 1,050 キー / 1,057 名
shimane/kochi/nara nameKey: 7 組が衝突 / 1,050 キー / 1,057 名
```

**3 通りとも同じ 7 組で、内訳も同一。** そしてその 7 組は**すべて生の表記から既に同姓同名**である
（青山繁晴・鬼木誠・河野義博・白坂亜紀・田中昌史・中田宏・和田政宗。いずれも参院と衆院に 1 人ずつ。
#369 で既知の 4 組を含む）。

**つまり字体を畳んだことで新たに生まれた衝突は 0 件。**

さらに**本番の呼び出し方**（`cli.ts` が名簿を院ごと・議会ごとに分けて渡す形）を再現すると:

```
sangiin: 0 衝突 / 307 名      shugiin: 0 衝突 / 465 名
pref-04: 0 / 56   pref-24: 0 / 47   pref-29: 0 / 40   pref-31: 0 / 35
pref-32: 0 / 35   pref-36: 0 / 36   pref-39: 0 / 36
```

**本番の分け方では衝突 0。** 上の 7 組は院をまたぐ組なので、院ごとに分けた時点で消える。

### 5.2 いちばん危ない実例を名指しで確認した

宮城（pref-04）の名簿には **`高橋`/`髙橋` が 4 人**いる:

```
p_04_kei                 高橋 啓      (U+9AD8)
p_04_meibo_takahashika   高橋 克也    (U+9AD8)
p_04_syuya               高橋 宗也    (U+9AD8)
p_04_sinji               髙橋 伸二    (U+9AD9)   ← 字体だけが違う
```

**宮城の `nameKey` は `髙→高` を畳まない。** 表決 PDF 側も名簿と同じ U+9AD9 を使っており、
4 人とも別々に正しく紐づいている（各 133 票）:

```
'高橋 克也'(U+9AD8) -> p_04_meibo_takahashika  133
'高橋 宗也'(U+9AD8) -> p_04_syuya              133
'高橋 啓'  (U+9AD8) -> p_04_kei                133
'髙橋 伸二'(U+9AD9) -> p_04_sinji              133
```

**ここに交換関係がある。**「畳む／畳まない」はどちらかが常に正しいのではなく、**壊れ方の向きが違う**:

```
名簿 [髙橋 伸二, 高橋 伸一]、PDF が「高橋 伸二」と書いた場合（罠 2 の形）
  畳まない → (未解決→unmatched)      ← 記録が出ない
  畳む     → 髙橋 伸二                ← 正しく紐づく

名簿 [髙橋 伸二, 高橋 伸二]（字体だけ違う別人が 2 人いる場合）
  畳まない → 髙橋 伸二                ← 正しく紐づく
  畳む     → (2人→未解決)             ← 記録が出ない
```

**下段の「畳むと別人と混ざる」形は、幸い現在の名簿には存在しない**（5.1 で 0 件と数えた）。
だが **`髙橋` と `高橋` が同じ名簿に同居している議会が現に 1 つある**以上、
**下の名前まで一致する 2 人が来たら成立する**。今は成立していないだけである。

### 5.3 部分列フォールバック（奈良・島根・高知）の危険度

奈良・島根・高知は、完全一致で 0 人のとき「**名簿の氏名に PDF の氏名が順序どおり部分列として含まれる**」
議員が 1 人に決まるときだけ寄せる、というフォールバックを持つ。**これは #529 の罠 1（欠ける）への対処**で、
コメントにも「文字層に落ちる字（外字「芦」・「均」）が先頭にも末尾にも出るため」と書いてある。

**このフォールバックが別人を掴む余地を数えた:**

```
名簿内で、ある議員の氏名が別の議員の氏名の部分列になっている組（奈良・島根・高知）: 0 組
先頭 1 字が欠けた形が別人に一意に当たる件数（同 3 議会）: 111 通り中 0 件

名簿の各氏名から 1 字落とした形（フォールバックを持つ奈良・島根・高知の 3 議会に限る）:
  430 通り中 → 唯一に決まる 426 / 複数候補（→unmatched）4 / **別人に一意に当たる 0**
（参考。全 9 議会に広げると 4,219 通り中 唯一 4,130 / 複数 89 / **別人 0**。
 ただしフォールバックが実際に働くのは上の 3 議会だけなので、判断に使うのは 430 の側）
```

**「1 字欠けたら別人になる」組は 1 つも無い。** これは名簿が小さい（35〜47 名）ことに依るので、
**議会が増えれば成り立たなくなりうる**（この点は確かめていない——将来の名簿は手元に無い）。

## 9. 既存テストが何を守っているか（変異で確かめた）

「テストがある」ではなく「**変異させて落ちるのを見た**」結果だけを書く。
変異は `scripts/dev/mutate.sh run` で当てた（md5 が変わったことを毎回確認している）。

**基準**: `packages/etl` の 4 ファイル（nara/mie/kochi/miyagi の `*-rollcalls.test.ts`）で **26 tests / 26 pass / 50.8 秒**。

| 変異 | 予測 | 実測 | 落ちた理由 |
|---|---|---|---|
| **M1** 奈良 `nameKey` から IVS 除去を削除 | 落ちる | **3 fail / 6** | `actual: [{ nameText: '芦󠄀髙清友', ...}]` を unmatched に出した。**狙いどおり** |
| **M2** 三重 `nameKey` から IVS 除去を削除 | 落ちる | **3 fail / 4** | `actual: '辻󠄀内裕也'`。**狙いどおり** |

| **M5** 奈良の部分列フォールバックを「候補が 1 人以上なら先頭を採る」に改悪（＝**別人を掴む**変異） | 落ちる | **1 fail / 6** | 一意性の要求は守られている |
| **M6** 宮城 `nameKey` を「全角空白を見ない ＋ `髙→高` を畳む」に差し替え | 落ちる（と考えた） | **5 pass / 5 = 素通り** | **守られていない**（下記） |

### 9.1 M3 の読み違いを訂正する

**「落ちた」と「狙った理由で落ちた」は別**なので、失敗の中身を見た:

```
✖ matchName: 名簿と完全一致（空白・異体字を寄せる）で 1 人に決まれば寄せる
  '' !== 'p_39_29'
```

テスト本体のコメントが実態を正確に書いていた:

> `// 岡﨑（異体字）は名簿も PDF も「﨑」。「岡崎」でも寄る`

**つまり高知の `﨑→崎` は、実データでは 1 度も必要になっていない防御的な行**であり、
それを固定しているのは**単体テストが作った入力だけ**である。**私の「実データの経路では落ちない」という予測は正しく、
「テストが落ちない」という予測が誤りだった。** 両者を混同していた。

### 9.2 M6 が素通りする理由（等価変異ではない）

M6 は `髙→高` を足し、同時に全角空白の処理を落とす変異である。**5/5 緑のまま**だった。
まず**等価変異ではないこと**を確かめた:

```
"髙橋 伸二"  元="髙橋伸二"  変異後="高橋伸二"   ★違う
"高橋　克也" 元="高橋克也"  変異後="高橋克也"   同じ
```

**キーが実際に変わるのに、テストは 1 件も落ちない。** 理由は構造的である:

**`nameKey` は名簿側と PDF 側の両方に同じ関数を当てる**ので、
**両側に同じ単射な写像を足しても結果は変わらない。**

```
名簿=[髙橋 伸二, 高橋 克也, 高橋 啓, 高橋 宗也]、PDF も同じ字
  元:   ["髙橋 伸二","高橋 克也","高橋 啓","高橋 宗也"]
  変異: ["髙橋 伸二","高橋 克也","高橋 啓","高橋 宗也"]   ← 同じ
```

**この fixture では等価**だが、**一般には等価ではない**（5.2 の 2 つの表が非等価な入力そのもの）。
**「両側が食い違う」入力が fixture に 1 つも無い**のが原因で、**実装ではなく見本の問題**である。

**これが本調査で見つかった、テスト側のいちばん大きな穴である**:
**正規化の規則を変えても、7 県ぶんのどのテストも鳴らない。**
`data/` は正しく作り直されるまで気づけず、しかも**壊れ方は「紐づかない」と「別人に紐づく」の両方がありうる。**

（M6 は宮城で測った。**同じ形が鳥取・徳島・三重・島根・高知・奈良にも当てはまるかは、
この 1 件しか測っていないので確かめていない。** 上の推論は構造から言えるが、**測ってはいない。**）

## 付録 B: PR #566 の「櫛」の数値を測り直した（2026-09-07）

PR #566（`docs/research/local-assemblies.md`）は、青森の `櫛引ユキ子` が欠けた理由をこう書いている:

> そのため `cx = x = 642.9` になり、**列の中心 648.5 から 5.6pt ずれる**。
> 中心からの許容差を **±6** にしていたため、**「櫛」だけが落ちて氏名が `引 ユキ子` になった**。

**`648.5 − 642.9 = 5.6` は `6` より小さいので、この説明のままでは落ちない。**
PO の指摘どおり数字が合っていないので、**一次資料の PDF を取り直して測った。**

**取得**: `https://www.pref.aomori.lg.jp/soshiki/gikai/files/326teirei_sanpi.pdf`
→ HTTP 200 / **507,968 バイト**（PR #566 が記録した値と一致）/ 1 ページ / 文字アイテム **1,701 個**（同上）。
測定は本リポジトリの `readPages` / `cluster`（`packages/etl/src/sources/local/pdf-table.ts`）をそのまま import した。

### B.1 実測値

| 項目 | PR #566 の記述 | **実測** |
|---|---|---|
| `櫛` のコードポイント | U+6ADB U+E0101 | **U+6ADB U+E0101**（一致） |
| `櫛` の `x` | — | **642.920** |
| `櫛` の `w` | `w=0.0` | **0**（一致） |
| `櫛` の `cx` | `642.9` | **642.920**（一致） |
| 「列の中心」 | `648.5` | `引` の `cx` は **648.470**。ただし下記のとおり**判定に効くのは 648.470 ではない** |
| ずれ | `5.6` | `648.470 − 642.920` = **5.550** |
| 許容差 | `±6` | **`±6` という値はコードのどこにも無い。実際は `cluster(…, 3)`（高知・`kochi/votes-pdf.ts`）** |

### B.2 判定の形が「中心からの距離」ではない

**`cluster` は固定した列の中心からの距離を見ていない。** 実装はソートしたうえで
**「直前のクラスタの**逐次平均**との差」を `eps` と比べ、`<=` なら併合する**（`<` ではない）。

そのため**決め手になる比較は `引`(648.470) との差ではなく、`ユ`/`キ` との差**である。
カタカナの `ユ`/`キ` は `w=10.6671` と漢字（`w=11.1`）より細いので `cx=648.44355` にあり、
ソート順で `櫛`(642.920) の直後に来る:

```
642.920 は直前の平均 633.8900 と差 9.0300 > eps → 新しいクラスタ
648.444 は直前の平均 642.9200 と差 5.5240 … ここが分かれ目
```

**`648.44355 − 642.920 = 5.523550`。** これが本当の境界値である。

### B.3 再現できた（境界値つき）

ページ全体の文字を `cluster(chars.map(c => c.cx), eps)` に通し、`引` の列を `joinVertical` で縦読みした:

```
eps=3     列数=59  「引」の列 → "引 ユキ子 ○"        櫛は列17 / 引は列18  ★別列＝欠落
eps=5.5   列数=59  「引」の列 → "引 ユキ子 ○"        櫛は列17 / 引は列18  ★別列＝欠落
eps=5.6   列数=58  「引」の列 → "櫛󠄁 引 ユキ子 ○"     同じ列
eps=6     列数=58  「引」の列 → "櫛󠄁 引 ユキ子 ○"     同じ列
```

**二分探索で詰めた境界（列だけで回しても、ページ全体で回しても同じ）:**

```
境界 eps ≈ 5.523550
  eps <  5.523550 → 櫛 は別クラスタ（氏名が「引 ユキ子」に欠ける）
  eps >= 5.523550 → 櫛 は氏名の列に入る（欠けない）
```

### B.4 結論

- **現象は本物である。** `櫛引ユキ子` は実際に **`引 ユキ子`** になる。**再現できた。**
- **原因の説明の数字が違う。** 正しくは:
  - ずれは **5.6 ではなく 5.550**（`引` との差）、
    **判定に効くのは 5.523550**（`ユ`/`キ` との差）
  - 許容差は **`±6` ではない**。コードにあるのは **`cluster(…, 3)`**。
    **`±6` なら櫛は落ちない**（`5.52355 <= 6`）ので、PR #566 の因果の説明は成立しない
  - 判定は「中心からの距離 < 許容差」ではなく、
    **「ソート順で直前のクラスタの逐次平均との差 `<=` eps なら併合」**
- **PO の指摘（レビューが挙げた「±5.55 未満」）はほぼ当たっていた。**
  **正確な境界は 5.523550** で、5.55 との差は `ユ`/`キ` が漢字より細いぶんである。

**これは作業合意の「現象は本物でも、原因の説明は別に検証が要る」（#243）そのものの形である。**
**「落ちた」ことは正しく観測されていたが、「なぜ落ちたか」は確かめられていなかった。**
