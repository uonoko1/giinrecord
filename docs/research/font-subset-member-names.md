# 議員名の明朝 700 を、見た目を変えずに軽くできるか

Issue #468 の調査の記録。**この issue では実装していない。**
`docs/research/font-transfer.md`（#449/#453）の続き。あちらが「原因はウェイトの重複」で
止まったのに対し、こちらは **`/members` の明朝 700（1,062 KB）だけ**を見ている。

結論を先に書く:

- **減らせる。実測で `/members` は 1,950 KB → 1,033 KB（初期表示）、
  展開後は 3,017 KB → 1,033 KB。** 明朝 700 だけで見ると **2,157 KB → 172 KB**。
- **方法は「ビルド時サブセット」**。議員名は `data/members/index.json` に確定しているので、
  出る字だけのフォントを作れる。**書体もウェイトも変えない。** #453 の判断には触らない。
- **見た目は変わらない。** 997 名の名前の**箱が 997 件すべて 1px も動かない**。
  描画に使われた face も `Shippori Mincho(custom=true) glyphs=1991` で**現状と同一**。
  スクリーンショットの差は**字の縁のアンチエイリアスだけ**（後述）。
- **ただし `/` は 931 → 989 KB と 58 KB 増える。** `/` は明朝 700 を 26 字しか使わないので、
  今は 8 スライス 114 KB で済んでいる。サブセットは**ページによらず 172 KB を必ず引く**。
  **減る側と増える側の両方がある案である。**
- **最大の危険は「Google の `text=` が黙って全スライスに戻る」こと。**
  URL 引数が約 7.2 KB を超えると、**エラーにならずに 122 スライスの CSS が返る**。
  **現在の対象 848 字は既にこの上限を超えている**（7,432 B）。分割すれば通るが、
  **検査を入れないと「効かなくなったこと」に誰も気づかない。**

---

## 1. 測り方

`origin/main`（`5fc916e6`）を `pnpm --filter web build` でビルドし、
`build/client` を素の Node の静的サーバ（gzip 無し）で配って Playwright の Chromium で開いた。
**390px 幅・ページごとに新しいコンテキスト**（＝初回訪問）。

- **woff2 のバイト数は `response` ハンドラで `await r.body()` してから記録した。**
  `encodedBodySize` は同じページを繰り返し開くと **0 を返す回がある**（実際に踏んだ。
  3 回のうち 1 回だけ `/members` が 1,341 KB になった）。**woff2 は gzip されない**ので
  （`deploy/nginx/site.conf:91` の `gzip_types` に font/woff2 は無い）、
  **本文バイト数 = 転送量**であり、`encodedBodySize` と一致する。
- **この測り方は本番と一致した。** `/members` 初期 **118 件 1,950 KB**、
  展開後 **139 件 3,017 KB** は、PO が本番で測った値と**件数もバイト数も同じ**。
  3 回とも同じ値。
- **`CSS.getPlatformFontsForNode` を `.members-item__name` の 400 要素について見た。**
  これを見ないと差が分からない（§5 で実際に助かった）。
- 名前の**箱は 997 要素すべて**を `getBoundingClientRect()` で測った
  （#456 の「見えている範囲を全体と書かない」）。

## 2. 61 スライスで実際に使われている字数（受け入れ条件 1）

**実測。**

| | 明朝700 のスライス | 転送量 | 明朝700 が描いた**異なり字数** |
|---|---:|---:|---:|
| 初期表示（229 名） | 62 | 1,090 KB | **339 字** |
| 展開後（997 名） | 83 | 2,157 KB | **665 字** |

（issue 本文の「61 スライス」は `.N.woff2` の数で、`latin` を足すと 62。以下 62 で書く。）

**1 スライスあたりの使用字数の分布（実測）:**

| | 1 字だけ | 2〜5 字 | 6〜20 字 | 21 字以上 |
|---|---:|---:|---:|---:|
| 初期表示 | **12 件 413 KB (38%)** | 25 件 347 KB (32%) | 24 件 298 KB (27%) | 1 件 31 KB (3%) |
| 展開後 | **20 件 1,033 KB (48%)** | 18 件 535 KB (25%) | 40 件 515 KB (24%) | 5 件 73 KB (3%) |

重い順（初期表示、実測）:

```
shippori-mincho-700.23.woff2    66 KB  使用 1 字   66.5 KB/字
shippori-mincho-700.41.woff2    57 KB  使用 1 字   57.4 KB/字
shippori-mincho-700.26.woff2    56 KB  使用 1 字   56.4 KB/字
shippori-mincho-700.28.woff2    53 KB  使用 1 字   53.0 KB/字
shippori-mincho-700.42.woff2    51 KB  使用 1 字   51.2 KB/字
shippori-mincho-700.20.woff2    47 KB  使用 1 字   47.4 KB/字
shippori-mincho-700.119.woff2   31 KB  使用 38 字   0.8 KB/字
```

**「1 字のために 66 KB」が実在する。** 展開後は 1 字だけのスライスが 20 件・1,033 KB になり、
**明朝 700 の転送量のほぼ半分**を占める。

**ただし #453 の警告どおり、これは「スライスが細かすぎる」ことの証明ではない。**
Google のスライスは頻度順に詰まっており（`font-transfer.md` §5-1 が 1 字あたり 138〜254 B と実測済み）、
粒度を動かしても総量は減らない。**効くのは「収録字数そのものを減らす」ことだけ**である。

### PO の観察の答え合わせ

> +1,067 KB 増えたのにスライスは 21 個しか増えていない。
> 「議員名の漢字は実はそれほど散っていない」ことを示唆するかもしれない

**半分当たっていて、半分外れている。**

- **当たり**: 768 名を足しても**新しいスライスは 21 個だけ**（実測 62 → 83）。
  スライスの「散り方」は確かに頭打ちになる。
- **外れ**: それでも **+1,067 KB 増える**。増えた 21 個が**1 字ずつしか使わない重いスライス**
  だからで、**「散っていない」ことは「軽い」を意味しない。**
  字数は 339 → 665 と 2 倍だが、転送量も 1,090 → 2,157 KB と 2 倍になっている。

**「スライス数」で軽さを見積もると外す。バイト数で見ること。**

## 3. 案: ビルド時サブセット（実測付き）

議員名に出る字は `data/members/index.json` にあり、**ビルド時に確定している**。
その字だけの woff2 を作って `shippori-mincho-700.*` の 122 面と差し替える。

### 3-1. 対象にすべき字（**ここで一度失敗した**）

最初、**議員名の字だけ（678 字）**でサブセットを作って測った。
`/members` は 1,950 → 996 KB になったが、**`/`・`/coverage`・`/assemblies` で
`WenQuanYi Zen Hei`（システムフォント）に落ちた**。
明朝 700 は `.tag` / `.section__title` / `.zip__title` にも使われており、
**議員名以外の字**（「議会」「会派」「反対」など）が抜けていた。

**`getPlatformFontsForNode` を見ていなければ気づかなかった。**
転送量だけ見ると `/members` は「減って成功」に見えていた。

対象を測り直した（各ページで明朝 700 が実際に描いた字を DOM から収集、実測）:

| ページ | 明朝700 が描く異なり字数 |
|---|---:|
| `/members`（展開後） | 665 |
| `/coverage` | 57 |
| `/assemblies` | 46 |
| `/about` | 35 |
| `/` | 26 |
| `/sources` | 9 |
| 議員詳細 20 件のサンプル | 45 |
| `/rollcalls` | **0**（明朝 700 を使っていない） |

これに `index.json` の全 1,057 名の名前・会派名・選挙区名の字を足して
**848 字**（空白 2 種を入れて 851 字）。**これが対象である。**

### 3-2. 作り方と、そこで踏んだ罠

**`pyftsubset` は入れていない**（依存の追加は PO の判断事項）。代わりに
**`scripts/fonts.ts` が既に使っている Google Fonts の `text=`** で作った
（同じ 3 ホストしか叩かないので `docs/ops/fonts.md` の方針の中に収まる）。

**罠: `text=` は上限を超えると、エラーではなく 122 スライスの CSS を返す（実測）。**

| 字数 | URL 引数 | 返ってきた `@font-face` |
|---:|---:|---|
| 800 | 7,184 B | **1**（サブセット） |
| 810 | 7,274 B | **122**（全スライスに逆戻り） |
| 848（今回の対象） | 7,432 B | **122** |
| 2,000 | 17,984 B | HTTP 400 |

**上限は「字数」ではなく URL 引数のバイト数で、約 7.2 KB。**
**現在の対象 848 字は既に超えている。** 400 が返るなら気づくが、
**122 スライスが返るのは黙って元に戻るのと同じ**である。

**2 分割で回避できる**（実測）:

```
p0: 425 字 / 3,616 B -> 77,880 B   @font-face=1
p1: 426 字 / 3,834 B -> 98,404 B   @font-face=1
合計 176,284 B = 172.2 KB
```

**罠 2: 空白を落とすと名前の 1 文字だけフォールバックする。**
最初の 2 分割は氏名の間の**全角空白 U+3000 を対象から外していた**ため、
229 名中 **218 名**が `Shippori Mincho:4 / Liberation Serif:1` になった。
**箱の比較では検出できなかった**（997 件すべて 0 差）。
`getPlatformFontsForNode` だけが捕まえた。

> **訂正（#477、2026-09-05）: いまのデータに全角空白 U+3000 は 1 文字も無い。**
> `data/members/index.json` の氏名の区切りは **1,013 件すべて U+0020（半角空白）**で、
> ビルド済み HTML にも U+3000 は現れない（実測。PO も独立に確認）。
> **現象（区切りの空白を落とすと 1 グリフだけフォールバックする）は本物**だが、
> **字を名指しで固定すると、実態と違うものを守ることになる。**
> #477 の実装では「U+3000 が入っている」ではなく
> **「目に見えない字が 1 つも欠けていない」**を検査している
> （`apps/web/app/lib/font-subset-coverage.test.ts`）。
> 実際に U+0020 を落とす変異を入れると、**1,013 名の氏名で落ちる**ことを確認済み。

### 3-3. 実測（3 回とも同じ値）

`fonts.css` の `shippori-mincho-700.*` 122 面を消し、上の 2 面に差し替えたビルドを
同じ手順で測った。

**`/members`**

| | 現状 | サブセット | 差 |
|---|---:|---:|---|
| 初期表示 woff2 | 118 件 **1,950 KB** | 58 件 **1,033 KB** | **−917 KB（−47%）** |
| 展開後 woff2 | 139 件 **3,017 KB** | 58 件 **1,033 KB** | **−1,984 KB（−66%）** |
| うち明朝700（初期） | 62 件 1,090 KB | 2 件 172 KB | −918 KB |
| うち明朝700（展開後） | 83 件 2,157 KB | 2 件 172 KB | **−1,985 KB** |

**「さらに表示」を押しても転送量が増えない**（58 件 1,033 KB のまま）。
現状は押した瞬間に +1,067 KB 増えるので、**展開する利用者にはこの案がいちばん効く。**

**全ページ（実測、初期表示）**

| ページ | 現状 | サブセット | 差 |
|---|---:|---:|---:|
| `/members` | 1,950 KB | 1,033 KB | **−917** |
| `/coverage` | 1,154 KB | 1,090 KB | −64 |
| `/assemblies` | 1,174 KB | 1,143 KB | −31 |
| `/rollcalls` | 888 KB | 888 KB | **±0**（明朝700 を使わない） |
| **`/`** | **931 KB** | **989 KB** | **＋58** |

**`/` は増える。** 明朝 700 を 26 字しか使わないページは、
今は 8 スライス 114 KB で済むのに、サブセットは**常に 172 KB を引く**から。
**#453 の「引き算のつもりが足し算だった」と同じ形の現象が、規模は小さいが起きている。**
今回は**外した状態を実際に作って測った**ので、事前に分かっている。

### 3-4. 見た目が変わらないことの確認（受け入れ条件 3）

1. **名前の箱: 997 件すべて一致（0 件差）。** テキスト・幅・高さを 0.01px 単位で比較。
2. **描画に使われた face: 同一。** 400 要素で
   `Shippori Mincho(custom=true) glyphs=1991` — 現状と 1 グリフも違わない。
   **システムフォントに落ちた要素は 0 件**（全 5 ページで確認）。
3. **スクリーンショット（390px、2x、全ページ長 2,800px）**:
   同じビルド同士は **0 px 差**（対照）。現状 vs サブセットは **5,645 px（0.258%）差、最大チャンネル差 218**。
   - 差の場所は**字の輪郭のみ**。閾値 128/160/200 のどれで 2 値化しても
     **インク画素の 0.20〜0.21% しか違わない**（閾値を変えても比率が動かない
     ＝**位置や字形ではなく縁の濃さ**が違う）。
   - 拡大して目で見ても字形は同じ（`青山 繁晴` などで確認）。
   - **原因はサブセット化でグリフ ID の並びとヒンティング表が変わり、
     サブピクセルアンチエイリアスが 1/3 px ずれること。** 字送りは変わっていない
     （箱が 997/997 一致しているのが根拠）。

**「同じ見た目」と言えるが、「ビット単位で同一」ではない。** 区別して書く。

## 4. 危険（受け入れ条件 5）

### 4-1. サブセットに無い字が来たらどうなるか — **名前は消えない**（実測）

**このプロジェクトで最も避けたい「名前が出ない」は起きない。**
サブセットに無い漢字を明朝 700 の要素に入れて測った:

| ビルド | 描画に使われた face | 文字 |
|---|---|---|
| 現状 | `Shippori Mincho(custom=true, glyphs=6)` | `彁妛暃穝橸壥` |
| サブセット | `WenQuanYi Zen Hei(custom=false, glyphs=6)` | `彁妛暃穝橸壥` |

**字は表示される。書体が明朝でなくなるだけ**（`--font-head` の
`"Hiragino Mincho ProN", "Yu Mincho", serif` にフォールバックする。
上の `WenQuanYi Zen Hei` は測定環境の Linux に明朝が無いためで、
利用者の環境では明朝系に落ちる可能性が高い）。**箱の幅も同じだった。**

**つまり失敗の形は「名前が出ない」ではなく「その名前だけ書体が違う」。**
訂正可能で、利用者から見て虚偽ではない。**#453 の「出さない側に倒す」原則には抵触しない。**

**ただし気づきにくい。** 転送量も箱も変わらないので、
**`getPlatformFontsForNode` を見る検査を入れない限り、誰も気づかない。**

### 4-2. ETL の日次更新との相性

`deploy-data.yml` → `deploy-site.yml` は **`data/` を overlay してから `pnpm build`** する
（`deploy-site.yml:64` の overlay が `:71-72` の install/build より前）。
**サブセットをビルド時に作れば、日次更新で入った新しい議員の字も同じビルドで入る。**

**ただし現状の `scripts/fonts.ts` はビルドでは動かない**（`docs/ops/fonts.md`「手動実行」）。
ビルド時に作るなら **`pnpm build` が Google Fonts を叩く**ことになり、これは今と方針が変わる:

- ビルドが**外部サービスの可用性に依存する**。Google が落ちていたらリリースが止まる。
- 訪問者の IP は依然 Google に行かない（#168 の目的は守られる）が、
  **`docs/ops/fonts.md` の「生成は手動」という設計は変わる。**

**代案**: 対象の字を**リポジトリにコミット**し（`apps/web/public/fonts/` の 2 ファイル）、
ETL が `index.json` を更新したときに**字が増えたかを検査して、増えたら落とす**。
落ちたら人がフォントを作り直す。**転送量の利得は同じで、ビルドは外部に依存しない。**
代わりに「新しい議員の字が、フォント再生成までの間だけシステム書体になる」。

### 4-3. `text=` の上限に近い（**最大の運用上の危険**）

§3-2 のとおり **1 リクエストの上限は約 7.2 KB（BMP の漢字で約 800 字）**で、
**現在の対象 848 字は既に超えている**ので 2 分割が前提になる。

**2 分割でどこまで耐えるかを実測した**（計算ではなく作って測った）:

| 対象字数 | 分割 | 各パート | 合計転送量 |
|---:|---:|---|---:|
| 851（現在） | 2 | 425 / 426 字 | **172 KB** |
| 1,600 | 2 | 800 / 800 字 | **390 KB** |

1,600 字でも 390 KB で、**現状の 2,157 KB よりはるかに小さい**。
パートを増やせばさらに伸びるので、**上限そのものは行き詰まりではない。**
問題は**超えたときに黙って 122 スライスに戻る**ことなので、
**「返ってきた `@font-face` が 1 であること」を検査する**必要がある。

### 4-4. 字の増え方（どれくらい猶予があるか）

`data/members/index.json` の履歴を実測:

| 日付 | 議員数 | 名前の異なり字数 |
|---|---:|---:|
| 2026-08-22 | 307 | 411 |
| 2026-08-23 | 772 | 598 |
| 2026-08-24 | 1,057 | **672** |
| 2026-09-04 | 1,057 | **672** |

**2026-08-24 以降 12 日間、字数は 1 字も増えていない。**
増えたのは**議会をまとめて足したとき**で、日次の入れ替わりでは増えていない。
**ただし地方議会はまだ追加中**なので、**次の議会追加でまとめて増える**と考えるべき。
**「日々じわじわ増える」ではなく「たまに一気に増える」**性質である。

### 4-5. 小さいが正直に書くこと

- **`fonts.css` の gzip 後が 37,227 → 38,131 B と 0.9 KB 増える。**
  `renderFontsCss` は同じ `unicode-range` を持つ 5 面を隣接させて gzip を効かせているが、
  明朝 700 だけ別形式になるとその並びが崩れる。**転送量全体では誤差。**
- リポジトリからは **3.66 MB（122 ファイル）が消えて 172 KB（2 ファイル）になる。**
- **`/rollcalls` には何の効果も無い**（明朝 700 を使っていない）。
  `/rollcalls` の 888 KB は `BIZ UDPGothic 700`（議案名）で、**これは別の問題**
  （`font-transfer.md` §5-2 の案 A）。

## 5. 測り方について、次の人へ

- **`encodedBodySize` は同じページを繰り返し開くと 0 を返す回がある。**
  `response` ハンドラで `await r.body()` してから記録するほうが安定した
  （3 回とも同値になった）。**woff2 は gzip されないので body の長さ = 転送量。**
  「`body().length` は解凍後なので `encodedBodySize` を使え」という注意は
  **gzip される CSS/JS についてのもの**で、**woff2 には当てはまらない**
  （`deploy/nginx/site.conf:91` の `gzip_types` に font/woff2 は無い）。
  両方に同じ規則を当てると、かえって測れなくなる。
  なお `font-transfer.md` §1 は逆に **`body().length` だけを見ると 3 回とも一致した**と
  書いており、woff2 についてはそちらが正しい。
- **箱の比較は、フォールバックを検出できない。**
  §3-2 の壊れた 2 分割は **997 件すべて箱が一致した**のに、
  218 名の名前が 1 グリフずつシステムフォントに落ちていた。
  **`getPlatformFontsForNode` を見ないと「効いている」と「壊れている」が区別できない。**
- **スクリーンショットの 1 回目は当てにならない。**
  同じビルドを 2 回撮ると 1 回目だけ 0.124% ずれた（フォント描画の暖機と思われる）。
  **1 回捨ててから撮ると、同じビルド同士は 0 px になる。**
- **外部 API の「上限」は、エラーで教えてくれるとは限らない。**
  Google の `text=` は超えると**成功したふりをして別物を返す。**
  #243 の「検索 API のヒット件数を判定に使わない」と同じ形の落とし穴である。

## 6. まとめ（PO の判断のために）

**やる価値はある。** `/members` の展開後で **3,017 → 1,033 KB（−66%）**、
初期表示でも **−917 KB**。**書体もウェイトも変えない**ので #453 の判断に触らない。

**ただし決めることが 3 つある:**

1. **サブセットをいつ作るか。** ビルド時（日次更新に自動追従するが、
   ビルドが Google に依存する）か、コミット済み＋検査（外部依存なし、
   ただし再生成までの間は新しい字がシステム書体）か。
2. **`text=` を使うか、`pyftsubset` を入れるか。** `text=` は依存が増えないが
   **上限で黙って壊れる**ので検査が要る。`pyftsubset` は上限が無く分割も自由だが**依存が増える**。
3. **`/` が 58 KB 増えるのを受け入れるか。** 受け入れないなら、
   `/` の明朝 700（26 字・114 KB）だけ別扱いにする必要があり、複雑になる。

**この issue では実装していない。** 上の 3 つは PO が決めること。
