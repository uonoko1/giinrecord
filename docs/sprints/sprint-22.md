## 2. 「監視している」が実効を伴っていなかった（#373）

`monitor.yml` は `*/10`（10分おき）だが、実測は**中央値119分・最大676分（11時間）・
10分以内は3%**だった。`monitoring.md` は運用目標として
「全議会を60分以内に一度は見る」「最悪検知遅延およそ40分」と**数字で約束していた**が、
これは10分間隔を前提にした計算である。**60分を超えた間隔が59回中42回**あった。

同じファイルが自分で警告している状態そのものだった:

> 放置すると「監視している」という安心感だけがあって実効が無い状態になる。

**設定は変えず、ドキュメントを実測に合わせた。** VPS 側の cron は実測でちょうど5分間隔で
動いている（自前のマシンなので間引かれない）ので、
**落ちたことに確実に気づく役目は VPS 側**、`monitor.yml` は「外から見えるか」の補助、と役割を明記した。

**設定をいじる前に測る。** 測らずに変えても、また同じ状態になる。

## 3. 「再実行したら通った」で閉じない（#377）

CI で `monitor-probe` が1度だけ落ちた。ローカルでは私のブランチでも main でも通り、
再実行で通った。**原因は特定できていないので、issue を開けたままにした。**

CI が不安定だと、次に本当の失敗が来たときも「また flaky だろう」と読み飛ばすようになる。

調査中に立てた仮説（`"sec"` という3文字が `mktemp` のランダム名に紛れ込む）は、
**確率を計算すると 0.002%** で今回の失敗を説明できず、外れだった。
**仮説が外れたことを認めた上で**、それとは別に「3文字の部分文字列で秘密の不在を見るのは脆い」
という事実は残るので、sentinel 値に変えた（#378）。
**秘密を本当に argv に載せる変異で2件落ちる**ことを確認し、検査の強さを落としていないことも示した。

## 4. 「直せるが見られない」権限（#375）

`giinops` は `docker compose up -d --force-recreate`（**再起動**）はできるのに
`ps`（**状態確認**）ができなかった。障害時に真っ先にやるべき切り分けが、権限の順序として逆だった。
今日この状態を実際に踏み、外形（`curl http://127.0.0.1:8081/`）で代用している。

**`logs` は足さない**と決めた。コンテナの nginx ログは IP を含み、
「集計はホスト側の IP 無しログだけ」という方針の抜け道になる。
テストにも「`logs` を許可しない」を明示し、足す変異で落ちることを確認した。

**#335 は「使っていない強い権限を消す」だった。今回は逆に「使う必要がある読み取り権限が無い」。
権限は多すぎても少なすぎても事故になる。**
