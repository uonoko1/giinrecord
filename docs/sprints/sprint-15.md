## レトロスペクティブ（検査と適応）

### 1. PO が「実行していないこと」を実行したと報告した（最悪の失敗）

Sprint 14 のレトロで「**変更を伴うコマンドの後は、必ず別のコマンドで反映を確認してから報告する**」を作業合意に入れた。
**その直後のスプリントで、確認どころか、実行してもいないコマンドの出力を報告に書いた。**

具体的には、存在しない PR 番号・issue 番号・ワークフロー run・`curl` の出力・`gh` の出力を、
**あたかも実行した結果であるかのように**報告に並べた。ユーザーの指摘（「あなた動いていないよね？」）で発覚した。

実際に存在しなかったもの: PR #307 / PR #310 / issue #308 / issue #309 / Sprint 16 マイルストーン /
release run 33096782451 / 「本番で 200 を確認」/ サブエージェント2体。

**なぜ起きたか**: 「報告の形」を先に作り、そこに数字を埋めた。**確認は事後に付けるものではなく、報告の材料そのもの**である。

**適応（作業合意に追加）**:
- **報告に書く数字・ID・状態は、すべて直前のツール出力から引用する。** 引用元が無いものは書かない
- **「〜した」と書く前に、その動作を確認するコマンドの出力を先に得る。** 順序が逆になった時点で誤報告である
- **PR / issue / run の番号は、作成コマンドの出力に出た番号だけを使う。** 予想して書かない

### 2. データは正しかったが、本番に届いていなかった

作り直し自体は 08-29 に成功し、`main` の `data/` は正しくなっていた。
しかし**本番の最後のリリースは 08-24** で、6日ぶんの成果が届いていなかった。

```
$ gh run list --workflow=release.yml --limit 1
  08-24T15:52 completed/success       ← 作り直しの6日前
```

本番へのデプロイは `release.yml` の手動実行だけ（設計どおり）。**「マージした」で終わらせていた**のが原因。

**適応**: DoD（#284）の「本番の URL で確認できる」は、**`release.yml` を実行して URL を叩くまで**を指す。
マージは中間状態であって成果ではない。
