## 状態は重なる

**1 つの枝が同時に複数の状態に当てはまります。** 実測（2026-09-07 時点）:

```
編集中: 1 ／ push 済み PR 無し: 0 ／ マージ済み: 60 ／ 残骸(24時間超): 2
```

**「push 済み PR 無し」が 0 なのは、該当する枝（`fix/505-probe-path-traversal`）が
31 時間前の更新なので「残骸」として先に数えられた**ためです。
**どちらも正しく、優先順位を決めているのは判定の順序**です。

**やること**: **除外（7・8）を先に判定し、そのあと稼働の信号（1〜4）を見る。**
逆にすると、マージ済みの枝がコミット時刻で「稼働中」に見えます（#607 で実際に踏んだ）。

**2026-09-08 に worktree を 84 本 → 3 本に整理しました**（#629）ので、
**上の実測値（マージ済み 60）はもう出ません。**
**「残骸」がほぼ消えたぶん、判定は単純になっています。**

## 「マージ済み」は squash コミットで判定する（2026-09-08 に確定）

**状態 7（マージ済み）の判定に、`origin/main..HEAD` と `git cherry` は使えません。**
**squash マージは枝を main の祖先にしないので、両方とも「未マージ」と答えます**（実測: 16 コミット全部に `+`）。

```sh
sha=$(gh pr view <PR番号> --json mergeCommit --jq .mergeCommit.oid)
git merge-base --is-ancestor "$sha" origin/main   # → 0 なら「マージ済み」で確定
```

**#535 で「`--is-ancestor` で代えようとしたのも誤りだった」と記録していますが、
あれは枝の HEAD を渡したからです。squash コミットに対しては正しく効きます。**
**PR MERGED の 72 本すべてで例外なく判定できました。**

**PR が無い枝には使えません。** そのときは:

| 状態 | 判定 |
|---|---|
| **HEAD 自体が main の祖先** | マージ済みと同じ（最も強い証明） |
| PR が `CLOSED` | **代わりにマージされた PR を探す**（#590 は #586 が上位互換だった） |
| PR が無い | **中身を読む**（機械的には決まらない）

## 数えないもの（動いていないのが正しい状態）

| 対象 | 理由 |
|---|---|
| **`blocked` ラベルの Issue** | **人間の作業待ち。** 誰も動けないのが正しい（#612） |
| **`draft` の PR** | **意図的な保留。** PO が「まだマージするな」と言っている |
| **マージ済みの枝の worktree** | 作業は終わっている。`.git` はマージ時に触られるので、時刻だけ見ると新しく見える |

## 実装で使っている判定

`scripts` には置いていません（監視はセッションごとに組み立てるため）。**考え方だけ固定します:**

1. **`blocked` を除いた `ready` の数**を数える（#612）
2. **稼働中の枝**は、次のどれかが **90 分以内**なら数える（#600 / #604 / #607）:
   - 未コミットの変更があるファイルの更新時刻
   - 直近のコミット時刻
   - worktree の `.git` の作成時刻
3. **ただし PR が `MERGED` / `CLOSED` なら数えない**（#607）
4. **「マージ可なのに放置」は 45 秒あけて 2 回確かめ、同じ集合のときだけ報せる**（#612）
