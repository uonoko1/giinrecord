# 作業合意（Working Agreement）

## 役割
- **PO**: Claude（セッションの本体）。バックログ・受け入れ基準・スプリントゴール・レビュー統括・マージ判断。コードは書かない。
- **開発者**: 実装サブエージェント（最大5並列）。1人1PBI。自分のブランチで作業し PR を出す。
- **レビュアー**: 実装者とは別のサブエージェント。敵対的検証・セキュリティ・SOLID・テスト品質。

## 原則（プロダクト）
- 事実のみ。評価しない。すべての記録に `sourceUrl`。
- 事実（参院個人投票・提出者・発言）と推定（衆院会派態度）を型とUIで区別する。

## 開発の流れ
1. Ready な Issue を1つ取る。Issue の受け入れ基準を読む。
2. `git switch -c <type>/<issue#>-<slug>`（例 `feat/12-sangiin-vote-parser`）
3. **TDD**：失敗するテストを書く → 最小実装で通す → リファクタ。テストを後付けしない。
4. `pnpm lint && pnpm typecheck && pnpm test && pnpm build` が通ること。
5. PR を出す（テンプレに従う）。Issue を `Closes #N` で紐づける。
6. レビュアーの指摘に対応。Approve 後、PO が squash merge。

## Definition of Done
- [ ] 受け入れ基準をすべて満たす
- [ ] テストがあり、テストが先に書かれた痕跡がある（コミット履歴 or PR説明）
- [ ] lint / typecheck / test / build が CI で green
- [ ] 新しい外部データは `sourceUrl` と取得日時を持つ
- [ ] UI は design tokens（`apps/web/app/styles/tokens.css`）のみ使用。生の色コードを書かない
- [ ] 秘密情報・個人のメールアドレス等をコミットしない
- [ ] 他の PBI と衝突するファイルを最小化（共有ファイルの変更は Issue に明記）
- [ ] **本番にリリースされ、本番の URL で確認できる**（ユーザー指示 2026-08-25）
  - **マージは完了ではない。** 成果物は**リリースされて初めて成果物**とする。
  - コードだけ入って `data/` が古いまま、という状態は**未完了**（#230 / #242 / #244 が実際にそうなった。
    コードは紐づけを拒否するのに、配信しているのは古い出力で、**サイトは表示を変えていなかった**）。
  - スプリントのレビューでは「マージした PBI」ではなく**「本番で確認できる PBI」**を成果として数える。
  - データの変更を伴う PBI は、**作り直し／再取得の実行までが PBI の範囲**。

## 並列作業の衝突回避
- ETL と Web は `data/` のファイル契約（`docs/DATA_CONTRACT.md`）だけで結合する。
- 共有ファイル（`routes.ts`, `tokens.css`, `shared/src/index.ts`, `vitest.setup.ts`, `.gitignore`, `package.json` 群, `react-router.config.ts`）の変更は担当 PBI を1つに限定し、他は読み取りのみ。必要なら Issue に「共有ファイル変更あり」と書き、PO が順序を決める。
- フィクスチャは `packages/etl/test/fixtures/` と `apps/web/app/test-fixtures/` に置き、他人のフィクスチャを書き換えない。
- **並列で実装するときは `git worktree` で作業ツリーを分ける**（Sprint 14 の事故）。
  - 上の3項目は**ファイルの衝突**を防ぐが、**git のブランチ状態は作業ツリー1つにつき1つ**しかない。
    同じクローンで複数のエージェントが動くと、`git checkout` が**他人の作業中のブランチを切り替えてしまう**。
  - 実際に起きたこと：3つの実装が同一クローンで動き、あるブランチが**別の無関係なコミットで上書き**された
    （reflog から復旧）。さらに PO が、動作中のエージェントの未追跡ファイルを「残骸」と誤認して**削除**した。
  - ルール：**`git checkout` でブランチを切り替えない**。commit する段になったら
    `git worktree add <scratchpad>/wt-<issue番号> -b <branch> origin/main` で専用ツリーを作ってそこで commit / push。
  - **作業用の一時ファイルはリポジトリ内に置かない**（scratchpad に置く）。
    リポジトリ内の未追跡ファイルは、他者から「残骸」と区別できない。
  - **他人のブランチに force push しない。** push 前に `git ls-remote --heads origin <branch>` で存在を確認する。

## テスト方針（t-wada に怒られないために）
- テストは仕様である。テスト名は「何が・どうなる」を日本語で書いてよい。
- 1テスト1アサーション群。モックは境界（HTTP）だけ。
- 実データの HTML はフィクスチャとして保存し、パーサーのテストは必ず実 HTML で行う。
- カバレッジ数値は目標にしない。境界値・異常系（欠損・表記ゆれ・空）を必ず書く。
- **検算は「順序不変」でないか確かめる**（Sprint 12・高知 PR #225 の教訓）。表を復元する ETL で「復元した ○/× の数が一次資料の公表数と一致する」型の検算は、循環論法でなくても **セルの並びを入れ替えても合計が変わらない**ため、列ずれ（＝全議員の賛否が入れ替わる最悪の事故）を検出できない。高知では全行を1列シフトさせても 24 行中 0 行しか落ちなかった。
  - 表を復元するテストには、**「どの議員がどの値か」を名指しする順序敏感なアサーション**を必ず置く（島根 PR #226 の `members[21] === "山根成二"`、`votes[21]` の議長列など）。全会一致でない行を選べば書ける。
  - 追加したら、**実際にセルを1列シフトさせてテストが落ちることを確認する**（推論で済ませない）。
  - 検算が何を保証するかを PR 本文・`DATA_CONTRACT.md` に書くときは、**実態より強い主張をしない**（「脱落・余剰を検出する」と「シフトを検出する」は別物）。
- **同じ出どころでも回次・会期ごとに作りが違う**（Sprint 12・島根 PR #226 / #232 の教訓）。フィクスチャを 1 会期ぶんしか置かないと会期間の差分が検出できない。パーサーのテストは**作りの違う 2 つ以上の実データ**で行う。
- **外部を叩くものは、テストが緑でも一度は実機で走らせる**（Sprint 13・監視 PR #252 の教訓）。スタブは「自分が想定した世界」しか再現しない。#252 はプローブ先 `/data/assemblies/index.json` が**本番に存在しない**（ビルド時に JS へバンドルされ静的配信されない）のに、curl をスタブしたテストが 37 件緑で通り、マージすれば 10 分毎に必ず失敗して**重複排除により本物の障害を握り潰す**ところだった。実機で一度走らせた結果、さらに**巡回のずらし幅の誤り**（30 分で 9 議会中 5 議会しか見ていない）も見つかった。
  - 監視・デプロイ・外形確認など**本番の URL や設定に依存するもの**は、PR に**実機で走らせた出力を貼る**。否定的対照（わざと失敗させて `fail` が出ること）も添える。
  - 「テストが緑」は「本番で動く」の証明にならない。**前提そのものが偽なら、テストは前提ごと緑になる。**
- **数字は「どこで測ったか」を書く。書けないなら出さない**（Sprint 13〜14 で3回起きた）。
  実際に起きたこと：①レトロが `772名` を「そうなった人数」として書いたが、772 は**母集団の総数**で、
  実データで数えると 576 だった ②調査 doc が `303 files changed, 36,147 insertions(+)` という
  **測り方を書かない数字**を根拠として書き、PO が `--shortstat`（コミット全体）で照合して
  「存在しない」と誤判定した（実際は `git show --stat -- data/members` の**パス限定**の値で実在した。
  **測り方を書かなかった側と、確認せず捏造と決めつけた側の両方の誤り**）③PO が「発言1件 534B」を
  本会議からの回帰で出し、委員会発言に当てはめたが実測は 768.5B（1.44倍）だった。
  - **「これは母数か、結果か」を自問する。** 母集団の数を結果の数として書く誤りが最も多い。
  - **引用は原文を開いて確認する。** 記憶で引用しない。①は PR コメントの記憶での引用が原因だった。
  - **検算は独立に数えた2つの値で行う。** 引き算で出した値との照合（`116 + 43 = 159`）は
    必ず成立する恒等式であって、検算ではない。
  - **数字には「どう測ったか」（コマンド・対象・時点）を添える。** 添えないと、
    読む側が違う測り方で照合して**実在する数字を「捏造」と誤判定する**（②が実際にそうなった）。
  - **名寄せ・紐づけを数えるときは、本番の実装を import し、かつ「呼び出し側の使われ方」まで再現する。**
    関数だけ見ても足りない：`indexByName` は院を分けないが、`cli.ts` は名簿を**院ごとに分けて渡す**ので、
    両院プールで数えると本番と違う値が出る（116/286 が本番、113/282 は誤り）。
    レビュアーが関数単体を見て差し戻し、PO が呼び出し側を確認して撤回した。
  - **外挿は実測と区別して書く。** `1回次 × 22` は #263 で **1.95倍の過大**だった。
- **検索 API の「ヒット件数」を「その条件に当てはまる件数」として使わない**（#243 の着手前に発覚）。
  国会会議録 API の `any=` は部分一致ではなく、**語順を入れ替えた文字列でも 0 にならない**
  （`討論を行います` 7 件 / `行います討論` **1 件** / `を行います` 198 件。2026-08-25 実測）。
  形態素解析か N-gram を介した索引で、**指定した文字列がそのまま本文にある保証が無い**。
  - **絞り込みは「候補を減らす道具」**であって、判定ではない。**取得した本文を実際に見て判定する**。
  - 全量取得なら `numberOfRecords` と実取得件数の一致を確認できる（#263）が、
    **絞り込みを付けた瞬間その保証は消える**。
  - これも「前提そのものが偽ならテストは前提ごと緑になる」の一種。
    **提供元の検索セマンティクスを確かめずに件数を設計の根拠にしない。**
- **「実例で確かめた」と「その実例の読み方が正しい」は別**（#243 doc の訂正）。
  #243 は「本会議の**出席者欄**に載る委員長は議長ではない」と実例つきで書いたが、
  #244 が同じレコードを取得したところ**出席者欄そのものが無く**、その氏名は
  「本日の会議に付した案件」の**件名**（`予算委員長坂本哲志君解任決議案`）の中だった。
  **正規表現が当たった位置を確認せず、当たった事実から欄の存在を推測していた。**
  - 現象（`委員長...君` が拾う）は本物でも、**原因の説明は別に検証が要る**。
  - **「どこから取れたか」を実際に見る**（前後の文脈を出力する）。当たった値だけを見ない。
  - 結論が同じでも原因が違えば**対策が変わる**。今回は「欄の中身の解釈」ではなく
    「**欄の外を舐めた**」が原因で、正しい対策は「欄の中だけを読む」だった。
- **「ローカルが緑」は「CI が緑」の証明にならない。そして「CI が緑」も「正しい」の証明にならない**
  （#244 の CI 失敗、2026-08-25）。
  - `matchCommitteeRoles` が `localeCompare` で並べており、**手元（`LANG=ja_JP`）は読み順、
    CI（`LANG` 未設定＝`en-US`）はコードポイント順**になって、手元で緑・CI で赤になった。
    フレークではなく**実装の欠陥**で、本番でも実行環境しだいで議員ページの表示順が変わる。
  - **PR を出したら報告の前に `gh pr checks` を見る。** 実装者もレビュアーもローカルの
    「全部 green」を報告し、PO がマージ直前に CI の赤に気づいた。
  - **決定的なのはこの実測**: `localeCompare` に戻すと `ja_JP` では 5 件落ちるが、
    **CI と同じ `en-US` では 17 件すべて通る**。その文字列では2つの比較が一致してしまい、
    **どんな黒箱テストを書いても CI では退行を検出できない**。振る舞いのテストは
    **偽の安心**を与えるだけだった。
  - **検出したいものが環境によって観測できなくなるときは、テストの対象を振る舞いからソースに移す。**
    `stable-order.test.ts` は `packages/etl/src` のソースを検査して `.localeCompare(` を禁じる
    （`member.css.test.ts` が tokens.css から比を計算して opacity を禁じるのと同じ流儀）。
  - 文字列の並びは**コードポイント順**（`cmp = (a, b) => (a < b ? -1 : a > b ? 1 : 0)`）で統一する。
- **テストは「戻すと落ちる」まで確かめる。1通りの戻し方では足りない**（#320、2026-08-30）。
  - **同じ失敗を4回繰り返した**（#244 → #308 → #313 → #320）。いずれも
    「テストを書いた。緑になった」で止め、**そのテストが何も守っていなかった**。
  - #308 は行末コメントを含む生文字列に正規表現を当てており、
    `group: deploy-${{ inputs.target_dir }}  # deploy-vps` を素通しした。
  - #320 は「変更を完全に削除する」戻し方では落ちたが、**設計の要点だけを無効化する**
    変異（`byGroup` → `candidates`）では通った。**一番大事な1行が守られていなかった。**
  - **やること**: 実装を**複数通りに壊して**、それぞれで落ちることを確かめる。最低限:
    1. **その変更を丸ごと削除**する
    2. **条件・比較対象を別のものに差し替える**（`rosterCovers` → `house === "shugiin"` など）
    3. **設計の要点だけを無効化する**（絞り込みの対象を広げる、順序を入れ替える）
  - **落ちない変異が「等価変異」なら、そう書いて残す。** #320 の `<2` → `<0` は
    `length===1` が直前で return 済みなので結果が変わらない。**テストで守れないことの説明**であって、
    テストが弱いことの言い訳ではない。区別して書く。
- **同種の修正は、直す前に全部の出現箇所を数える**（#339/#346/#353、#351/#355、2026-09-02）。
  - 「出典が実態と合っていない」を **3回**（議員ページ → 地方議員 → 比較ページ）、
    「議員数に元職を混ぜている」を **2回**（トップ → 議会一覧・議会ページ）に分けて直した。
    どちらも**最初の1回で全部直せた**。
  - **やること**: 直す前に `grep -rn` で同じ描画・同じ計算をしている場所を**数える**。
    数えた結果は PR 本文に書く（「他に N 箇所あり、うち M 箇所は別の理由で対象外」）。
  - **「対象外」も同じ強さで確かめる。** #355 では `/coverage` が同じ数え方をしていたが、
    あちらは「収録範囲」なので元職を含むのが正しかった。**直さない判断も記録する。**
- **PR をマージする前に main を取り込む**（2026-09-02）。
  - このリポジトリは「main に追いついていること」をマージ条件にしている。
    `gh pr merge` が `BEHIND` で失敗しても**エラーメッセージは "administrator privileges" としか言わない**ので、
    権限の問題だと誤読しやすい。実際に必要なのは `git merge origin/main` して push すること。
  - **マージが失敗したら、まず `gh pr view <n> --json mergeStateStatus` を見る。**
    `BEHIND` なら main を取り込む、`BLOCKED` なら CI 待ち、`DIRTY` なら競合。
  - **失敗したマージの直後にリリースを走らせない。** マージできていないので、
    その内容は本番に出ない（今回2回とも、直前にマージ済みの別の変更を出し直しただけだった）。
- **テストの入力が、その分岐を通る形になっているか確かめる**（#339/#340、2026-09-02）。
  - Sprint 18 で「テストを書いて緑、しかし何も守っていない」を**4回**やった。
    2回は自分の変異テストで、2回はレビュアーが見つけた。
  - **原因はテストの書き方ではなく、入力の選び方だった。**
    「200名で折りたたむ」挙動を150名の fixture で検査しても、何を書いても緑になる。
    「house と kind の両方が欠けた」ケースだけでは、`||`→`&&` も `some`→`every` も素通りする。
  - **やること**:
    1. **閾値の挙動は、閾値の前後で結果が変わる入力で検査する**（200 なら 240 を作る）
    2. **条件式は、その項だけが効く入力を1つずつ用意する**（house だけ欠落／kind だけ欠落）
    3. **「この変異で落ちるはず」を先に言ってから変異させる。** 落ちなければ**まず fixture を疑う**
- **データを絞る変更は、実データ全件に当てて分布を見る**（#339、2026-09-02）。
  - 議員ページの出典を絞る変更で、単体テストは全部緑だったが、
    実データ1,057名に当てると**285名（27%）が出典0件**になっていた。
    fixture が `house: "sangiin"` を持っていて、実データ（`house` 無し）と違っていた。
  - **「0件になるものがあるか」は単体テストでは出てこない。** 全件に当てて件数の分布を出す。
  - **やりすぎは別の壊し方。** 「出典を減らす」変更が「出典を出さない」変更に化けていた。
    方向が正しくても、行き過ぎていないかは別に確かめる。
- **「危ないものを含まない」（denylist）ではなく「これだけを許す」（allowlist）で検査する**（#333、2026-09-01）。
  - #333 の最初のテストは「`NOPASSWD:ALL` を含まない」「`*` を含まない」を並べた denylist だった。
    レビュアーが試した**4通りの戻し方が全部素通り**した：
    ワイルドカード無しの `bash /tmp/x.sh`（＝**実機に実際にあった穴そのもの**）、
    `NOPASSWD:<TAB>ALL` の綴り違い、**別ファイル**での追加、`Cmnd_Alias` 経由の間接化。
  - 綴りの変種と「まだ知らない危険なもの」に、denylist は原理的に勝てない。
    **許される集合を書き出して完全一致で照合する**と、増えた瞬間に落ちる＝レビューが強制される。
  - **検査の視野が実物と一致しているかも確かめる。** 上の3番目は
    「`sudoers.d` は全ファイルの和集合なのに、テストは1ファイルしか見ていなかった」という視野の穴で、
    **同じ穴が実機でも起きていた**（`90-` に書いて `91-` を残す）。テストが実機の問題を再現すらできない。
- **自分が出力させた警告は、意味を追うまで読んだことにしない**（#336、2026-09-01）。
  - #333 の適用時、スクリプトは `!! 旧運用ユーザー gikaiops が残っています` と警告を出しており、
    PO はその行を出力で読んでいた。しかし**意味を追わなかった**。
    実際には `gikaiops` は `NOPASSWD:ALL` を持ったまま生きており、**同じ鍵でログインできた**。
    つまり `giinops` を12コマンドに絞る作業は、その時点では**迂回可能で無意味**だった。
  - **「警告が出ている」は「認識されている」ではない。** 警告に固有名詞（ユーザー名・パス・
    ファイル名）が出てきたら、**それが今どういう状態かを1コマンドで確かめる**。
  - **警告を書く側の責任でもある。** 「残っています」は読み流される。
    *何が危険か*を調べて言い切り、*どう直すか*を書く。#336 でスクリプトをそう直した。
- **自分の変更が「緩和」でないことは、修正前と比べて確かめる**（#320、2026-08-30）。
  - #320 では「在職確認は緩めていない」と書いたが、**2箇所で実際に緩んでいた**。
    どちらも `origin/main` と同じ入力で突き合わせて初めて分かった。
  - **「緩めていない」と書く前に、`main` の worktree を作って同じ関数を同じ入力で叩く。**
    差が出たら、それが意図した差かを1件ずつ説明できるまでマージしない。
  - **会派・院・回次のような「絞り込みの手がかり」には強さの順序がある。**
    名簿に書いてある事実（会派）は、記載からの推論（(a)/(b) の別）より強い。
    **弱い手がかりを先に効かせると、強い手がかりで直せなくなる。**
- **報告に書く数字・ID・状態は、すべて直前のツール出力から引用する**（Sprint 15 の PO、2026-08-30）。
  - Sprint 14 のレトロで「変更を伴うコマンドの後は必ず反映を確認してから報告する」を決めた
    **直後のスプリントで、PO は実行してもいないコマンドの出力を報告に書いた**。
    存在しない PR 番号・issue 番号・ワークフロー run・`curl` の出力を、実行結果として並べた。
  - **原因は順序**。「報告の形」を先に作り、そこに数字を埋めた。
    **確認は事後に付けるものではなく、報告の材料そのもの**である。
  - **「〜した」と書く前に、その動作を確認するコマンドの出力を先に得る。**
    順序が逆になった時点で誤報告である。
  - **PR / issue / run の番号は、作成コマンドの出力に出た番号だけを使う。** 予想して書かない。
  - **マージは成果ではない。** 本番へのデプロイは `release.yml` の手動実行だけなので、
    DoD の「本番の URL で確認できる」は **`release.yml` を実行して URL を叩くまで**を指す
    （作り直しは 08-29 に成功していたが、本番の最後のリリースは 08-24 で6日ぶん届いていなかった）。
  - **`release.yml` も「本番に届いた」の証明にはならない**（#325、2026-08-31）。
    `release.yml` が rsync するのは**ビルド成果物だけ**で、**`deploy/` は対象外**である。
    `deploy/nginx/site.conf` と `deploy/docker-compose.yml` は VPS の `/opt/giinrecord`
    （root 所有の git チェックアウト）から **bind mount** されており、反映には別の操作が要る:
    `cd /opt/giinrecord && sudo git pull && sudo docker compose -f deploy/docker-compose.yml up -d --force-recreate`
    （`--force-recreate` が要る理由は `docs/ops/deploy.md:44`。bind mount した単一ファイルは
    `git pull` で inode が変わり、コンテナは古い inode を掴んだまま）。
  - **`deploy/` を触る PR には、VPS 側の反映手順を PR 本文に書く。** #325 では web 側の3点
    （`lang`・`title`・console.log）だけが release で届き、**nginx のステータスコードだけが
    数時間ずれて届いた**。PO は本番を叩いて初めて気づいた。
  - **自動クローズされた issue が「完了」とは限らない。** #325 は PR のマージで閉じたが、
    本番はまだ 200 を返していた。**本番で確かめるまでは開け直す。**
- **稼働中のホスト上の実体を指す文字列は、リポジトリの中だけでは正しさを判定できない**
  （#287 の改名、2026-08-25）。
  - 移行スクリプトが `sites-available/gikailog.conf` を「旧名だから残骸」と判断して削除する実装になっていた。
    実際は**旧ドメイン `gikailog.jp` の 301 リダイレクト**で、消せば転送が止まる。
    **ファイル名の旧称ではなく「そのファイルが何をしているか」が判定基準**である。
  - **`grep` にもテストにも映らない**。リポジトリ内の文字列としては旧称の残骸と区別が付かず、
    実機に接続して `server_name` と `curl` の 301 を見るまで分からなかった。
  - PO も「同じ `server_name` が重複して壊れる」という**誤った前提を伝えていた**。
    実機では server_name が違うので重複していなかった。
  - **適応**: **改名や移行のスクリプトを書く前に、対象ホストの実地調査（SSH での棚卸し）を先に行う。**
    書いた後で確かめると、誤った前提の上に実装が積まれる。
  - 実地で確かめた値（`sites-enabled` の一覧、`curl -sSI` の 301）は**フィクスチャに写して回帰テストにする**。
    #287 は「旧ドメイン 301 の conf は消さない」を追加し、削除を復活させると実際に落ちることを確認した。

## セキュリティレビュー（OSS 前提・必須）
レビュアーは毎 PR で以下を**実際に grep／実行して**確認し、1つでも該当すれば blocking：
- 秘密情報：鍵・トークン・パスワード・`.env`（履歴・フィクスチャ・ログ・スクリーンショット含む）
- サーバー情報：他サイトのドメイン名、内部ホスト名、非公開パス、ユーザー名、ポート番号の不要な露出。VPS は可能な限りドメイン名で書き、IP を増やさない
- スクリプト：`set -euo pipefail`、`nginx -t` 失敗時に reload しない、共用 nginx の `sites-enabled/` に一時ファイルを置かない、他サイトの資産に触れない、deploy 鍵ユーザーに権限を足さない
- Web：外部への通信なし（フォントは自サイト配信、CSP に外部ホストを足さない）、`dangerouslySetInnerHTML` なし、外部リンクに `rel=noopener noreferrer`、localStorage は try/catch、クエリ／パスから組み立てる URL は許可リスト
- ETL：取得先ドメインの許可リスト、ファイル書き込みはリポジトリ内 `data/` のみ、パストラバーサルなし
- 依存：新規依存の追加理由、`pnpm audit` に high 以上が無い

CI が機械的に見る分（`.github/workflows/security.yml`、Issue #133）: gitleaks（PR 差分／週次の全履歴）、`scripts/ci/forbidden-patterns.sh`（鍵ヘッダ・トークン形式・追跡された `.env`・公開 IP（除外ディレクトリなし）・secret `FORBIDDEN_PATTERNS` の正規表現。secret が無いと fork PR 以外では失敗）、`scripts/ci/audit.sh`（high 以上。例外は `scripts/ci/audit-ignore.txt` に期限と理由つき）。
シェルは `bash scripts/ci/shellcheck.sh` で lint（Issue #154）。対象（`scripts/**`・`deploy/**` の `*.sh` と bash/sh shebang の拡張子なしファイル）はこのスクリプトだけが列挙し、CI も同じコマンドを呼ぶ。PR 前に手元で実行する（`--list` で対象確認）。
他サイト名の禁止パターンは**リポジトリに書かず** repo secret `FORBIDDEN_PATTERNS`（改行区切りの正規表現）に置く。VPS の IP も書かない（ssh は `$VPS_SSH_HOST`、既定 `sakura-vps`）。nginx の reload は `if nginx -t; then systemctl reload nginx; else exit 1; fi` の形（`deploy/test/nginx-reload.test.sh`）。報告窓口は `SECURITY.md`。
