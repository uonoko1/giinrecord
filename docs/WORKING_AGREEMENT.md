# 作業合意（Working Agreement）

## 役割
- **PO**: Claude（セッションの本体）。バックログ・受け入れ基準・スプリントゴール・レビュー統括・マージ判断。コードは書かない。
- **開発者**: 実装サブエージェント（最大5並列）。1人1PBI。自分のブランチで作業し PR を出す。
- **レビュアー**: 実装者とは別のサブエージェント。敵対的検証・セキュリティ・SOLID・テスト品質。

## 原則（プロダクト）
- 事実のみ。評価しない。すべての記録に `sourceUrl`。
- 事実（参院個人投票・提出者・発言）と推定（衆院会派態度）を型とUIで区別する。
- **氏名は「取れた文字列」を信じない。** PDF から読んだ氏名は、**元の氏名と違うことがある**——
  **しかも利用者からは検出できない**（#569 / #529 / #617 / #670 で 4 通りの機序を実測）:
  | 機序 | 実例 | 文字数で気づけるか | かなとの比（#632）で気づけるか | 実際に守っているもの |
  |---|---|:-:|:-:|---|
  | **異体字セレクタで幅 0**、列がずれて 1 文字落ちる | 青森 `櫛引ユキ子` → `引 ユキ子` | **気づける** | **気づけない**（#771） | `lossyNameMatches`（#750 / **#778 で 11 県すべて**） |
  | **名簿と PDF で字体が違う**（NFC/NFKC でも一致しない） | 青森 `寬`(U+5BEC) / `寛`(U+5BDB) | 気づけない（数は同じ） | **気づけない**（#771） | `sourceConflict`（#711） |
  | **フォントのサブセットに BMP 外文字が無く、描画命令ごと欠落** | 大分 `𠮷村哲彦` → `村哲彦` | **気づけない**（最初から無い） | **気づけない**（#771） | `lossyNameMatches`（#750 / **#778 で 11 県すべて**） |
  | **別の字に化ける（欠落ではなく置換）** | 滋賀 `辻` → `□`(U+25A1)（#670） | **気づけない**（字数が同じ） | **気づけない**（字数が同じ） | `sourceConflict`（#711） |
  **`lossyNameMatches` は 2026-09-13 まで 11 県中 3 県（青森・秋田・佐賀）にしか無かった**——
  **#778 が `buildLocalAssembly` に移し、11 県すべてが通る 1 か所で数えるようにした。**
  **移した時点で、奈良に 2 件（`西川`→`西川 均` 125 票 ／ `髙清友`→`芦高 清友` 37 票）が出た**
  ——**`nara/rollcalls.ts` の docblock は知っていたのに、公表データのどこにも出ていなかった。**
  **鳥取だけは鳴らせない**——**PDF が `○○議員`（姓だけ）なので、名の側の欠落は誰にも見えない。**
  **「鳴らない」ではなく「鳴らせない」**（#778 で測った事実。守りがあるように数えない）。

  **4 機序すべてが PDF 側で起きる。** **`kanaNameRatioExceeds`（#632）はどれも捕まえない**——
  **見ているのは名簿の行（`m.name, m.kana`）だけで、PDF から読んだ氏名を一度も見ないからである**（#771、2026-09-13）。
  **この表は 2026-09-13 まで 1 つ目を「気づける」、3 つ目を「短い氏名だけ気づける」と書いていたが、
  それは「#632 が PDF 側の氏名に掛かる」という誤った前提に立っていた。**
  **名簿は無傷なので比は動かない。** **#632 が守るのは「名簿の HTML 自体を読み違えた」場合だけである。**
  - **「氏名は名簿の PDF から、かなは名簿の HTML から」という前提も事実ではなかった**——
    **名簿を作る 13 モジュール（地方 11 県 + 衆院 + 参院）のうち、氏名を PDF から取るものは 0。**
    **衆参とも氏名とかなは同じ `<tr>` の隣り合う `<td>` から来る**ので、**国会でも「独立した 2 つの値」ではない。**
  - **閾値を下げても解決しない**（見ている対象が違うだけ。偽陽性が増える）。
    **1 文字欠落を名簿側に当てた実測でも 4,554 通り中 19 通り（0.42%）しか鳴らない**
    （国会 3,106 通り中 14 / 地方 1,448 通り中 5。`packages/etl/test/kana-ratio-provenance.test.ts`）。
    **閾値を 1.7 まで下げれば 89.96% 鳴るようになるが、同時に壊れていない本物の議員
    1,225 名中 739 名（60.3%）が鳴る**——**守りが増えるのではなく、全部鳴って誰も見なくなる。**

  **3 つ目と 4 つ目が重い。**
  **3 つ目**: `ToUnicode` の bfchar が全部 4 桁で、**サロゲートペアが 1 件も無い**ため、
  **テキスト層にその文字が存在しない**。**同じ議会でも会期によってフォントが違い、片方だけ落ちる。**
  **4 つ目（2026-09-09、#670 で実測）**: **字数が変わらないので、既存の守りが全部無力である。**
  **`ITAIJI`（`name-match.ts`）は `□` を持たないので畳んでも戻らず、
  `kanaNameRatioExceeds`（#632）は比が変わらない**（`辻内 裕也` も `□内 裕也` も 4 文字 / かな 7 拍 = 1.75）。
  **同じ PDF の中で `隆` が U+F9DC と U+9686 で混在する例もある**（#670、滋賀）——
  **こちらは「同じ字の別コードポイント」なので `ITAIJI` を足せば畳めるが、`□` は元の字が失われている。**
  - **やること**: **名簿側を「BMP 外文字を含むか」で先に分類し、含む議員は突き合わせ方を変える。**
    **突き合わせに失敗した氏名は `unmatched.json` に落とし、黙って捨てない**（#529）。
    **「記録が出ない」と「別人の記録が出る」は重さが違う。迷ったら出さない側に倒す**（#569）。
    - **PO 自身が、氏名の一致だけで数えて捕まった**（2026-09-13、#796 → PR #803）。
      **「`unmatched` の 55 人中 42 人が名簿に居る」と起票したが、実測は 41 人だった。**
      **差の 1 人（`鈴木敦`、5 件）に一致するのは `house` を持たない宮城県亘理町の議員で、
      衆院の発言者と同じ人だとは言えない。**
      **担当者は「同一人物とは書いていない」と明記した**——**正しい。**
      - **`nameText` の一致で数えることは、同一人物だと仮定することである。**
        **「紐づけていない、数えただけだ」は通らない**——**数えた時点で紐づけている。**
      - **やること**: **氏名で突き合わせるときは、議会・院・会期まで見る。**
        **見ないなら「氏名が一致する行が N 件」と書く**（**「N 人が名簿に居る」と書かない**）。

### 実際に起きる 4 機序では、別人に決まる例は 1 件も無い（#722、2026-09-09）

**#711 が「名簿の氏名を 1 文字、同じ議会に実在する別の漢字に差し替えると 16 件が別人に決まる」
と測った**（母数 120,010）。**その 16 件に機序があるかを、上の 4 機序それぞれで測り直した。**

**測り方**: 地方議員 285 名（7 県）の氏名キーに各機序の変化を当て、その県の突合規則
（鳥取は `matchBySurnamePrefix`、他 6 県は `matchBySubsequence`）で引き直す。

| 機序 | 母数 | 本人 | **別人** | 決められない |
|---|---|---|---|---|
| **1/3. 1 文字欠落**（異体字セレクタ・BMP 外の欠落） | 1,123 | 1,010 | **0** | 113 |
| **2. 字体違い**（`高/髙` `崎/﨑` `徳/德` `辺/邊/邉` `沢/澤` `寛/寬` の既知の対） | 31 | 22 | **0** | 9 |
| **4. 別の字に化ける**（`□` `◇` `■` `?` `�` の 5 通り） | 各 1,123 | 0 | **0** | 各 1,123（**全件 `brokenGlyph` 判定**） |

**実データで起こりうる変化では、別人に決まらない。**
**機序 4 は 1,123 件すべてが `brokenGlyph` として落ちる**（#680 の守りが効いている）。

#### **16 件が要求するのは「機序の無い置換」である**

**16 件の (元の字 → 置換後の字) を 1 組ずつ調べた。16 組とも NFC でも NFKC でも同一にならず、
`ITAIJI` でも畳まれない**（`啓`→`二`、`喜`→`津`、`美`→`雅` など。**異体字でも似た字形でもない**）。

**16 件の内訳は 2 つの構造だけである:**

- **完全一致 6 件**: **実在する 2 人が最初から 1 文字違い**
  （宮城 `高橋 克也`/`高橋 宗也`、三重 `喜田 健児`/`津田 健児`、高知 `西森 美和`/`西森 雅和`）。
  **PDF 側が壊れなくても、正しく読めた氏名がそのまま相手に当たる。**
- **部分列 10 件**: **名が 1 文字の議員**（宮城 `高橋 啓`、奈良 `川口 信`、島根 `中村絢`、徳島 `岡田 晋`）が、
  **より長い同姓の氏名の部分列になる**（`高橋啓` → `高橋克` は `高橋 克也` の部分列）。
  **キーが 3 字以下の議員は 285 名中 44 名。**

#### **#711 の守りは、この 16 件には届いていない**（実測）

**`unmatchedReason` は 16 件すべてを `sourceConflict` と判定する**（`conflictingRosterNames` も相手を返す）。
**だが `local-assemblies.ts:204` はそれを `unmatched` に落ちたものにしか呼ばない。**
**16 件は `matchBySubsequence` が先に別人を返すので `unmatched` に入らず、判定は一度も走らない。**

**これは #711 の欠陥ではない**——**#711 は「寄せられなかった氏名に理由を付ける」PBI であり、
「寄ってしまった氏名」は範囲外だった。**

- **やること**: **この 16 件を直すなら、`matchBySubsequence` が返す前に見る必要がある。**
  **ただし今は実データで起こりうる機序が無いので、直す根拠が無い**——
  **「起こりうる変化を測ったら 0 件だった」までが今の実測である。**
  **名簿が変わって「1 文字違いの現職」が増えたら、この 16 件は増える。**

### 「落とす」だけでは、落ちた理由が消える（#680、2026-09-09）
**上の 4 つ目（置換）を滋賀の全 147 本で数えたら、`□` は 2 本 3 個・議員 1 名だけだった。**
**それでも「何もしない」を採れなかったのは、数の大小ではなく `unmatched.json` の読まれ方のため。**

**`□正隆` は `matchByExact` も `matchBySubsequence` も `memberId: ""` / `candidates: []` を返す**（実測）。
**「PDF の字が壊れている」と「名簿にいない議員」が、出力の上で 1 バイトも違わない。**
**運用者は前者を後者と読み、直すべきでない名簿を直しにいく。**
**落とす判断（#569）は正しい。足りないのは「なぜ落ちたか」を書くこと**（`LocalUnmatchedName.reason`）。

**同じ会期の 2 本で結果が割れた**（`Kg900` は `辻󠄀` が読めて `Kg907` は `□`）。
**「この会期は壊れている」という単位で切り分けられない以上、「今は 1 名だけ」は「次も 1 名」を意味しない。**

**壊れている字を名指しする守り（denylist）にしない。**
**`□` だけを見る守りは、次に `◇` で化けた PDF に対して無力。**
**「名前になれる文字」の側を列挙し（allowlist）、そこから外れたら壊れているとする。**
**その allowlist は実データで裏を取る**——本番 1,057 名・45,054 票の氏名に出る文字は
**漢字・かな・`々`・空白・異体字セレクタだけで、記号は 1 文字も無い**（実測。偽陽性 0 件）。
**そして「元の字が何だったか」は返さない。**`□` を `辻` と読むのは推定で、別人の記録を作る側（#569／#674）。

**「記録した」は「見えるようにした」ではない**（2026-09-13。**1 日で 3 回出た**）。

| # | **知っていた場所** | **出ていなかった場所** |
|---|---|---|
| **#778** | `nara/rollcalls.ts` の docblock（**字が落ちたまま寄せていることを知っていた**） | **公表データのどこにも出ていなかった** |
| **#785** | GitHub の secret scanning（**本物の漏洩を検出していた**） | **誰も読んでいなかった**（**21 日**） |
| **#800** | `data/assemblies/pref-29/meta.json`（**#778 を直した結果**） | **web が一切参照せず、`/data/` でも配信されない** |

**3 つ目が重要である**——**1 つ目を直した結果、一段先で同じ形になった。**
**「公表データに出す」を実装したら、今度は「公表データには入ったが、配信も表示もされない」になった。**

- **やること**: **記録を足したら、「これは誰がどこで見るのか」を 1 行で言えるか確かめる。**
  **言えないなら、まだ終わっていない。**
- **「`data/` に入れた」で止めない。** このリポジトリでは **`data/` 配下でも配信されるものとされないものがある**
  （**`OPS_DATA_FILES` の 5 本と、`import.meta.glob` がバンドルするものだけ**）。
  **地方の `meta.json` はどちらでもない**——**`git clone` した人しか読めない。**
- **見ていない検出器は、無い検出器と同じである**（#785 の担当者の言葉）。
  **これは我々の出力にも当てはまる。**

## 原則（作業）
**この文書の教訓は、ほぼすべて「確かめられるのに確かめなかった」の実例である。**
2026-09-06 の 1 日で PO が捕まった誤りは、4 つの型に収まった:

| 型 | 実例 | 確かめる手 |
|---|---|---|
| **数字の測り方を書かない**（詳細は「**数字は「どこで測ったか」を書く**」の項） | 「3.6–4.9s」（負荷を書かず、別の人は 27–55s）／「472 件」（部分実行の値。実測 1,182）／「woff2 520 個」（実測 371） | **測ったコマンドを添える** |
| **実装や一次資料を読まずに書く** | shellcheck の警告を要約して嘘を作った（#525、取り下げ）／自分が薦めたコマンドが**実装では意図的に退けられていた**（#535） | **`grep` 1 回。1 行叩く** |
| **diff の見た目で判断する** | 「他人の変更が消える」（**三方マージは落とさない**。最小例で再現可）／**CI の緑バッジで判断した**（#559 自身が踏んだ——その緑は**16 分前の main と比べた緑**だった）／**`git diff origin/main` を merge-base と取り違えた**（2026-09-13。**PO が担当者 2 人に「あなたの枝は他人の作業を消す」と誤って警告した**） | **実際にマージして数える**／**CI はいつの何と比べた緑か見る**／**`git merge-base` を取ってから比べる** |
| **出力を確かめない** | `gh issue comment` の終了コードだけ見て、**投稿された中身を読まなかった**（バッククォートが展開されて 2 箇所欠けた）／追記が**既存の文を割った**のに diff で気づかなかった（#553） | **叩いた結果を目で読む** |

- **4 つとも「1 コマンドで確かめられること」だった。** 時間が無くて省いたのではなく、
  **確かめる必要があると思わなかった**のが原因である。
  （**「1 分」と書いたのは誇張だった**——`pnpm --filter web test` は実測 **100 秒**。
  **測り方を書かずに数字を出す**という、この表の 1 行目そのものを踏んだ。）
  - **`git diff <branch>` は merge-base とは比べない**（2026-09-13）。**PO は `git diff --stat origin/main` の「1,196 行削除・14 ファイル」を見て、担当者の枝が #799 と #798 を消していると判断し、2 人に警告を送った。**
    **正しくは `git merge-base` を取ってから比べる。実測すると 2 ファイル・282 行の追加だった。**
    - **そして `scripts/ci/stale-base.sh` が、まさにこの形（古い main から切った枝が main の得た行を消す）を検出するために #536 で作られており、CI が必ず見る。**
      **走らせたら `ok` と言った。** **手で確かめる必要すら無く、手で確かめた方法が間違っていた。**
    - **やること**: **枝の差分を見るときは `git merge-base` を取る。**
      **「他人の作業が消える」と思ったら、まず `bash scripts/ci/stale-base.sh` を走らせる**——**そのために在る。**
    - **ただし `git reset --soft origin/main` は本当に巻き戻す**（2026-09-13、#800 の担当者の申告）。
      **その担当者は squash しようとして「まさに PO の警告が指していた docs を巻き戻す差分が実際に出た」。**
      **`git reset --soft $(git merge-base origin/main HEAD)` でやり直し、
      `git diff --cached --stat` が自分のファイルだけになることを確認してからコミットした。**
      - **読むときの `git diff origin/main` は幻を見せるが、書くときの `reset --soft origin/main` は本当に消す。**
        **同じ間違いが、読むと無害・書くと有害という形で 2 つある。**
    - **被害を数えるときは `--numstat` で全ファイルを見る**（2026-09-14。**PO と担当者が独立に同じ間違いをした**）。
      **PO は #832 の巻き戻しを「17 行」と報告した**——**`docs/WORKING_AGREEMENT.md` しか見ていなかった。**
      **別の PR の衝突解決中に偶然見つけたので、そのファイルだけを開いていた。**
      **`git show <commit> --numstat` で全ファイルを数えたら 3 ファイル 286 行だった**（**16.8 倍**）。
      **#836 の担当者も同じ間違いをして、同じように訂正した**（「最初 `docs/` だけを見て『#832 = 17 行』と書いていました」）。
      - **やること**: **「何行消えたか」を言う前に `git show <commit> --numstat` を叩く。**
        **見つけた経緯（どのファイルを開いていたか）が、そのまま数える範囲になってしまう。**
      - **そして「消えた」と言う前に、探し方が正しいかを確かめる**——
        **PO は #825 の節を `#825` で grep して「消えている」と判断したが、
        見出しの実際の番号は `#811` だった**（#839 の担当者が指摘）。
        **別の 3 本（#775 / #777 / #818）も「消えた」と読み違え、逐語で確かめ直したら全部在った。**
  - **「測る候補」に、1 コマンドで確かめられることを入れない**（2026-09-13、#812。**PO が同じ日に 2 回踏んだ**）。
    **PO は CI の詰まりを測る PBI を起票し、その「測ること」の一項目に
    「`concurrency` グループが効いているか、`cancel-in-progress` がどうなっているか読むこと」と書いた。**
    **自分で `grep` 1 回叩いたら、`ci.yml` の 6 行目に書いてあった**（`cancel-in-progress: true`）。
    - **そのうえ、測る前の推測も外れていた**——**「cancelled 15 件」を浪費のように書いたが、
      それは守りが働いた回数だった。** **訂正を Issue に足した。**
    - **PBI に「調べること」を書くのは、担当者に時間を使わせる判断である。**
      **1 コマンドで済むことを渡すのは、上の表の「実装や一次資料を読まずに書く」と同じ形。**
    - **やること**: **PBI を書くとき、項目ごとに「これは自分で 1 コマンドで確かめられるか」を見る。**
      **確かめられるなら、確かめてから書く**——**結果を Issue に書けば、担当者はそこから始められる。**
- **やること**: **書く前に「これは確かめたか、それとも確かめずに書いているか」を自問する。**
  **確かめていないなら、確かめるか、確かめていないと書く。**
- **「確かめていない」と書くのは弱さではない。** #546 の担当者は PR 本文に
  **「PAT を置いた後の成功経路は、実機の Actions では未確認です」**と書いた（**原文が PR に残っている**）。
  そのレビュアーも「自分では再現できていない」と保留し、**別の源（GitHub の JSON Schema）で埋めた**。
  **書かずに断定するほうが、はるかに高くつく。**
  - **ただしレビュアーの言葉は GitHub に残っていない**（#546 の review / comment はいずれも 0 件）。
    **PO はそれを引用符つきで書いて捕まった**——**引用は原文を開いて確認する。記憶で引用しない**（既出）。

## 開発の流れ
1. Ready な Issue を1つ取る。Issue の受け入れ基準を読む。
2. `git switch -c <type>/<issue#>-<slug>`（例 `feat/12-sangiin-vote-parser`）
3. **TDD**：失敗するテストを書く → 最小実装で通す → リファクタ。テストを後付けしない。
4. `pnpm lint && pnpm typecheck && pnpm test && pnpm build` が通ること。
5. PR を出す（テンプレに従う）。Issue を `Closes #N` で紐づける。
6. レビュアーの指摘に対応。Approve 後、PO が squash merge。

## Definition of Done
- [ ] 受け入れ基準をすべて満たす
- [ ] テストがあり、テストが先に書かれた痕跡がある（コミット履歴 or PR説明）
- [ ] lint / typecheck / test / build が CI で green
- [ ] 新しい外部データは `sourceUrl` と取得日時を持つ
- [ ] UI は design tokens（`apps/web/app/styles/tokens.css`）のみ使用。生の色コードを書かない
- [ ] 秘密情報・個人のメールアドレス等をコミットしない
- [ ] 他の PBI と衝突するファイルを最小化（共有ファイルの変更は Issue に明記）
- [ ] **本番にリリースされ、本番の URL で確認できる**（ユーザー指示 2026-08-25）
  - **マージは完了ではない。** 成果物は**リリースされて初めて成果物**とする。
  - コードだけ入って `data/` が古いまま、という状態は**未完了**（#230 / #242 / #244 が実際にそうなった。
    コードは紐づけを拒否するのに、配信しているのは古い出力で、**サイトは表示を変えていなかった**）。
  - スプリントのレビューでは「マージした PBI」ではなく**「本番で確認できる PBI」**を成果として数える。
  - データの変更を伴う PBI は、**作り直し／再取得の実行までが PBI の範囲**。
  - **裏返しもある**——**マージ直後に本番を測ると、リリース前の状態を見る**（2026-09-14、#851）。
    **PO は #840 をマージした 11 分後に本番を測り、「人数は公表記録にありません」と出たので
    「data は直ったのに index.json が古い」と結論して Issue を立てた。**
    **実際は次の Release（11 分後）でその表示は消えた。** **担当者が測り直して食い違いを申告し、PO が誤りを認めた。**
    - **`released` タグと比べてから測る**——`git log --oneline released..origin/main` が空でなければ、
      **本番はまだ古い。**
    - **「マージした」と「本番に出た」は別である。** **この原則の表と裏で、2 回とも同じ境を踏んだ。**
    - **ただし Issue 自体は無駄ではなかった**——**`index.json` が原本と食い違っていたのは事実**で、
      **担当者が `validateLocalAssemblies` に突き合わせを足した。** **前提が誤っていても、見つけたずれは本物だった。**

## 並列作業の衝突回避
この節は何の話か: 並列でエージェントが動くときに worktree・stash・担当の重複で衝突する話。
- ETL と Web は `data/` のファイル契約（`docs/DATA_CONTRACT.md`）だけで結合する。
- 共有ファイル（`routes.ts`, `tokens.css`, `shared/src/index.ts`, `vitest.setup.ts`, `.gitignore`, `package.json` 群, `react-router.config.ts`）の変更は担当 PBI を1つに限定し、他は読み取りのみ。必要なら Issue に「共有ファイル変更あり」と書き、PO が順序を決める。
- フィクスチャは `packages/etl/test/fixtures/` と `apps/web/app/test-fixtures/` に置き、他人のフィクスチャを書き換えない。
- **共有リポジトリの `git stash` を触らない**（2026-09-04）。
  - worktree は作業ツリーを分けるが、**`git stash` はリポジトリ共有**（`.git/refs/stash` は1本）。
    ファイルもブランチも分けたのに、stash だけが全員で1つのスタックを共有している。
  - 実際に起きた: #411 の担当が作業中、**別ブランチの stash（`WIP on fix/387-hsts`）が消えた**。
    自分の stash しか pop していないと言うので、並行作業中の誰かが `stash pop` で
    **他人のものを取った**と考えられる（`pop` は「一番上」を取るので、誰のものかを見ない）。
  - 今回は**実害ゼロ**だった（消えた内容は #386/#387 で、既に本番に出ていた）。
    dangling commit にも残っていた（`git stash apply <sha>` で復旧できる）。**次は失われうる。**
  - **やること**: サブエージェントは `git stash` を使わない。退避が要るなら**自分のブランチに WIP コミット**する
    （worktree ごとにブランチは分かれているので衝突しない）。
    PO も、他人の作業中に `git stash pop` / `drop` を打たない。
    **変異のための退避も stash でやらない**（`scripts/dev/mutate.sh` が `cp` でやる。#542）。
- **並列で実装するときは `git worktree` で作業ツリーを分ける**（Sprint 14 の事故）。
  - 上の3項目は**ファイルの衝突**を防ぐが、**git のブランチ状態は作業ツリー1つにつき1つ**しかない。
    同じクローンで複数のエージェントが動くと、`git checkout` が**他人の作業中のブランチを切り替えてしまう**。
  - 実際に起きたこと：3つの実装が同一クローンで動き、あるブランチが**別の無関係なコミットで上書き**された
    （reflog から復旧）。さらに PO が、動作中のエージェントの未追跡ファイルを「残骸」と誤認して**削除**した。
  - ルール：**`git checkout` でブランチを切り替えない**。commit する段になったら
    `git worktree add <scratchpad>/wt-<issue番号> -b <branch> origin/main` で専用ツリーを作ってそこで commit / push。
  - **作業用の一時ファイルはリポジトリ内に置かない**（scratchpad に置く）。

      **マージ済みの worktree が `scripts/po/worktree-sweep.sh` で消えなくなった**

        後者なら `.measure/` に置かない（`packages/etl/.cache/` は `fetch` の取得キャッシュで、

  - **他人のブランチに force push しない。** push 前に `git ls-remote --heads origin <branch>` で存在を確認する。

  - #574 を担当したサブエージェントの**最終報告が、作業報告ではなく攻撃文だった**。中身は

## テストそのもの（変異・否定的対照・fixture・恒真・自己参照の下限）
この節は何の話か: テストや検査そのものが本当に守っているか、書いただけで満足していないかの話。
- テストは仕様である。テスト名は「何が・どうなる」を日本語で書いてよい。
- 1テスト1アサーション群。モックは境界（HTTP）だけ。
- 実データの HTML はフィクスチャとして保存し、パーサーのテストは必ず実 HTML で行う。
- カバレッジ数値は目標にしない。境界値・異常系（欠損・表記ゆれ・空）を必ず書く。
- **検算は「順序不変」でないか確かめる**（Sprint 12・高知 PR #225 の教訓）。表を復元する ETL で「復元した ○/× の数が一次資料の公表数と一致する」型の検算は、循環論法でなくても **セルの並びを入れ替えても合計が変わらない**ため、列ずれ（＝全議員の賛否が入れ替わる最悪の事故）を検出できない。高知では全行を1列シフトさせても 24 行中 0 行しか落ちなかった。
  - 表を復元するテストには、**「どの議員がどの値か」を名指しする順序敏感なアサーション**を必ず置く（島根 PR #226 の `members[21] === "山根成二"`、`votes[21]` の議長列など）。全会一致でない行を選べば書ける。
  - 追加したら、**実際にセルを1列シフトさせてテストが落ちることを確認する**（推論で済ませない）。
  - 検算が何を保証するかを PR 本文・`DATA_CONTRACT.md` に書くときは、**実態より強い主張をしない**（「脱落・余剰を検出する」と「シフトを検出する」は別物）。
- **同じ出どころでも回次・会期ごとに作りが違う**（Sprint 12・島根 PR #226 / #232 の教訓）。フィクスチャを 1 会期ぶんしか置かないと会期間の差分が検出できない。パーサーのテストは**作りの違う 2 つ以上の実データ**で行う。
  - **「作りが違う」は見た目だけではない。同じテンプレートでも、PDF の中の
    文字の切れ方（アイテムの分割粒度）が会期によって変わる**（#615 秋田で実測、PO が追試）:
    ```
    令和8年7月3日版:   1 セル = 1 アイテム（宮城と同じ前提が通る）
    令和6年12月20日版: "○ ○ ○ ○ ○ ○" が 1 アイテム（6 セルが結合）。該当 10 箇所
    ```
    **宮城の `readRows` は `hits[c].length === 1` を前提にしている**ので、
    **後者をそのまま当てると誤って `UNKNOWN_CELL` になる。**
    **見た目もレイアウトも同じなのに、テキスト層の作りだけが違う**——
    **目で見て「同じ様式だ」と判断してはいけない。**
  - **これは「別人の記録」には直結しないが、静かに落ちる**。1 会期だけで
    フィクスチャを作ると、**もう片方の会期で全議員の賛否が UNKNOWN になる。**
- **外部を叩くものは、テストが緑でも一度は実機で走らせる**（Sprint 13・監視 PR #252 の教訓）。スタブは「自分が想定した世界」しか再現しない。#252 はプローブ先 `/data/assemblies/index.json` が**本番に存在しない**（ビルド時に JS へバンドルされ静的配信されない）のに、curl をスタブしたテストが 37 件緑で通り、マージすれば 10 分毎に必ず失敗して**重複排除により本物の障害を握り潰す**ところだった。実機で一度走らせた結果、さらに**巡回のずらし幅の誤り**（30 分で 9 議会中 5 議会しか見ていない）も見つかった。
  - 監視・デプロイ・外形確認など**本番の URL や設定に依存するもの**は、PR に**実機で走らせた出力を貼る**。否定的対照（わざと失敗させて `fail` が出ること）も添える。
  - 「テストが緑」は「本番で動く」の証明にならない。**前提そのものが偽なら、テストは前提ごと緑になる。**
  - **CI に入れる検査は、否定的対照の PR を draft で立てて「本番の CI で落ちる」ことを示す**
    （#554、2026-09-06。**担当者が指示されずにやった**）。
    #554 は `stale-base` という新しい CI job を足す PR で、**わざと古い土台から切った枝**を
    **別の draft PR（#555）として立てた**:
    ```
    PR #555（古い土台の枝）: stale-base completed/failure
    PR #554（正しい枝）:     stale-base completed/success
    ```
    - **手元で落ちることと、CI で落ちることは別である。**
      `paths:` トリガ・`fetch-depth`・`GITHUB_TOKEN` の権限・`bash -e` ——
      **手元では出会わない条件が CI にはある**（#546 は `bash -e` で実機だけ動かなかった）。
    - **draft にして題に「DO NOT MERGE」と書く。** 役割を果たしたら閉じる。
    - **これは「検査を書いた」ではなく「検査が実際に落ちる」の証拠**であり、
      **検査を入れる PR では最も強い形**である。
  - **生成物を「入っている」と主張するファイルは、主張であって証拠ではない**（#520、2026-09-06）。
    #520 はフォントのサブセットを作り、収録した字を `subset.txt` に書き出して検査に使っていた。
    **`.txt` と `data/` を突き合わせるが、実物の woff2 を一度も読んでいなかった。**
    レビュアーが**woff2 からだけ 1 字を抜き、`.txt` は残す**と:

      正規表現は**3 度書いて 3 度とも穴があった**（行単位で 1 形 → 行単位のまま 4 形 →

      「どう書かれているか」ではなく「**何が起きるか**」を見る、の具体形がこれ。

  - **実データを期待値の源にするテストは、失敗メッセージで「実データが変わったのか、実装が壊れたのか」を

    **実データが変わった** 合図です」）。**どちらで落ちたかが失敗行から分かる。**

  - `browser-check` にテーマの検査を足したとき、**修正のリリース前に本番へ向けて走らせて

## 数字と測り方（測り方を書く・母数と結果・外挿と実測・負荷を書く）
この節は何の話か: 数字や事実をどう測り、どう確かめ、どう書けば読む側が照合できるかの話。
- **「探した場所に無い」と「存在しない」は別**（2026-09-07〜08、PO が 5 回踏んだ）。
  **最初の 3 回は「起票する直前で気づいた」**ので実害は無かった。**4 回目と 5 回目は起票した**——
  **既にある守りを二重に作る Issue を、実際に Ready に置いた**（#634 は取り下げ、
  #636 は前提を訂正して残した）。
  - **先に手順**（5 例に共通していたことなので、例を読む前にこれを守る）:
    - **実装を読んだら、その実装のテストも読む。テストを読んだら、その実装も読む。**
      **5 例のうち 4 例が、この片側だけを見て「無い」と言っていた。**
    - **`grep | head` の結果を「無い」の根拠にしない。**
      **5 例目で、私の grep は実際にヒットしていた**——**1,466 行の出力の 555 行目**にあり、
      **`head -40` で切っていた。** **「探さなかった」のではなく「探した結果を最後まで見なかった」。**
      **`| wc -l` で総数を見て、`head` で切った分が何行あるかを知ってから読む。**
      **絞るなら `head` ではなく検索語を絞る**（見えない行を作らない）。
    - **手探りを始める前に `docs/ops/` を見る**（2026-09-08、6 例目。**今度は探してすらいなかった**）。
      **データの PR を手でマージしたあと本番に反映されず、`deploy-data.yml` の中身を読み、
      concurrency を調べ、run のログを追い、`staging` が cancelled になった理由まで調べました。**
      **`docs/ops/etl.md` の 66 行目に答えが書いてありました:**

      > 手動で PR をマージすれば staging は `push: main` で走るが**production は走らない**点に注意
      > → `gh workflow run deploy-data.yml`

      **ただしその行は「15 分待ってもマージされないとき」の対処表の中にあり、
      私の状況（正常にマージした後）とは別の見出しの下です。**
      **それでも「手動マージでは production が走らない」という事実は同じで、
      `deploy-data` で grep すれば 1 回で出ました**（`docs/` に 20 件、`etl.md` に 6 件）。
      **調べたことは全部正しかったが、全部いらなかった。**

    #477 の担当者は、サブセット版で **`fbGlyph=5`（システム書体に 5 グリフ）**を見た。
    **サブセットが壊したように見える数字**だった。両ビルドで比べると:
    ```
    BASELINE: .member-name "阿達 雅志"  Shippori Mincho ExtraBold:5
    SUBSET  : .member-name "阿達 雅志"  Shippori Mincho ExtraBold:5
    ```
    **`.member-name` は明朝 800**（この PBI が触っていない側）で、**どちらも正しく描かれていた**。
    `fbGlyph=5` は**待ち時間が短すぎた**だけだった。
    - **「3 回測って一致」では防げなかった**: **3 回とも同じ `fbGlyph=5` が出ていた**ので、
      **3 回一致していたら嘘の数字を採用していた。**
      捕まえたのは `getPlatformFontsForNode` と、**なぜそうなるかを両ビルドで比べたこと**。
    - **やること**: 変更後に「壊れた」ように見える数字が出たら、
      **変更前のビルドでも同じ数字が出るか**を必ず見る。
      **出るなら、それは変更のせいではない。**
  - **「3 回測って一致」は必要だが十分ではない**（2026-09-05、#477）。
    **3 回とも待ちが足りなければ、3 回とも同じ嘘の値で一致する。**
    - #477 は `networkidle` + `document.fonts.ready` まで待っても、3 回のうち 1 回
      `/members` が **118 件 1,950 KB ではなく 16 件 268 KB** になった
      （`getPlatformFontsForNode` は **231 件のフォールバック**）。
      **転送量だけ見ていれば「−86%」という嘘の成果**になっていた。
    - `document.fonts.status === "loaded"` を待つ形も**不十分**で、
      テストを並行実行して CPU を食わせると **14 ページ中 13 ページでばらついた**。
    - **正解は「測る前に、測るのと同じ道具で 0 になるまで待つ」。**
      `getPlatformFontsForNode` のフォールバック数が 0 になるまでポーリングし、
      **`settled` フラグとして記録する**。
      **これは 0 に見せかけることではない** — 本当に字が足りなければ何秒待っても 0 にならず、
      `settled: false` として残る。
  - **本番の HTML は「出るもの全部」ではない**（2026-09-05、#477）。

- **自分が出力させた警告は、意味を追うまで読んだことにしない**（#336、2026-09-01）。

  - Sprint 14 のレトロで「変更を伴うコマンドの後は必ず反映を確認してから報告する」を決めた

  - **マージは成果ではない。** 本番へのデプロイは `release.yml` の手動実行だけなので、

## git と PR の運用（比べている基準・二点と三点・マージの成否・rebase）
この節は何の話か: git の出力や CI の状態をどう読み違えたか、PR とマージをどう安全に進めるかの話。
- **追記の PR は、足した行だけでなく「既存の文が壊れていないか」を見る**（#553、2026-09-06）。
  PO が「**すべて同じ根だった——省略した再現である。**」の**直後**に 17 行を挿入したところ、
  その続きだった 3 行（「担当者は…／PO は…／レビュアーは…」）が**主語だけ残って親を失った**。
  **インデントも 8 スペースのまま新ブロック（4 スペース）の下にぶら下がり、Markdown としても壊れた。**
  - **PO は本文でも diff でも気づかなかった。** 追記の diff は
    **足した行が `+` で並ぶだけ**で、**その前後がどう繋がるかは映らない。**
  - **やること**: **挿入したら、その前後 5 行を続けて読む。**
    箇条書きの中に入れるなら、**入れ子の深さ（スペース数）を親と揃える。**
  - **これは「数字を確かめる」と同じ形である**——**足したものは見るが、
    足した結果どうなったかを見ていない。**
  - **CI の状態は commit を固定して読む**（2026-09-05、PO が 1 日に 2 回読み違えた）。
    - **1 回目**: `gh pr checks` の `pending` を待ち続けたが、実体は **`cancelled`** だった
      （PO 自身の push で新しい run が始まり、古いものが自動キャンセルされていた）。
      **`gh pr checks` の表示では pending と cancelled が区別できない。**
    - **2 回目**: `gh run rerun <id>` で緑にしたが、**その run の commit は PR の HEAD ではなかった。**
      branch protection が読むのは `commits/<PR の HEAD>/check-runs` なので、
      **古い commit が緑になっても PR は BLOCKED のまま。**
    - **やること**:
      ```sh
      sha=$(gh pr view <N> --json headRefOid --jq .headRefOid)
      gh api "repos/<owner>/<repo>/commits/$sha/check-runs" \
        --jq '.check_runs[]|"\(.name) \(.status)/\(.conclusion)"'
      ```
      **`gh run view <id>` の緑は、その run の commit が PR の HEAD だとは限らない。**
  - **git の出力は、比べている基準を自分で言えるまで信じない**（2026-09-06、PO が続けて 2 回読み違えた）。
    - **1 回目**: マージ済みの worktree 15 本を掃除する前に「中身が main にあるか」を確かめようとして、
      `git diff origin/main <枝>` を見た。**全部が数百ファイルの差分**に見えたので未マージかと思った。
      **これは枝が古い main から分かれているぶんの差**であって、**枝が加えた変更が残っているかは映らない**。
      正しくは `base=$(git merge-base origin/main <枝>)` を取り、
      **`git diff --name-only $base <枝>` で「枝が触ったファイル」に絞ってから** main と比べる。
      それでも squash マージだと内容一致は保証されないので、**枝が追加した行が main に在るかを直接引く**
      （`git show origin/main:<file> | grep -F <追加行>`）。**15 本すべて取りこぼし 0 だった。**
    - **2 回目**: `git push origin main` の出力に
      `remote: - 4 of 4 required status checks are expected.` が出たのを**拒否だと読み**、
      枝を切って PR を出そうとした。**push は成功していた**（これは branch protection の案内文）。
      `gh pr create` が `No commits between main and <枝>` で落ちて初めて気づいた。
    - **やること**: **`git push` の成否は終了コードと `git rev-parse origin/<branch>` で確かめる。**
      **`remote:` 行は remote からの案内であって、成否ではない。**
    - **3 回目（2026-09-07、PO）**: `gh pr merge` が
      `GraphQL: 4 of 4 required status checks are expected. (mergePullRequest)` を返した。
      **これは push のときと同じ文言だが、今度は本当に拒否だった。**
      **同じ 1 行が、成功のときにも失敗のときにも出る**——だから**この行では何も判断できない。**
      **`git log origin/main` が動いたかどうかだけが証拠**である。
      **やること**: マージの成否は**マージ前後で `git rev-parse origin/main` を比べる**。
      変わっていなければ**マージされていない**（`gh` の終了コードも 0 になることがある）。
    - **「まとめてマージ」はできない**（同上）。**1 本マージすると、残り全部が `BEHIND` になる。**
      6 本を続けて `gh pr merge` に渡したところ、**1 本目以外はすべて拒否**された。
      必須チェックが「土台が最新であること」を要求する設定では、
      **rebase → CI 緑を待つ → マージ、を 1 本ずつ順にやるしかない。**
      並列に投げると、待ち時間ぶんだけ無駄に赤くなる。
    - **「main が動いたか」で判定するときは、動かしうる者が自分だけか確かめる**（2026-09-07、PO）。
      上の教訓に従い、マージの成否を**前後の `git rev-parse origin/main` の比較**で判定する
      仕組みにした。**その判定が、正しいのに「拒否された」と報告した。**
      **マージキューを 2 本同時に走らせていた**ためで、**もう 1 本が先に #532 をマージし、
      自分が測った瞬間には main が「動いていなかった」。** 実際には #532 は**マージされている**
      （`gh pr view 532 --json state` が `MERGED`）。
      - **SHA 比較は「誰も他に動かさない」ことを前提にしている。** 前提が崩れると、
        **`remote:` の行を読むのと同じくらい当てにならない。**
      - **やること**: **同じ資源を触る仕組みは 2 本走らせない**（`mkdir` によるロックを入れた）。
        判定が「動いていない」と言ったときは、**`gh pr view <n> --json state` で PR 自身にも聞く。**
      - **幸い二重マージにはならなかった**（GitHub 側が 2 回目を拒否する）が、
        **同じ作業ツリーを 2 本が同時に rebase する**危険は残っていた。
    - **共通する形**: **どれも「何と何を比べているか」を言えないまま判断していた。**
      **2 回目と 3 回目は同じ 1 行を、一方は成功・他方は拒否と読んでいる。**
      **文言が同じなら、その文言は証拠ではない。**
      **4 つ目は、文言をやめて SHA を見るようにしてもなお誤った**——
      **「比べ方」を直しても、「比べている前提」を書き出していなければ同じ穴に落ちる。**
      作業合意の「**数字を出すときは、測り方も書く**」の、**自分の目で読むとき版**である。
  - **PR を出す前に `git diff origin/main HEAD` を全部読む**（2026-09-05、#477 で寸前に止まった）。
    #477 の担当者が PR 本文を書こうと diff を見たところ、
    **`docs/WORKING_AGREEMENT.md` に 44 行の削除**が出ていた。
    中身は **PO がその日に書いたばかりの教訓**（**しかも担当者自身の発見から書かれたもの**）。
    原因は**ローカルの `origin/main` が 2 コミット古く、リベースの土台が遅れていた**こと。
    - **担当者の言葉**: 「**PR 本文を書こうとして diff を見たから気づきました。
      見ていなければ、PO が私の発見から書いた教訓を、私が消す PR を出していました。**」
    - **今日、リベースの土台が古くて手戻りした人が 3 人いる**（#470 / #485 / #477）。
      **`git fetch` を先にする**だけで防げる。
    - **やること**: PR を出す前に、**`git diff origin/main HEAD --stat` で
      触っていないファイルが出ていないか**を見る。
      **自分が触った覚えのないファイルが出たら、まず `git fetch` してリベースし直す。**
    - **この教訓は、書いた翌日に PO 自身が 2 回破った**（#531 / #534、2026-09-06）。
      **どちらも `docs/WORKING_AGREEMENT.md` への追記だけの PR** で、
      **どちらも 50 行の削除**（`9dd7e44c` 時点の `docs/WORKING_AGREEMENT.md` に限った数）が
      diff に出たまま push していた。**同じ日に #517 の担当者も踏んでいる**（39 行）。
    - **ただし「他人の変更が消える」は誤りだった**（#536 の担当者が実測で訂正、2026-09-06）。
      **三方マージは行を落とさない。** PO は「消しかけた」と 3 回報告したが、
      **同じ形を作って `git merge --squash` を実際に走らせると、
      `10 deletions` と出るのに消えた行は 0 だった**（衝突する形・しない形の両方で確認）。
      ```
      $ git diff master HEAD --numstat     →  1  10  d.md   （10 行の削除に見える）
      $ git merge --squash old && git commit
      $ grep -c '^main-' d.md              →  10           （1 行も消えていない）
      ```
      **本当に消えるのは、衝突を「自分の側を採る」で片付けたとき**である。
      - **やること**: **`WOULD-LOSE`（マージが衝突する）と `DIFF-DELETES`（diff では削除に見えるが
        マージは残す）を分けて見る。** 前者は止めるべきだが、後者は**うるさいだけかもしれない。**
      - **PO の起票（#536）はこの前提を誤っていた。** **「diff がそう見える」を
        「実際にそうなる」と読んだ**——この文書が何度も戒めている形を、また踏んだ。
      - **「読む」で守るのは限界がある。** 追記だけの PR は
        **`--stat` の「ファイル名の一覧」に異物が出ない**ので、
        **ファイル名だけ見ていると気づかない**（削除数そのものは `--stat` にも出る）。
      - **「削除行を数える」は denylist だった。数え方を変えるたびに穴が出た**
        （**PO が 2 回書き、レビューが 2 回とも捕まえた**）:
        | 数え方 | 破れる形 |
        |---|---|
        | `grep -c '^-[^-]'` | **消えた行が `-` で始まる**（**行頭の**箇条書き）→ 0 |
        | `--numstat` / `--shortstat` | **バイナリの削除** → `-\t-` を 0 と足して 0 |
        | 同上 | **upstream 側がリネームしていた** → 全部 insertion に見えて 0 |
        **バイナリの穴は空論ではない**: このリポジトリの woff2 は **371 個**（2026-09-06 時点）で、
        **`0c15263a` で 614 → 492 と一度に 122 個消した前例**がある。
        **フォントが黙って消えれば、表示だけが壊れて diff は綺麗なままになる。**
        - **ただし「この文書で発火した」は誤りだった**（#554 のレビュアーが再現できず、PO も確認）。
          **実在するコミット対 3 組すべてで `--numstat` と `grep -c` は一致した**（15/50/50）。
          この文書の追記は**入れ子の箇条書き**（`  - ` / `    - `）で**行頭が空白**なので `^-` に当たらない。
          **罠は実在するが、この文書では踏んでいなかった。**
      - **`--is-ancestor` で代えようとしたのは誤りだった**（#535、2026-09-06。**PO が 3 度目に間違えた**）。
        「数え方に穴が出るなら数えるのをやめる」と考えて
        `git merge-base --is-ancestor origin/main HEAD` を薦めたが、
        **#554 の実装はこれを意図的に退けていた**:
        > Being BEHIND main is normal and must stay quiet: **firing on it would fail every open PR
        > the moment main moves, and a check that fires on everything is a check nobody reads.**
        **実測**（#554 のレビュアーと PO が別々に確認）: 正常な枝でも `--is-ancestor` は `STALE` を返す。
        **`stale-base.sh` が `ok` と言う枝で、`--is-ancestor` だけが赤くなる。**
        - **「対象が何であっても効く」は「何であっても発火する」の別の言い方だった。**
          **識別力の無い検査は、誰も読まなくなる。**
        - **同じ形を PO 自身が監視で踏んだ**（2026-09-07）。「Ready の Issue があるのに
          **開いている PR が 0** なら、誰も動いていない」という監視を書いた。
          **担当者が作業ツリーで実装中（3 ファイル変更済み・未コミット）でも「誰も動いていない」と報せた。**
          **PR は作業の終わりに出るもので、作業中かどうかを表さない。**
          **数えるべきは「PR の数」ではなく「動いている枝の数」だった**——
          未コミットの変更か `origin/main` より進んだコミットがある worktree を数える形に直した。
          **この節を書いた本人が、同じ日に同じ穴を掘った。**
          - **その直し方も、一度目は足りなかった。** 「動いている枝の数」に変えたところ、
            **54 本が該当した**（本当に動いていたのは 1 本）。**前のセッションの残骸も
            「未コミットの変更あり」のままだった**からで、**これでは本物の停止を覆い隠す。**
            **90 分以内に触られたか**まで見て **54 → 1** になった。
            **「発火しすぎ」を直した先に「発火しなさすぎ」があった**——
            **どちらも識別力が無いことの別の顔である。**
            - **やること**: 監視を直したら、**直した判定を現在の状態に当てて数を見る。**
              **「発火しなくなった」は正しさの証明ではない**（何も検出しない検査も発火しない）。
            - **三度目も足りなかった。** 「90 分以内に触られた枝」は
              **未コミットの変更の更新時刻**で見ていたが、**コミットを打った直後は作業ツリーが
              綺麗になり、見る対象そのものが消える。** 実際に、**55 秒前にコミットして push した
              担当者を「誰も動いていない」と報せた。**
              **直近のコミット時刻**も見る形にしたら、今度は**マージ済みの枝 3 本まで数えた**
              （squash マージなので `origin/main..HEAD` は 0 にならない）。
              **PR の状態が `MERGED`/`CLOSED` なら数えない**を足して、ようやく 1 本になった。
            - **三度とも「片側だけ見ていた」。** 未コミットだけ／コミットだけ／マージ済みを除かない。
              **「作業中」という言葉が指すものを、状態の組み合わせとして書き出していなかった。**
            - **四度目もあった。** **枝を作った直後（まだ何も書いていない＝読んでいる最中）**は、
              変更もコミットも無いので捉えられない。**枝の作成時刻**を足したら、
              **今度はマージ済みの枝 3 本が戻ってきた**（マージのときに `.git` が触られるため）。
              **同じ「マージ済みは除く」を、足した信号にも書く必要があった。**
            - **四度直したという事実の方が、個々の修正より重い。**
              **毎回「いま目に入っている抜け」を 1 つ塞いで終わりにしていた。**
              **やるべきだったのは、最初に「作業中とは何か」を状態の一覧として書き出すこと**だった:
              **枝を作った／読んでいる／編集中／コミット済み／push 済み／PR 有り／マージ済み**。
              **一覧があれば、どの状態を見ていないかが一目で分かる。**
              **一覧を作らずに直すと、抜けを見つけるたびに直す作業が終わらない。**
            - **さらに二度あった（五度目・六度目）。** どちらも**「数えるべきでないものを数えていた」**側:
              - **マージ直前の PR は数秒 `CLEAN` のまま残る。** 1 回だけ見て「放置」と報せた
                （#608 と #611 で 2 回）。**45 秒あけて 2 回確かめ、同じ集合のときだけ報せる**形に直した。
              - **`blocked`（人間の作業待ち）の Issue も `ready` として数えていた。**
                **誰も動けないのが正しい状態**なのに「誰も動いていない」と報せた。
                **`ready` は外さずに、監視側で除いた**——ラベルを外すと
                「もう着手できる状態にはある」という情報まで消えるため。
            - **六度のうち、前半三度は「見落とし」、後半三度は「数えすぎ」だった。**
              **同じ判定を直しているのに、外す方向と入れる方向が交互に出る。**
              **これが「一覧を先に書いていない」ことの症状である**——
              **何を数えるかを決めていないので、毎回その場の一例に合わせて境界を動かしている。**
        - **採られた形**（`scripts/ci/stale-base.sh`）は**両側が触ったファイルだけに絞り**、
          **`WOULD-LOSE`（三方マージが落とす）と `DIFF-DELETES`（diff では削除に見えるが残る）を
          分けて出す**。**denylist をやめたのではなく、比べる対象を正しく絞った。**
        - **PO の誤り**: **自分が書いたコマンドが採用されたはず、を確かめずに教訓へ書いた。**
          「**diff がそう見えることを、実際にそうなると読んだ**」と同じ節で自ら戒めながら、
          **実装を読まずに書いた。**

- **PR のマージは `scripts/po/merge-when-green.sh <pr>` を使う**（2026-09-02）。
  - このスクリプトは **`BEHIND` なら自動で `gh pr update-branch`**、CI が緑になるまでポーリング、
    緑になったら squash マージ＋ブランチ削除まで**1コマンドでやる**。待っている間に main が動いて
    再び `BEHIND` になっても、毎回 `mergeStateStatus` を見て取り込み直す（#89）。
  - **私は手で `gh pr merge` を叩いて `BEHIND` を4回踏んだ。** スクリプトが既にあるのに使わず、
    毎回「失敗 → main を取り込む → push → 待つ」を手でやり直していた。
    さらに**失敗したマージの直後にリリースを走らせた**ことも2回ある（その内容は本番に出ない）。
  - **やること**: マージは原則このスクリプト。手で叩くのは、スクリプトが扱えない事情
    （base ブランチが消えた等）があるときだけ。
- **PR を別の PR の上に積まない**（2026-09-03、#392）。
  - **同じ根っこの事故を3回起こした。** どれも「マージ処理を走らせている間に、その周りで
    人が気づかないまま何かが失われる」型:
    1. マージ処理の起動後に同じブランチへ push → **古い方がマージされ、追加コミットが取り残された**（#389）
    2. `update-branch` の直後に固定 sleep で再試行 → チェック再実行中に3回とも拒まれた（#390）
    3. `test/386-production-paths` を base にしていた #391 が、**#390 のマージでブランチが消えて
       GitHub に CLOSED にされた**。`gh pr reopen` も「base が無い」で通らず、PR を出し直した（#395）
  - **やること**: **PR は原則 main から切る。** 前の PR の変更が必要でも、
    「main にマージされるのを待ってから切る」方が、積むより安い。
  - `merge-when-green.sh` は上の3つを検査して**中断する**ようになった（#392）が、
    **検査は最後の砦であって、積まないのが先**。
  - **マージ処理を走らせたら、そのブランチには触らない。** 待ち時間は数分あるので、
    「ついでに1つ直しておこう」が最も危ない。
- **PR をマージする前に main を取り込む**（2026-09-02）。
  - このリポジトリは「main に追いついていること」をマージ条件にしている。
    `gh pr merge` が `BEHIND` で失敗しても**エラーメッセージは "administrator privileges" としか言わない**ので、
    権限の問題だと誤読しやすい。実際に必要なのは `git merge origin/main` して push すること。
  - **マージが失敗したら、まず `gh pr view <n> --json mergeStateStatus` を見る。**
    `BEHIND` なら main を取り込む、`BLOCKED` なら CI 待ち、`DIRTY` なら競合。
  - **失敗したマージの直後にリリースを走らせない。** マージできていないので、
    その内容は本番に出ない（今回2回とも、直前にマージ済みの別の変更を出し直しただけだった）。

## CI と検査の作り方（識別力・握り潰さない・無限後退を止める場所）
この節は何の話か: CI に入れる検査そのものをどう設計すれば、緩んだときに黙って通らないかの話。
- **「ローカルが緑」は「CI が緑」の証明にならない。そして「CI が緑」も「正しい」の証明にならない**
  （#244 の CI 失敗、2026-08-25）。
  - `matchCommitteeRoles` が `localeCompare` で並べており、**手元（`LANG=ja_JP`）は読み順、
    CI（`LANG` 未設定＝`en-US`）はコードポイント順**になって、手元で緑・CI で赤になった。
    フレークではなく**実装の欠陥**で、本番でも実行環境しだいで議員ページの表示順が変わる。
  - **PR を出したら報告の前に `gh pr checks` を見る。** 実装者もレビュアーもローカルの
    「全部 green」を報告し、PO がマージ直前に CI の赤に気づいた。
  - **決定的なのはこの実測**: `localeCompare` に戻すと `ja_JP` では 5 件落ちるが、
    **CI と同じ `en-US` では 17 件すべて通る**。その文字列では2つの比較が一致してしまい、
    **どんな黒箱テストを書いても CI では退行を検出できない**。振る舞いのテストは
    **偽の安心**を与えるだけだった。
  - **検出したいものが環境によって観測できなくなるときは、テストの対象を振る舞いからソースに移す。**
    `stable-order.test.ts` は `packages/etl/src` のソースを検査して `.localeCompare(` を禁じる
    （`member.css.test.ts` が tokens.css から比を計算して opacity を禁じるのと同じ流儀）。
  - 文字列の並びは**コードポイント順**（`cmp = (a, b) => (a < b ? -1 : a > b ? 1 : 0)`）で統一する。
  - **検査が指示する手順が、検査を黙らせないか見る**（2026-09-05、#507）。
    #490 の検査は、落ちるとこう指示する（良いメッセージ）:
    > **増えた分が `import.meta.glob` に触らないことを確かめて、この一覧を更新してください**

    **その手順で「触らないことを確かめる」だけを飛ばすと、検査は完全に黙る**（実測 6/6 全部緑。
    その状態で `tsx sitemap.ts` は `glob is not a function` で落ちる）。
    - **今日それが実際に起きた**: #479 のマージで #490 の検査が落ち、
      PO は担当者に「**一覧を14モジュールに更新する**」と指示した。
      担当者は**検査器自身に測らせて**確かめたので正しかったが、
      **急いでいれば飛ばす手順**だった。
    - **「うっかりなら落ちる」は、塞がない理由にならない。**
      **落ちる場合があることは、落ちない場合が無いことの証明にならない**（#484 と同じ）。
    - **やること**: 検査に「こうしてください」というメッセージを書いたら、
      **その手順を実行したときに検査が黙らないか**を確かめる。
      **「更新してください」と指示する検査が、更新の副作用で黙るなら、指示のほうが罠。**
  - **防御は「不可能にすること」ではなく「隠れて通れなくすること」**（2026-09-05、#507 のレビュー）。
    今日、**検査を殺す変異を完全には閉じられない**ことが何度も分かった。
    **それでも前進はある** — **変異のコストが上がれば、レビューで見える。**
    - #507 の例: 直す前は「**述語を 1 つ足す**」だけで黙った。
      直した後は「**3 箇所の呼び出しを別の関数に差し替える**」が要る。
      **どちらも「原理的には閉じていない」が、後者はレビューで目に見える改変。**
    - **危険度は「閉じているか」ではなく「差分が何行か」で測る。**
      **差分 1 行で通る変異は、差分 20 行の変異よりずっと危険。**
    - **やること**: 「完全に閉じる」を目指さない。
      **「隠れて通れるか」を問う。** 隠れて通れるなら塞ぐ。
      目に見える改変が要るなら、**そこで止めてよい**（#504 / #507 の担当者の線引きは正しかった）。
  - **「塞げるのに塞いでいない」と「そのレイヤでは塞げない」を区別する**（2026-09-05、#504 のレビュー）。
    今日、検査を殺す変異が何度も見つかったが、**2 種類ある:**

## セキュリティレビュー（OSS 前提・必須）
レビュアーは毎 PR で以下を**実際に grep／実行して**確認し、1つでも該当すれば blocking：
- 秘密情報：鍵・トークン・パスワード・`.env`（履歴・フィクスチャ・ログ・スクリーンショット含む）
- サーバー情報：他サイトのドメイン名、内部ホスト名、非公開パス、ユーザー名、ポート番号の不要な露出。VPS は可能な限りドメイン名で書き、IP を増やさない
- スクリプト：`set -euo pipefail`、`nginx -t` 失敗時に reload しない、共用 nginx の `sites-enabled/` に一時ファイルを置かない、他サイトの資産に触れない、deploy 鍵ユーザーに権限を足さない
- Web：外部への通信なし（フォントは自サイト配信、CSP に外部ホストを足さない）、`dangerouslySetInnerHTML` なし、外部リンクに `rel=noopener noreferrer`、localStorage は try/catch、クエリ／パスから組み立てる URL は許可リスト
- ETL：取得先ドメインの許可リスト、ファイル書き込みはリポジトリ内 `data/` のみ、パストラバーサルなし
- 依存：新規依存の追加理由、`pnpm audit` に high 以上が無い

CI が機械的に見る分（`.github/workflows/security.yml`、Issue #133）: gitleaks（PR 差分／週次の全履歴）、`scripts/ci/forbidden-patterns.sh`（鍵ヘッダ・トークン形式・追跡された `.env`・公開 IP（除外ディレクトリなし）・secret `FORBIDDEN_PATTERNS` の正規表現。secret が無いと fork PR 以外では失敗）、`fixture-secret`（`test/fixtures/` の中の第三者の鍵・トークン。**gitleaks の既定ルールは Google の `AIza…` 形を検出しない**——#785 で実測。母数 0 は clean ではなく error）、`scripts/ci/audit.sh`（high 以上。例外は `scripts/ci/audit-ignore.txt` に期限と理由つき）。
シェルは `bash scripts/ci/shellcheck.sh` で lint（Issue #154）。対象（`scripts/**`・`deploy/**` の `*.sh` と bash/sh shebang の拡張子なしファイル）はこのスクリプトだけが列挙し、CI も同じコマンドを呼ぶ。PR 前に手元で実行する（`--list` で対象確認）。
他サイト名の禁止パターンは**リポジトリに書かず** repo secret `FORBIDDEN_PATTERNS`（改行区切りの正規表現）に置く。VPS の IP も書かない（ssh は `$VPS_SSH_HOST`、既定 `sakura-vps`）。nginx の reload は `if nginx -t; then systemctl reload nginx; else exit 1; fi` の形（`deploy/test/nginx-reload.test.sh`）。報告窓口は `SECURITY.md`。

### `pr-closes` が赤いとき、本文を直しても `gh run rerun` では緑にならない

**2026-09-14、PR #860 で実測**（担当者がジョブのログを読んで特定した）。

`ci.yml` の `pr-closes` は **イベントのペイロード**から本文を読む:

```
PR_BODY: ${{ github.event.pull_request.body }}
```

**`gh run rerun` は「その run が作られた時点の本文」を再生する。**
**本文を編集しても rerun では反映されない。**

**直し方**: **空コミットを push して新しい `synchronize` イベントを起こす。**

```
git commit --allow-empty -m "chore: 本文を直したので pr-closes を測り直す"
git push
```

**押す前に手元で確かめるなら**——GitHub から本文を読み直して、**自作の正規表現ではなく実物の
`scripts/ci/pr-closes.sh`** に食わせる:

```
gh pr view <番号> --json body --jq .body > /tmp/body.txt
bash scripts/ci/pr-closes.sh - < /tmp/body.txt; echo "exit=$?"
```

**否定的対照も取る**（逃げ道や `Closes #N` を消した本文で `exit=1` になること）。
**`| echo $?` では測れない**——パイプの最後のコマンドの終了コードを見ることになる。
PO は最初これで両方 0 に見えた。**ファイルに落としてリダイレクトで測る。**

**この手順を `ci.yml` のコメントに書いてはいけない。**
`scripts/ci/test/pr-closes.test.sh` の wiring 検査が
`assert_not_contains "$body" 'gh pr view'`（#793「CI は API を叩かない」）を見ていて、
**コメントか実行の行かを区別しない**ので落ちる（PO が PR #863 で実際に落とした）。
**検査の側を緩めない**——緩めると実行の行も見逃す形に弱まる。**手順はここに書く。**

### 時間を 1 回だけ測って数字にしない——交互に測る

**2026-09-14、#855 の担当者が実測して自分で気づいた。**

新しいテストが CI を遅くしないかを測るのに、**WITH を測ってから WITHOUT を測った:**

```
WITH 115.3 秒 / WITHOUT 81.4 秒   →  ＋34 秒
```

**これは嘘だった。** **自分が並列に走らせていた別の測定との取り合いである。**

**交互に測り直した**（WITH / WITHOUT を続けて 3 組）:

| 組 | WITH | WITHOUT | 差 |
|---|---|---|---|
| 1 | 79.1 | 80.4 | **−1.3** |
| 2 | 80.5 | 80.4 | **＋0.1** |
| 3 | 159.0 | 154.3 | ＋4.7（**両方遅い。機械が混んでいた**） |

**中央値の差は ＋0.1 秒——測定の揺れの中だった。**

**組 3 が効いている**——**両方が同じだけ遅くなったので、「機械が混んでいた」と言い切れる。**
**片方だけ測っていたら、組 3 の 159 秒を「遅くなった証拠」として出していた。**

**規則**:

- **時間は必ず交互に測る**（WITH → WITHOUT → WITH → WITHOUT …）。**まとめて測ってから比べない。**
- **最低 3 組。** **中央値を出す。** **1 回の値を数字として出さない。**
- **同時に別の重い測定を走らせない**（または、走らせるなら**両方に同じだけ掛かる形にする**）。
- **本番（CI）で測れるなら、そこでも測る。** **ローカル 16 CPU と CI 4 CPU では並列度が違う。**

**なぜ起きるか**: **節は「同じ位置に足される」。** 文書の末尾や、同じ見出しの後ろに
**別々の人が別々の節を足すと、行の並びとしては同じ場所の書き換えに見える。**

- **解いたあと、両親に対して「消えた行」を数える。** 片方だけでは足りない:

```
git show origin/main:<file> > /tmp/m.md
git show HEAD:<file>        > /tmp/h.md
comm -23 <(sort -u /tmp/m.md) <(sort -u <file>) | grep -vc '^$'   # main から消えた行
comm -23 <(sort -u /tmp/h.md) <(sort -u <file>) | grep -vc '^$'   # 自分の側から消えた行
```

  「落ちたから消えた」のかは、数だけでは分からない**——
  **PO は 1 行の欠落を見つけ、`grep` で差し替え後の行が在ることを確かめてから通した。**
- **節の見出しを数える。** `grep -c '^## ' で、**両親に在った節がすべて在ることを見る。**
- **`scripts/ci/stale-base.sh --net-deletions` は通るので、これでは気づけない**——
  **節が落ちても、別の人が足した行で総数が増えていれば「差し引きで減っていない」になる。**

**`--net-deletions` が ok でも、節が落ちていないことの証明にはならない。**
